= Packages
:description: GitLab package registry and Conan package publishing

Cuppa can consume (and publish) prebuilt packages from a GitLab generic package registry via `cuppa.package_dependency()`.
You can also publish Cuppa-built libraries as **Conan 2** packages (parallel to GitLab generic packages; see <<conan-package-publishing>>).

== package_dependency

[source,python]
----
import cuppa

MyPkg = cuppa.package_dependency(
    'mypkg',
    package_manager = 'gitlab',
    registry = 'https://gitlab.example.com/api/v4/projects/123/packages/generic',
    package = 'mypkg',
    version = '1.2.3',
)

cuppa.run(
    dependencies = [MyPkg],
    default_dependencies = ['mypkg'],
)
----

Package archives are typically *per toolchain / variant / architecture*.
A missing package surfaces as a registry HTTP error (often `404`) during configure, before compile.

== Authentication

|===
| Mechanism | Notes

| `GITLAB_REGISTRY_TOKEN` | Personal or project access token with package read (and write if publishing)
| `CI_JOB_TOKEN` | Used automatically in GitLab CI when available
| `--<name>-gitlab-custom-token` | Point at another env var / token setting for that package
|===

The `cuppa` launcher redacts env values whose names contain `TOKEN` in logged output.

== Develop vs package downloads

`--develop` affects *location* develop paths and package develop flags where defined.
It does *not* invent a local substitute for a missing registry archive: the matching package must exist in the registry or already be cached under the download/cache roots.

== Boost package

`cuppa.packages.boost_package.define(...)` builds a `boost_package` dependency backed by the registry:

[source,python]
----
import cuppa

BoostPkg = cuppa.packages.boost_package.define(
    registry = 'https://gitlab.example.com/api/v4/projects/123/packages/generic',
    version = '1.85',
)

cuppa.run(
    dependencies = [BoostPkg],
    default_dependencies = ['boost_package'],
)
----

Use `package.use_libs([...])` helpers where provided to append the correct static library files for the active toolchain/variant.

== Publishing (GitLab generic)

From a sconscript, `env.PublishPackage(...)` with a `GitlabPackagePublisher` builds a toolchain-scoped tarball.
Add `--publish-package` to upload it to the GitLab generic registry.
`env.InstallPackage(...)` installs a package into the local cuppa download layout.

[#conan-package-publishing]
== Conan 2 publishing (optional)

Cuppa can package libraries it has already built and export them into a Conan 2 cache (and optionally upload to a remote).
Conan does **not** drive the compile: Cuppa remains the orchestrator.

Use `ConanPackagePublisher` with the same `env.PublishPackage(...)` method used for GitLab:

[source,python]
----
Import('env')
from cuppa.package_managers.conan import ConanPackagePublisher

lib = env.BuildStaticLib('mylib', 'mylib.cpp')

publisher = ConanPackagePublisher(
    env,
    name = 'mylib',
    version = '1.2.3',
    user = 'myorg',          # optional → mylib/1.2.3@myorg/stable
    channel = 'stable',
    remote = 'artifactory',  # required only for upload
    remote_url = None,       # optional: conan remote add if missing
    source_include_dir = 'include',
    source_lib_dir = env['abs_final_dir'],
)

env.PublishPackage(lib, publisher)
----

Without `--publish-package`, Cuppa stages headers/libs, writes a minimal `conanfile.py`, and runs `conan export-pkg` into the local Conan cache (settings match the active toolchain and variant via the same mapping as `conan_deps`).

With `--publish-package`, Cuppa also runs `conan upload` to `remote=` (and may `conan remote add` when `remote_url=` is set and the remote is missing).

[NOTE]
====
Reuse `--publish-package` for both GitLab and Conan publishers.
If several `PublishPackage` nodes appear in the graph, each publisher runs when the flag is set.
====

=== Authentication

Cuppa does not store Conan credentials.
Configure remotes and login before the Cuppa job (or in CI):

|===
| Mechanism | Notes

| `CONAN_LOGIN_USERNAME` / `CONAN_PASSWORD` | Common for non-interactive `conan remote login`
| GitLab CI | Often `ci_user` + `CI_JOB_TOKEN` against a GitLab Conan remote
| Pre-login | `conan remote login <name>` already done by the user or pipeline
|===

=== Offline behaviour

With `--offline`, `export-pkg` may still update the **local** Conan cache.
Upload is refused with a clear error (remotes are not contacted for publish).

=== Consumer round-trip

A second Cuppa project can require the published reference through existing `cuppa.conan_deps` / `conan_dependency` (see xref:dependencies.adoc#conan-2-consumer-optional[Dependencies]).
Settings fidelity matters: consume with the same toolchain, variant, arch, and C++ dialect that produced the package.

[WARNING]
====
GitLab's Conan 2 package registry may still be marked under development.
Treat it as one possible remote; Artifactory and other Conan 2 remotes are equally valid targets.
====

MVP recipes are leaf packages (headers + libs, no generated `requires`).
Hand-written recipes, shared/static options, and transitive Conan requires are follow-on work (see `CONAN_PUBLISH_PLAN.md` in the repository).
