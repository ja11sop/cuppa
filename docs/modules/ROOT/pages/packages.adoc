= Publishing packages
:description: Publish Cuppa-built libraries to GitLab generic registries and Conan 2

Consuming a prebuilt archive belongs under Dependencies:
xref:dependencies/packages.adoc[Package dependencies] and
xref:dependencies/gitlab.adoc[GitLab packages].
This page is about **publishing** libraries that Cuppa has already built.

You can publish to a GitLab generic package registry (`env.PublishPackage` +
`GitlabPackagePublisher`) or as **Conan 2** packages (`ConanPackagePublisher`; see
<<conan-package-publishing>>).

== Publishing (GitLab generic)

From a sconscript, `env.PublishPackage(...)` with a `GitlabPackagePublisher` builds a toolchain-scoped tarball
and writes a ``.packaged`` stamp beside it in ``final/``. The toolchain token in the archive stem is
`toolchain.package_name()`, which follows `--toolchain-identity=` (see
xref:toolchains/overview.adoc#toolchain-identity[Build and package identity]). Switching identity
does not rename archives already in a registry; republish or use consume-side lookup
(`--package-gitlab-toolchain-override-<name>=`,
`--package-gitlab-identity-fallback`) described in
xref:dependencies/gitlab.adoc#consume-overrides[GitLab lookup overrides].
`--package-gitlab-os-identity=include|omit` (default `include`) controls whether the
published basename includes the OS id (`widget_debian_gcc15_…`) or omits it
(`widget_gcc15_…`). Omit is an ABI bet that the artefact is not OS-scoped; it is not
the product default. Consume prefers the same encoding when the flag is set, and with
fallback on also tries the other shape after a `404`. When staged headers and libs are not newer than the
existing archive, cuppa skips recreating the tarball — so a follow-up ``cuppa --rel --publish-package`` can
upload without re-tarring multi-gigabyte trees.
Add `--publish-package` to upload it to the GitLab generic registry.
`env.InstallPackage(...)` installs a package into the local cuppa dependencies layout.

=== Declaring transitive dependencies

Pass ``dependencies=[...]`` to ``GitlabPackagePublisher`` when package **A** needs other GitLab
packages at include or link time. Cuppa writes ``cuppa-dependency.json`` into the staged package
directory (next to ``include/`` / ``lib/``) before creating the archive. Omit the argument when
there are no edges — no manifest file is written, matching today's standalone packages.

[source,python]
----
publisher = GitlabPackagePublisher(
    env,
    source_include_dir = '#/include',
    source_lib_dir     = env['abs_final_dir'],
    registry           = 'https://gitlab.example/api/v4/projects/1',
    package            = 'widget',
    version            = '1.0.0',
    dependencies = [
        {
            'name': 'fmt',
            'package': 'fmt',
            'version': '12.1.0',
            'registry': 'same',
            'use_libs': ['fmt'],
        },
    ],
)
env.PublishPackage(lib, publisher)
----

Consumers that ``BuildWith`` / link **A** pick up **B** from the manifest — see
xref:dependencies/gitlab.adoc#transitive-package-dependencies[Transitive package dependencies].

Relative `source_include_dir` / `source_lib_dir` values are SCons nodes under the active variant directory. Cuppa copies from the generated path when it exists, and only falls back to `srcnode()` for a source-tree directory that is present. Always using `srcnode()` would look for a missing project-root copy such as `boost/1.92/lib` and fail the package step, especially under `--parallel`. Use `env['abs_final_dir']` when libraries already land in `final/`. The same resolution is used for Conan publishing (<<conan-package-publishing>>).

Authentication for registry upload uses the same tokens as consume
(`GITLAB_REGISTRY_TOKEN`, `CI_JOB_TOKEN`, `--<name>-gitlab-custom-token`).
See xref:dependencies/gitlab.adoc[GitLab packages].

[#publishing-from-external-cmake]
=== Publishing from an external CMake build

Some packages are built by **CMake** (or another external tool) and only *packaged* by Cuppa.
Cuppa still owns the sconscript graph: `Command()` configure/build steps, optional `Install()`,
then `PublishPackage()`. Map Cuppa's active toolchain and variant into CMake flags so
`--dbg` / `--rel` / `--cov` and `--toolchains=` produce matching external builds instead of
always forcing `Release` and a hard-coded compiler path.

Use xref:methods/custom-commands.adoc[Custom commands] when you need a raw
`Command()`, but prefer **`env.CMakeConfigure` / `CMakeBuild` / `CMakeInstall`**
for the usual configure → build → install graph. Those methods wrap
`cuppa.buildsys.cmake` (Option B argv helpers) and `cuppa.utility.command.run` so
`CMAKE_BUILD_TYPE` / `CMAKE_CXX_COMPILER` track the active variant and toolchain,
and `CMakeBuild` passes ``cmake --build --parallel N`` when you pass Cuppa
``--parallel``. Pair with xref:methods/staging-files.adoc[Staging files]
when you need `Install()` into a package layout under `final/`.

Lower-level: `cmake_configure_command` / `cmake_build_command` remain available if
you must hand-wire `env.Command` yourself.

==== Cuppa surface → CMake flag

The active toolchain and variant are bound on each sconscript `env` for the current
toolchain×variant invoke. Prefer the zero-arg accessors:

[source,python]
----
cxx = env.Toolchain().binary()
name = env.Variant().name()   # dbg, rel, cov, …
----

`env['toolchain']` / `env['variant']` remain valid. Do not use keyed `env.Toolchain(name)` for
the active handle (that form is deprecated; use `HasToolchain(name)` for registry checks).

[cols="2,2,3",options="header"]
|===
| Cuppa surface | Typical CMake flag / use | Notes

| `env.Toolchain().binary()` or `env['CXX']`
| `-D CMAKE_CXX_COMPILER=…`
| Cuppa-resolved absolute driver (including fetched toolchains)

| `env['CC']`
| `-D CMAKE_C_COMPILER=…`
| When the project also builds C

| `env.Variant().name() == 'dbg'`
| `-D CMAKE_BUILD_TYPE=Debug`
| Mirror `--dbg`

| `'rel'`
| `-D CMAKE_BUILD_TYPE=Release`
| Mirror `--rel` — do **not** hard-code Release for every Cuppa variant

| `'cov'`
| `-D CMAKE_BUILD_TYPE=RelWithDebInfo`
| Cuppa `--cov` instruments *Cuppa* compiles (gcov/llvm-cov). A pure CMake tree does
  **not** get that instrumentation unless the project adds its own coverage flags

| `env.StdCpp(...)` / `--stdcpp` / toolchain default
| `-D CMAKE_CXX_STANDARD=…`
| Mapped by `cmake_configure_args` when `env['stdcpp']` is a known dialect
  (`c++20` → `20`, …). Tokens such as `c++latest` are omitted; `c++2c` / `c++26`
  map to `26` when your CMake is new enough

| `publisher.package_variant()` (or the same token Cuppa uses in package stems)
| Subdirectory for `-B` (for example `_build/<variant_token>`)
| Keeps dbg/rel/cov (and toolchain) configure trees from clobbering each other

| `env['abs_build_dir']`
| Destination for copied libs / completion markers under the sconscript variant
| Good `Command` targets beside Cuppa's `working/` layout

| `env['abs_final_dir']` and paths under `final/`
| `CMAKE_INSTALL_PREFIX` and/or `Install()` destinations
| Large third-party trees often install once under `final/`, then publish from that prefix

| `--parallel` / `env['job_count']`
| `cmake --build … --parallel N` via `env.CMakeBuild`
| When Cuppa `--parallel` is set, `CMakeBuild` passes `--parallel` with
  `env['job_count']` (affinity-aware — same count as SCons `-j`, after the
  wrapper leaves cores free for the OS). Override with `jobs=N` or omit with
  `jobs=False`. Nested oversubscribe is possible if several CMake builds run
  under SCons `-j` at once; use `jobs=` then.

| Generator (`-G Ninja`, …)
| Author choice (`generator=` on `CMakeConfigure`)
| Common on Linux; not required by Cuppa

| `cuppa -c` / SCons clean
| Removes configure/build/install stamps **and** the CMake `-B` tree
| `CMakeConfigure` / `CMakeBuild` / `CMakeInstall` register `env.Clean` on the
  absolute `-B` path (including trees under location-dependency checkouts).
  Without that, clean only removes Cuppa copies/stamps and the next build
  looks like a no-op ninja rebuild.
|===

==== Pattern A — small library: configure, build, install, publish

Sketch: CMake produces a static archive; Cuppa copies or installs headers/libs into a package
tree under `final/`, then `PublishPackage`.

[source,python]
----
Import( 'env' )
import os
from cuppa.package_managers.gitlab import GitlabPackagePublisher

# Source tree already available (location dependency, extract step, …)
widget_src = env.BuildWith( 'widget_src' ).local_sub_path()

package_dir = os.path.join( env['abs_final_dir'], 'package' )
publisher = GitlabPackagePublisher(
    env,
    source_include_dir = os.path.join( package_dir, 'include' ),
    source_lib_dir     = os.path.join( package_dir, 'lib' ),
    registry           = 'https://gitlab.example/api/v4/projects/1',
    package            = 'widget',
    version            = '1.0.0',
)

cmake_build_dir = os.path.join( '_build', publisher.package_variant() )
configure = env.CMakeConfigure(
    widget_src,
    working_dir = widget_src,
    build_dir = cmake_build_dir,
    generator = 'Ninja',
    extra_defines = { 'WIDGET_BUILD_TESTS': False },
)
built = env.CMakeBuild(
    configure,
    build_dir = cmake_build_dir,
    working_dir = widget_src,
)

# Install or copy headers/libs into package_dir, then:
# env.PublishPackage( installed_nodes, publisher )
----

When `PublishPackage` is sourced from the include `Install` only, order the library
Install with `Requires(installed_include, installed_lib)` under `--parallel` — do not
use `Depends` for that edge (headers should not re-copy when only the `.a` changes).
See xref:methods/staging-files.adoc#package-staging-with-install[Staging files].

==== Pattern B — install prefix: CMake install, then publish

Sketch: CMake installs into a prefix under `final/`; `GitlabPackagePublisher` points
`source_include_dir` / `source_lib_dir` at that prefix.

[source,python]
----
Import( 'env' )
import os
from cuppa.package_managers.gitlab import GitlabPackagePublisher

# extraction_folder = … Dir under env['build_dir'] after download/extract …
install_prefix = env.Dir( os.path.join( env['final_dir'], 'installed' ) )
publisher = GitlabPackagePublisher(
    env,
    source_include_dir = os.path.join( str( install_prefix ), 'include' ),
    source_lib_dir     = os.path.join( str( install_prefix ), 'lib' ),
    registry           = 'https://gitlab.example/api/v4/projects/1',
    package            = 'widget',
    version            = '2.28.0',
)

cmake_out = os.path.join( '_build', publisher.package_variant() )
configure = env.CMakeConfigure(
    extraction_folder,
    working_dir = extraction_folder,
    source_dir = '.',
    build_dir = cmake_out,
    install_prefix = install_prefix,
    extra_defines = { 'BUILD_TESTING': False },
)
built = env.CMakeBuild(
    configure,
    build_dir = cmake_out,
    working_dir = extraction_folder,
)
installed = env.CMakeInstall(
    built,
    build_dir = cmake_out,
    working_dir = extraction_folder,
    target = install_prefix,
)
# env.PublishPackage( installed, publisher )
----

[NOTE]
====
`GitlabPackagePublisher.build_package` stages include/lib (and modules, when
present) under `final/<package>/<version>/`. Staging is created when missing
and **refreshed when the source tree is newer** than the staged copy (same-path
source and stage are left alone). `publisher.sources()` lists include and lib
when those paths sit **outside** `abs_final_dir`; trees under the final
directory are omitted to avoid SCons dependency cycles — wire the install or
library node through `env.PublishPackage(source, publisher)` instead. Packaging
a large install prefix still **duplicates** disk use on the first package; see
https://github.com/ja11sop/cuppa/issues/209[#209] for in-place packaging
follow-on.
====

[#conan-package-publishing]
== Conan 2 publishing (optional)

Cuppa can package libraries it has already built and export them into a Conan 2 cache (and optionally upload to a remote).
Conan does **not** drive the compile: Cuppa remains the orchestrator.

Use `ConanPackagePublisher` with the same `env.PublishPackage(...)` method used for GitLab:

[source,python]
----
Import('env')
from cuppa.package_managers.conan import ConanPackagePublisher

lib = env.BuildStaticLib('mylib', 'mylib.cpp')

publisher = ConanPackagePublisher(
    env,
    name = 'mylib',
    version = '1.2.3',
    user = 'myorg',          # optional → mylib/1.2.3@myorg/stable
    channel = 'stable',
    remote = 'artifactory',  # required only for upload
    remote_url = None,       # optional: conan remote add if missing
    source_include_dir = 'include',
    source_lib_dir = env['abs_final_dir'],
    shared = False,          # optional; None = infer from staged libs
    requires = None,         # optional; generated recipe only
    # conanfile = 'conanfile.py',  # optional hand-written recipe override
)

env.PublishPackage(lib, publisher)
----

`source_include_dir` / `source_lib_dir` (and `source_modules_dir` / `conanfile=`) use the same VariantDir path resolution as GitLab publishing above.

Without `--publish-package`, Cuppa stages headers/libs, writes a minimal `conanfile.py` (unless `conanfile=` is set), and runs `conan export-pkg` into the local Conan cache (settings match the active toolchain and variant via the same mapping as `conan_deps`).

With `--publish-package`, Cuppa also runs `conan upload` to `remote=` (and may `conan remote add` when `remote_url=` is set and the remote is missing).

=== Generated recipe options and requires

When Cuppa generates the recipe:

* `shared=True/False` sets Conan `options.shared` / `default_options` and `package_type`, and passes `-o shared=…` to `export-pkg`. When omitted, Cuppa infers static vs shared from staged library files.
* `requires=['fmt/12.1.0', …]` embeds those dependencies on the generated recipe. At `export-pkg` time they must already be in the local Conan cache if you are `--offline` (otherwise remotes may be used by Conan).

=== Hand-written `conanfile=`

Pass `conanfile='conanfile.py'` to copy a recipe you author into the stage instead of generating one.
Cuppa still stages `include/` and `lib/` and still supplies settings / name / version / user / channel on `export-pkg`.
Declare `requires`, `package()`, and `package_info()` in that recipe yourself.
`requires=` on the publisher is ignored when `conanfile=` is set (Cuppa logs a warning).

Hand-written recipes must still only **package** prebuilt artefacts — do not call Cuppa or compile from `build()`.
If you override `package()` and ship modules, copy staged `modules/` (Cuppa still stages BMIs into the recipe folder when `final/modules/module-map.json` exists).

=== Packaged modules (BMI)

When the producer builds with `--modules`, `BuildLib` installs BMIs under `final/modules/` with `module-map.json`.
`ConanPackagePublisher` copies that tree into the Conan package (same layout as GitLab generic packages).
`cuppa.conan_deps` consumers automatically call `load_packaged_modules` when a dependency’s package contains `modules/module-map.json` and the consumer build uses `--modules`.
BMI extensions remain toolchain-family specific (`.gcm` / `.pcm` / `.ifc`).

Optional ctor: `source_modules_dir=` to point at a modules tree explicitly; otherwise `\{source_lib_dir}/modules` is used when `module-map.json` is present.

[NOTE]
====
Reuse `--publish-package` for both GitLab and Conan publishers.
If several `PublishPackage` nodes appear in the graph, each publisher runs when the flag is set.
====

=== Authentication

Cuppa does not store Conan credentials.
Configure remotes and login before the Cuppa job (or in CI):

[cols="2,3"]
|===
| Mechanism | Notes

| `CONAN_LOGIN_USERNAME` / `CONAN_PASSWORD` | Common for non-interactive `conan remote login`
| GitLab CI | Often `ci_user` + `CI_JOB_TOKEN` against a GitLab Conan remote
| Pre-login | `conan remote login <name>` already done by the user or pipeline
|===

=== Offline behaviour

With `--offline`, `export-pkg` may still update the **local** Conan cache.
Upload is refused with a clear error (remotes are not contacted for publish).
Recipes with `requires` still need those packages already cached locally under `--offline`.

=== Consumer round-trip

A second Cuppa project can require the published reference through existing `cuppa.conan_deps` / `conan_dependency` (see xref:dependencies/conan.adoc#conan-2-consumer-optional[Conan packages]).
Settings fidelity matters: consume with the same toolchain, variant, arch, and {cpp} dialect that produced the package.

[WARNING]
====
GitLab's Conan 2 package registry may still be marked under development.
Treat it as one possible remote; Artifactory and other Conan 2 remotes are equally valid targets.
====

Components / multi-lib `cpp_info.components` remain deferred (tracked as https://github.com/ja11sop/cuppa/issues/125[#125]).
Conan packages may include Cuppa `modules/module-map.json` + BMIs for parity with GitLab generic packages; consumers load them automatically via `conan_deps` when `--modules` is enabled.
