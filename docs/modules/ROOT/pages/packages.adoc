= Publishing packages
:description: Publish Cuppa-built libraries to GitLab generic registries and Conan 2

Consuming a prebuilt archive belongs under Dependencies:
xref:dependencies/packages.adoc[Package dependencies] and
xref:dependencies/gitlab.adoc[GitLab packages].
This page is about **publishing** libraries that Cuppa has already built.

You can publish to a GitLab generic package registry (`env.PublishPackage` +
`GitlabPackagePublisher`) or as **Conan 2** packages (`ConanPackagePublisher`; see
<<conan-package-publishing>>).

== Publishing (GitLab generic)

From a sconscript, `env.PublishPackage(...)` with a `GitlabPackagePublisher` builds a toolchain-scoped tarball
and writes a ``.packaged`` stamp beside it in ``final/``. The toolchain token in the archive stem is
`toolchain.package_name()`, which follows `--toolchain-identity=` (see
xref:toolchains/overview.adoc#toolchain-identity[Build and package identity]). Switching identity
does not rename archives already in a registry; republish or use consume-side lookup
(`--package-gitlab-toolchain-override-<name>=`,
`--package-gitlab-identity-fallback`) described in
xref:dependencies/gitlab.adoc#consume-overrides[GitLab lookup overrides].
`--package-gitlab-os-identity=include|omit` (default `include`) controls whether the
published basename includes the OS id (`widget_debian_gcc15_…`) or omits it
(`widget_gcc15_…`). Omit is an ABI bet that the artefact is not OS-scoped; it is not
the product default. Consume prefers the same encoding when the flag is set, and with
fallback on also tries the other shape after a `404`. When staged headers and libs are not newer than the
existing archive, cuppa skips recreating the tarball — so a follow-up ``cuppa --rel --publish-package`` can
upload without re-tarring multi-gigabyte trees.
Add `--publish-package` to upload it to the GitLab generic registry.
`env.InstallPackage(...)` installs a package into the local cuppa dependencies layout.
The publish step depends on the archive file as well as the empty ``.packaged`` stamp, so
a retar (for example after updating ``cuppa-publish.json``) invalidates upload under
SCons ``MD5-timestamp``.

[#publish-version-latest]
=== Publisher ``version="latest"`` (seed vs staged identity)

The same floating tokens used on consume —
xref:dependencies/gitlab.adoc#version-latest[registry ``latest``] —
are available on ``GitlabPackagePublisher``: ``version="latest"``, ``"current"``,
or ``None``. This is a **general** publisher facility, not Boost-only. Boost is
the workflow that needs it most often today; any GitLab package publisher can
use the same kwargs.

Cuppa splits identity on purpose:

| Where | What is written |
|-------|-----------------|
| Publisher-tree seed ``cuppa-publish.json`` (beside ``sconstruct``) | May keep the floating token (``"latest"`` / ``"current"``) so you need not hand-edit the seed on every release |
| Staged archive under ``final/<package>/<concrete>/`` and its traveling ``cuppa-publish.json`` | Always a **concrete** version string |
| Registry upload URL | Same concrete version |

Nothing in the uploaded tarball claims to be the word ``latest``. Consumers that
pin ``version="latest"`` still resolve against **registry** contents after you
upload; they never re-resolve the publisher's floating seed.

==== How Cuppa picks the concrete pin

When the publisher ``version`` is floating, resolve order is:

. **Active ``BuildWith``** for that package name (and, for registry slug
  ``boost``, source ``BuildWith('boost')`` before ``boost_package``) — the
  usual case when the sconscript already built or consumed the package this
  session.
. **Upstream Boost latest** (package ``boost`` only) — major.minor form, same
  as ``Boost.version().replace('_', '.')`` / ``boost_package.latest_release()``.
. **Registry latest** for ``registry`` + ``package`` — the same
  ``gitlab_latest`` helper as consume ``version="latest"``.

If none of those yield a pin, configure / publisher construction fails with an
actionable error. Pass an explicit concrete ``version=`` when you want the seed
and the archive to agree (most libraries that cut named releases in git).

==== When floating helps, and when it does not

*Use* ``version="latest"`` when the publisher tree's authored identity is meant
to float with the session — for example a leaf that always publishes “whatever
``BuildWith`` resolved,” or a tip seed you do not want to bump by hand every
cut. Cascade still discovers the tree from the seed; nested publish uploads
under the concrete folder and URL.

*Prefer a concrete* ``version=`` when the tracked seed should be a reviewable
pin (typical for application and library publishers with SemVer tags).

*Do not confuse* registry latest with upstream software latest. For ordinary
packages, step 3 above means “newest version **already in our registry**,”
which is a poor pin for a *first* upload of a brand-new upstream release (the
registry has nothing newer yet). In that case resolve from ``BuildWith`` of the
tree you just built (step 1), or pass the concrete version explicitly. Source
Boost is the exception that also understands upstream latest (step 2).

Minimum / range pins (``>=1.28.0``) are a separate story; this token is only
the named floating ``latest`` / ``current`` spelling.

==== Example (any package)

[source,python]
----
from cuppa.package_managers.gitlab import GitlabPackagePublisher

# After BuildWith('abseil_cpp') (or equivalent) has a concrete version this session:
Publisher = GitlabPackagePublisher(
    env,
    source_include_dir = include_path,
    source_lib_dir     = lib_path,
    registry           = 'https://gitlab.example/api/v4/projects/1',
    package            = 'abseil-cpp',
    version            = 'latest',  # seed keeps latest; stage/upload use BuildWith pin
)
----

For a full Boost sconscript that uses the same facility (plus upstream Boost
resolve when needed), see
xref:dependencies/gitlab.adoc#publishing-boost-from-source[Publishing Boost from source].

[#build-and-publish-dependencies]
=== Cascading dependency publishes

Deep GitLab package stacks are painful to publish by hand (leaves first, then
parents, then the tip). Pass ``--build-and-publish-dependencies`` with a companion
action — ``--publish-package`` (nested publish + tip upload) or
``--publish-cascade-dependencies`` (nested publish, tip build only):

[source,shell]
----
cuppa -D --rel --toolchains=gcc15 \
  --publish-package --build-and-publish-dependencies \
  --publisher-root=~/coding/packages

# Or: nest-publish deps, tip build only (consume-only or publisher tip)
cuppa -D --rel --toolchains=gcc15 \
  --publish-cascade-dependencies --build-and-publish-dependencies \
  --publisher-root=~/coding/packages
----

Cuppa then:

* Reads this publisher’s ``dependencies=`` (optional ``package_source`` on each
  edge, else one declared on the dependency itself) and expands the DAG from each
  resolved tree’s ``cuppa-publish.json``
* Resolves each node to a publisher working tree: the dependency's
  xref:#cascade-develop[``develop`` tree] when you pass ``--develop``, else
  ``package_source`` (filesystem path), else an existing tree under
  ``--publisher-root`` or the default ``<storage-root>/publishers`` forest
  (``{root}/{name}``, ``{root}/{package}``, or one nesting level), cloning from
  a ``package_source`` URL when you pass ``--clone-publishers``
* Runs a nested ``cuppa -D … --publish-package`` for each dependency in
  leaf-first order (**without** re-entering cascade)
* Invalidates that package’s download/extract caches under the tip’s storage
  roots and re-fetches from the registry so the tip build sees the new
  artefacts
* Continues with this project’s normal build and publish when ``--publish-package``
  is set (publisher tip), or **build only** when ``--publish-cascade-dependencies``
  is set (consume-only or publisher tip)

Pre-sconscript ``BuildWith`` still runs before cascade on publisher tips.
Consume-only tips run cascade **after** the sconscript read (once it is clear no
tip publisher constructed); Slice F deferral still covers a missing registry pin
during that earlier ``BuildWith``. When a tip dependency is
one cascade can publish (``package_source``, a publisher-shaped ``develop=``, or
a tip ``cuppa-publish.json`` edge with a source) and the registry returns
``404``, cuppa **defers** that fetch instead of stopping: nested publish and the
refresh above fill the consume cache. A registry-only pin that cascade cannot
publish still fails immediately. If a deferred pin is still missing after
cascade, cuppa stops and names the package.

Publisher builds stage a single traveling ``cuppa-publish.json`` (identity, deps
including ``package_source``, optional ``default_use_libs`` / ``link``) and seed
a copy beside the tip ``sconstruct`` for local cascade discovery. The publisher
may use floating ``version="latest"`` on that seed while the staged archive and
registry upload stay concrete — see
xref:#publish-version-latest[Publisher version latest]. Consume and
``--list-dependencies`` ``requires`` read the traveling file; legacy
``cuppa-dependency.json`` remains a **read-only fallback** for older extracts.

``--build-and-publish-dependencies`` **enables** the graph; pair it with a
companion **action**:

* ``--publish-package`` — nested publish, then tip **upload** (publisher tips)
* ``--publish-cascade-dependencies`` — nested publish, then tip **build only**
  (consume-only and publisher tips; cannot combine with ``--publish-package``)
* ``--cascade-plan`` / ``--collect-cascade`` / ``--update-publishers`` — stop modes

Bare cascade alone is refused. Seed each direct package pin with
``package_source=…`` (or a develop publisher tree under ``--develop``); transitive
edges come from each resolved tree’s ``cuppa-publish.json``. Missing
``package_source`` / unresolved trees fail before nested uploads. A
``package_source`` URL needs either a tree that
already exists under ``<storage-root>/publishers`` (or ``--publisher-root``), a
filesystem ``package_source``, or ``--clone-publishers``, described next.

[#cascade-consume-only]
==== Consume-only tips (app projects)

An application that only **consumes** GitLab packages (no tip
``PublishPackage``) can still drive cascade from its ``package_dependency`` list.
Declare ``package_source`` on each direct package edge that should open the DAG
(for example the root of a stack), then plan or nest-publish under a monorepo forest:

[source,python]
----
cloud = cuppa.package_dependency(
        'google_cloud_cpp',
        registry       = REGISTRY,
        package        = 'google-cloud-cpp',
        version        = '2.28.0',
        package_source = 'git@gitlab.example:org/packages/google_cloud_cpp.git',
)
----

[source,shell]
----
cuppa -D --rel --toolchains=gcc15 \
  --build-and-publish-dependencies --cascade-plan \
  --publisher-root=~/coding/packages

cuppa -D --rel --toolchains=gcc15 \
  --build-and-publish-dependencies --collect-cascade --clone-publishers \
  --publisher-root=~/coding/packages

cuppa -D --rel --toolchains=gcc15 \
  --build-and-publish-dependencies --publish-cascade-dependencies \
  --publisher-root=~/coding/packages
----

The last form nest-publishes the package DAG (nested sessions still pass
``--publish-package``) and then **builds the tip** — it does not upload the app.
Use ``--publish-package`` instead of ``--publish-cascade-dependencies`` only when
the tip itself should upload.


[#cascade-develop]
==== Publishing from a tree you are working in

When you run with ``--develop``, a dependency's develop path is the tree cascade
publishes from. It outranks both ``package_source`` and ``--publisher-root``,
because a develop path is you naming the copy you mean for this run, where a root
convention is cuppa guessing one:

[source,python]
----
capy = cuppa.package_dependency(
        'capy',
        registry = REGISTRY,
        package  = 'capy',
        version  = 'develop',
        develop  = '../../packages/capy'
)
----

That path is anchored to the ``sconstruct`` directory, so it means the same tree
wherever you invoke cuppa from, and
xref:cli/dependencies-and-develop.adoc[``--list-develop``] reports it. A
``--<name>-<manager>-develop=`` override on the command line takes precedence, as
it does everywhere else.

Cascade needs the project that *publishes* the package here, which is a tree with
an ``sconstruct``. A develop path pointing at a built package — a prefix with
``include/`` and ``lib/`` and no ``sconstruct`` — is refused for cascade with both
meanings named (consume still accepts that prefix shape with a log note). A
develop path with no tree at that location is likewise refused: cascade never
clones into a develop path, since that is
``--clone-develop``'s job. A staged ``cuppa-publish.json`` does not make a prefix
a publisher tree, because publisher builds stage that manifest beside ``include/``
and ``lib/``.

Because such a tree is the *source* of the package rather than the package,
``--develop`` does not swap it in as the prefix this build links against.
Instead the tip links ``include/`` and ``lib/`` from an existing stage under
``_build/.../final/<package>/<version>/``. If that stage is missing, Cuppa stops
with a clear error naming ``--stage-develop``.

Pass ``--develop --stage-develop`` to nest-build that tree (stage, no upload) from
the tip, and to nest ``-c`` / ``--clean`` into those trees as well. The same
flag also nest-builds **location** ``develop=`` Cuppa projects (normal project
build; the tip still compiles against the develop path). See
xref:dependencies/managing/develop.adoc[Working with develop copies]. The same
develop path still ranks first for cascade when you also pass
``--build-and-publish-dependencies``; cascade may upload afterward, but local
consume does not depend on the upload succeeding.

A develop path that is only a built prefix (``include/`` and ``lib/``, no
``sconstruct``) keeps today's prefix swap, with a log note that the publisher-source
shape is preferred for new work.

Without ``--develop``, a configured develop tree is left alone and the plan says
so, rather than leaving you to wonder why the tree you have been editing was
ignored.

===== Local work is not publishable

Cascade refuses to publish from a develop tree holding work that exists only on
your machine — uncommitted changes, unpushed commits, or a branch with no
upstream — because the resulting registry version could not be rebuilt from
history. Every offending tree is named at once, before the first upload, rather
than one per failed session:

[source,text]
----
cascade will not publish from a develop tree holding work only this machine has,
because the registry version could not be rebuilt from history: [capy develop
(capy)] at [~/coding/packages/capy] has uncommitted changes, 2 commits not
pushed. Commit and push, drop --develop for the publish run, or pass
--publish-modified-develop to publish anyway.
----

A detached head is fine: publishing version X from tag ``vX`` is the normal case,
and a commit you can name is a commit others can fetch. A tree cuppa cannot read
as a working copy raises a warning rather than a refusal, since being unable to
inspect a tree is not evidence of local work.

A tree found under ``--publisher-root``, or cloned by ``--clone-publishers``,
runs the same hazard and is reported the same way — but as a **warning**, and the
publish goes ahead. Those trees are how cascade has always worked, and refusing
them would stop a workflow that predates the question. The plan report grades them
as warning rows, so you can see what a run is about to put in the registry without
being stopped by it.

``--publish-modified-develop`` lifts the refusal for a run and says so on every
tree it allows. ``--cascade-plan`` reports the same judgement without publishing:
an error row per tree that would be refused, or a note row per tree the override
allows.

[#clone-publishers]
==== Fetching publisher trees on demand

``--clone-publishers`` lets cascade clone a publisher tree it cannot find locally
from that dependency's ``package_source`` URL, which may be pinned:

[source,python]
----
'package_source': 'git@gitlab.example:packages/capy@develop'
----

A pin may name a branch, a tag, or a revision. Branch names containing ``/``
(``@feature/cascade``) are fine. Tags are welcome here even though
``--clone-develop`` refuses them, because publishing version X from tag vX is the
normal case; a tag or revision lands on a detached head. A filesystem
``package_source`` is never pinned — that tree is whatever you have checked out,
and honouring a pin would mean switching your branch.

Cloning is opt-in rather than automatic, because cascade does not merely fetch a
tree: it runs a build in it, which executes that tree's ``sconstruct``. Edges
deeper in the stack come from ``cuppa-publish.json`` inside **downloaded
archives**, so without the flag a registry manifest could decide which
repositories your machine clones and builds. Run xref:#cascade-plan[
``--cascade-plan``] first to see every URL and destination before anything is
fetched.

Where a clone lands follows what you asked for. The same path is searched for an
**existing** tree even without ``--clone-publishers``, so a forest populated on
an earlier run is found again the way ``downloads_root`` falls back to
``storage_root``:

[cols="1,2"]
|===
| Flags | Destination / lookup forest

| No publisher root
| ``<storage-root>/publishers/<name>`` — cuppa owns that tree, so a bare cascade
  never writes into your working area; a later run finds it without re-passing
  ``--clone-publishers``

| ``--publisher-root=PATH``
| ``PATH/<name>`` — the first place the resolver already looks, so the clone is
  found again by the same rules. Use this when you want those trees somewhere you
  can explore and work in
|===

Cascade clones once and then leaves the tree alone. An existing tree is always
preferred over cloning, and is used exactly as it stands: cascade never switches
branches, stashes, resets, or fetches, and reports when a reused clone is not on
the revision a ``package_source`` pinned. A destination that already holds a
different repository is refused rather than overwritten, as is a clone whose tree
turns out to have no ``sconstruct`` or ``cuppa-publish.json``. Cloning needs the
network, so it is not available with ``--offline``.

Clones are keyed by dependency name, matching the rest of cuppa's storage layout.
Two dependencies whose URLs differ but whose names collide are refused with both
URLs named, rather than one quietly publishing from the other's tree. Trees under
the storage root are not yet listed by the ``--list-*`` reports, so remove them by
path when you are done with them.

[#cascade-plan]
==== Checking the plan before anything uploads

A cascade run publishes to a registry, so it is worth seeing the resolved order
first. ``--cascade-plan`` reports that order and stops. It needs the cascade flag
it describes, but not ``--publish-package``, because nothing is built, published,
or uploaded:

[source,shell]
----
cuppa -D --rel --toolchains=gcc15 \
  --build-and-publish-dependencies --cascade-plan \
  --publisher-root=~/coding/packages
----

The report lists each dependency in publish order — package nodes first, with
errors, warnings, and notes nested beneath them the way a judgement tree nests
reasons under a severity heading — and this package last. The invoking command
line sits above the tree so recommended flags can be compared with flags already
present (cascade-relevant ones are emphasised):

[source,text]
----
Printing Cascade plan for building and publishing package widget [==0.2.0] given the command:
cuppa -D --rel --toolchains=gcc15 --build-and-publish-dependencies --cascade-plan --publisher-root=~/coding/packages

Cascade plan: widget [==0.2.0] (this package) with 2 package dependencies: [0 errors][0 warnings][0 notes]
│
├── 1 of 2  capy [==develop]
│           └── using publisher at [/home/user/coding/packages/capy]
├── 2 of 2  corosio [==0.3.1]
│           └── using publisher at [/home/user/coding/packages/corosio]
└── then widget [==0.2.0] from this tree

--cascade-plan: 1 package planned; nothing was built, published, uploaded, or cloned.
----

Unlike a real run, which stops at the first dependency it cannot place, the plan
reports **every** unresolved tree. Hard failures (no URL to clone, bad path) are
an **error** group and the finish line exits non-zero. A URL ``package_source``
with nothing local yet and without ``--clone-publishers`` is a **warning**
(pass ``--clone-publishers`` to make the plan executable) plus **notes** for
alternatives (``--publisher-root``, a develop path + ``--develop``) — not advice
to rewrite the dependency's ``package_source``. A develop path configured without
``--develop`` is likewise a **warning** (pass ``--develop``) plus **notes**; when
a tree already exists under the publishers forest, a second **warning** says the
plan would use that copy instead. Construct announces
``Running in PACKAGE BUILD: CASCADE PLAN mode`` (short info-label chip plus plain
qualifying text) the same way clone-develop announces itself.

With ``--clone-publishers``, a tree cascade would fetch is a note group rather than
an error, naming the URL, the pin, and where it would land. The plan stops at such a
node, because a dependency's own edges live in the ``cuppa-publish.json`` inside a
tree that does not exist yet:

[source,text]
----
Printing Cascade plan for building and publishing package widget [==0.2.0] given the command:
cuppa -D --rel --toolchains=gcc15 --build-and-publish-dependencies --cascade-plan --clone-publishers

Cascade plan: widget [==0.2.0] (this package) with 1 package dependency: [0 errors][0 warnings][2 notes]
│
├── 1 of 1  capy [==develop] (git@gitlab.example:packages/capy)
│           │
│           └── 2 notes
│               ├── would clone [git@gitlab.example:packages/capy] at [develop] into
│               │   [~/.cuppa/publishers/capy]
│               └── its own package dependencies are not known until that tree exists,
│                   so nothing is planned beneath it
└── then widget [==0.2.0] from this tree

--cascade-plan: 1 package planned, 1 publisher tree to clone first; nothing was built, published, uploaded, or cloned.
----

[#collect-cascade]
==== Collecting publisher trees without building

When the next step is a full ``--publish-package`` cascade, you may want every
publisher tree on disk first — clone what is missing, reuse what is already
there — without compiling or uploading. ``--collect-cascade`` does that. It
needs the cascade flag and typically ``--clone-publishers``; it does **not**
need ``--publish-package``, and it is not the same as ``--publish-package -n``
(SCons dry-run still configures nested sessions, which cannot create
``.sconf_temp`` — a full cascade refuses ``-n`` / ``--no-exec`` up front):

[source,shell]
----
cuppa -D --rel --toolchains=gcc15 \
  --build-and-publish-dependencies --collect-cascade --clone-publishers
----

Construct announces ``Running in PACKAGE BUILD: CASCADE COLLECT mode`` as a short
info-label chip, with plain detail that resolve/clone runs without build or
publish. The plan header says **collecting packages**; warnings say make this
**collect** executable. The finish line counts publisher trees actually gathered
(``0 publisher trees collected`` when ``--clone-publishers`` was still needed),
not tip packages.

[#update-publishers]
==== Updating publisher trees

``--collect-cascade`` reuses an existing forest tree as it stands — it does not
fetch. When ``~/.cuppa/publishers/…`` (or a ``--publisher-root`` checkout) is
behind its upstream, pass ``--update-publishers``. It uses the same gates as
``--update-develop``: fetch, then fast-forward only when the copy is clean,
tracking an upstream, and strictly behind. Dirty, ahead, diverged, or detached
trees are left alone. Trees ranked from ``--develop`` /
``develop=`` are skipped — use ``--update-develop`` for those.

The report is an **ACTION** table (not the ``STATUS`` severity column from
``--list-develop``): live rows read **updated** / **no change** / **left alone**;
dry-run rows read **would update** / **no change** / **leave alone**. On a tty,
remote checks rewrite one subdued status line (``Fetching [name] (i/n) ·`` plus
git ``--progress``), then clear it so the table replaces that line.

[source,shell]
----
cuppa -D --rel --toolchains=gcc15 \
  --build-and-publish-dependencies --update-publishers

cuppa -D --rel --toolchains=gcc15 \
  --build-and-publish-dependencies --collect-cascade --clone-publishers \
  --update-publishers
----

Requires the cascade flag. Alone (or with ``--collect-cascade``) it stops before
build/upload. With ``--publish-package`` it updates first, then runs the nested
publish. Refuse ``--cascade-plan`` (review-only) and ``--offline`` for a live
update. ``-n`` still contacts remotes when online so **would update** vs
**no change** is honest; only the fast-forward is skipped. Offline ``-n`` falls
back to the last observed state. Untracked paths that a fast-forward would
overwrite are **leave alone** / **left alone** (warn), not a post-merge
**failed**.

A real cascade prints the same plan before its first nested publish, then brackets
each nested session with a banner naming the session number, the publisher tree,
the command it ran, and how long it took. Cascade deliberately does not capture or
re-indent nested output: that would cost colour, progress rewriting, and
interleaved stderr from the build you are watching. The banners mark the
boundaries instead, and a closing banner says this package is resuming.

When a dependency's tip consume archive already matches the registry (local file
size equals a successful ``HEAD`` ``Content-Length``, and the extract has
``include/``), cascade **skips** that nested session and reports
``skipped (current)``. Pass ``--force`` to rebuild and upload every node anyway
(nested ``PublishPackage`` targets are ``AlwaysBuild``). Tip consume cache is
invalidated and re-fetched **only after a nested session that actually
uploaded**, and only for the tip's current toolchain stem — sibling stems under
``downloads/packages/<pkg>/<ver>/`` stay put. With multiple tip toolchains
(``--toolchains=gcc15,gcc16``), the nested publish graph runs **once** per tip
command (forwarding the full toolchain list), not once per tip variant.

With ``-c`` / ``--clean``, the plan intro says **cleaning package**, nested
sessions forward ``-c``, the closing banner counts **nested clean(s)**, and
cascade does **not** invalidate/re-fetch the tip consume cache afterward (nothing
was uploaded). The plan also notes that out-of-tree CMake ``-B`` trees under
location downloads are removed only when the publisher registers ``env.Clean`` on
them — ``CMakeConfigure`` / ``CMakeBuild`` do; raw ``Command`` wrappers often do
not. In that case Cuppa still cleans ``working/`` / ``final/`` stamps, but the
next rebuild can look like an incremental Ninja build while re-packaging and
re-uploading. See xref:#publishing-from-external-cmake[Publishing from an external
CMake project].

Session end banners report ``uploaded`` or ``no registry upload`` when the tip
can tell (nested upload marker). Skipped-current nodes never start a nested
``scons``.

[#amend-package-manifest]
=== Amending metadata without rebuilding

When only traveling metadata changes (for example adding
``default_use_libs: []`` on a fat package, or correcting dependency pins), a full
DownloadExtract → CMake → install cycle is disproportionate. Pass
``--amend-package-manifest`` together with the usual variant and toolchain flags:

[source,shell]
----
cuppa -D --rel --toolchains=gcc15 --amend-package-manifest --publish-package
----

Cuppa then:

* skips ``DownloadExtract``, ``RemoveEmptyDirs``, and ``CMakeConfigure`` /
  ``CMakeBuild`` / ``CMakeInstall`` (they register no-op stamps so the graph still
  links)
* rewrites ``cuppa-publish.json`` from the current ``GitlabPackagePublisher``
  kwargs (``dependencies``, ``default_use_libs``, ``link``) and removes any
  legacy ``cuppa-dependency.json`` twin
* retars from an existing ``final/<package>/<version>/`` stage when present;
  otherwise extracts a local ``.tar.gz`` / ``.zip`` under ``final/``, or downloads
  that archive from the registry first
* uploads when ``--publish-package`` is also set (same publish dependency on the
  archive as a normal retar)

This path does **not** refresh include/lib payloads from ``source_include_dir`` /
``source_lib_dir``. Use a normal publish (without ``--amend-package-manifest``)
when binaries or headers change. Consumers that already cached the same version
need a download refresh after a same-version overwrite — see
xref:dependencies/gitlab.adoc[GitLab packages] and the planned
``--refresh-downloads`` work.

=== Declaring transitive dependencies

Pass ``dependencies=[...]`` to ``GitlabPackagePublisher`` when package **A** needs other GitLab
packages at include or link time. Cuppa writes ``cuppa-publish.json`` into the staged package
directory (next to ``include/`` / ``lib/``) before creating the archive. Entries may be bare
BuildWith **names** (``'protobuf'``), partial dicts, or mixed. When only ``name`` is given,
``package`` defaults to the hyphenated form (``opentelemetry_cpp`` → ``opentelemetry-cpp``);
when only ``package`` is given, ``name`` defaults the other way. Pass both when the slug is not
that transform (for example Boost). You may omit ``version`` when those packages are already on
the env via ``BuildWith`` / ``auto_enable_dependencies`` — the publisher fills the pin from the
active package object at package time. An explicit ``version`` still wins. Empty or omitted
``registry`` means ``same``.

Optional package-level fields on the same publisher (written into the same manifest):

* ``default_use_libs=[...]`` — stems linked when a consumer primary-``BuildWith``s / auto-enables
  the package (not when it is pulled only as a transitive include). Use ``[]`` for fat packages
  that must not link by default.
* ``link=`` — ``prefer_static`` (default), ``prefer_shared``, ``static``, or ``shared``.

Omit ``dependencies`` and those fields when the package is standalone with no defaults — then no
manifest file is written. Publishing only ``default_use_libs`` still writes the file.

[source,python]
----
publisher = GitlabPackagePublisher(
    env,
    source_include_dir = '#/include',
    source_lib_dir     = env['abs_final_dir'],
    registry           = 'https://gitlab.example/api/v4/projects/1',
    package            = 'widget',
    version            = '1.0.0',
    default_use_libs   = [ 'widget' ],
    dependencies = [
        'fmt',
        { 'name': 'boost_package', 'package': 'boost', 'use_libs': ['system'] },
    ],
)
env.PublishPackage(lib, publisher)
----

Consumers that ``BuildWith`` / link **A** pick up **B** from the manifest — see
xref:dependencies/gitlab.adoc#transitive-package-dependencies[Transitive package dependencies].

Relative `source_include_dir` / `source_lib_dir` values are SCons nodes under the active variant directory. Cuppa copies from the generated path when it exists, and only falls back to `srcnode()` for a source-tree directory that is present. Always using `srcnode()` would look for a missing project-root copy such as `boost/1.92/lib` and fail the package step, especially under `--parallel`. Use `env['abs_final_dir']` when libraries already land in `final/`. The same resolution is used for Conan publishing (<<conan-package-publishing>>).

Authentication for registry upload uses the same tokens as consume
(`GITLAB_REGISTRY_TOKEN`, `CI_JOB_TOKEN`, `--<name>-gitlab-custom-token`).
See xref:dependencies/gitlab.adoc[GitLab packages].

[#publishing-from-external-cmake]
=== Publishing from an external CMake build

Some packages are built by **CMake** (or another external tool) and only *packaged* by Cuppa.
Cuppa still owns the sconscript graph: `Command()` configure/build steps, optional `Install()`,
then `PublishPackage()`. Map Cuppa's active toolchain and variant into CMake flags so
`--dbg` / `--rel` / `--cov` and `--toolchains=` produce matching external builds instead of
always forcing `Release` and a hard-coded compiler path.

Use xref:methods/custom-commands.adoc[Custom commands] when you need a raw
`Command()`, but prefer **`env.CMakeConfigure` / `CMakeBuild` / `CMakeInstall`**
for the usual configure → build → install graph. Those methods wrap
`cuppa.buildsys.cmake` (Option B argv helpers) and `cuppa.utility.command.run` so
`CMAKE_BUILD_TYPE` / `CMAKE_CXX_COMPILER` track the active variant and toolchain,
and `CMakeBuild` passes ``cmake --build --parallel N`` with the **same**
``N`` as Cuppa ``--parallel`` / ``env['job_count']`` (affinity-sized, never
bare ``--parallel``), or ``--parallel 1`` when Cuppa ``--parallel`` is off.
Pass ``jobs=False`` on ``CMakeBuild`` to omit ``--parallel`` and leave the
generator default. Pair with xref:methods/staging-files.adoc[Staging files]
when you need `Install()` into a package layout under `final/`.

Lower-level: `cmake_configure_command` / `cmake_build_command` remain available if
you must hand-wire `env.Command` yourself.

==== Acquiring upstream source (`DownloadExtract`)

Publisher sconscripts often start from a GitHub release tarball. Prefer
**`env.DownloadExtract`** over hand-rolled `wget` / `tar` `Command` strings — Cuppa
uses the shared download progress reporter and stamps a marker file under the
extract directory:

[source,python]
----
extracted = env.DownloadExtract(
    'https://github.com/example/widget/archive/v1.0.0.tar.gz',
    extract_dir = 'widget',
    marker = 'CMakeLists.txt',   # default
    strip_components = 1,        # default (GitHub nests sources one level deep)
)
----

Feed `extracted` into `RemoveEmptyDirs` and/or `CMakeConfigure`. The method
registers `Clean` on `extract_dir`.

==== Empty submodule placeholders (`RemoveEmptyDirs`)

GitHub source archives often leave **empty** directories for git submodules under
`third_party/`. Some upstream trees only fetch those paths when they do **not**
exist (for example gRPC's `gRPC_DOWNLOAD_ARCHIVES`). An empty directory still
exists, so configure fails later looking for files under it.
`cuppa -c` / deleting `_build` does not help: every fresh extract recreates the
empties.

After extract, call **`env.RemoveEmptyDirs`**, then list the stamp among
`CMakeConfigure`'s sources. Candidate selection:

* `gitmodules=True` — only empty immediate children of `parent` that appear as
  submodule paths in `<dirname(parent)>/.gitmodules` (good default when the
  extract has a root `.gitmodules`)
* omit `names` and `gitmodules` — every empty immediate child of `parent`
* `names=(…)` — definitive list (overrides `gitmodules`)

[source,python]
----
archives = env.RemoveEmptyDirs(
    extracted,
    parent = os.path.join( working_src, 'third_party' ),
    gitmodules = True,
    target = 'src/.cuppa_download_archives.stamp',
)
configure = env.CMakeConfigure(
    [ extracted, archives ],
    working_dir = extraction_folder,
    # …
)
----

Or call `cuppa.buildsys.acquire.remove_empty_dirs(…)` from your own `Action`
(`cuppa.buildsys.cmake.remove_empty_dirs` still re-exports the same helper).
Populated trees stay; library submodules you satisfy via `*_PROVIDER=package`
/ system packages do not need to remain as empty placeholders.

==== Cuppa surface → CMake flag

The active toolchain and variant are bound on each sconscript `env` for the current
toolchain×variant invoke. Prefer the zero-arg accessors:

[source,python]
----
cxx = env.Toolchain().binary()
name = env.Variant().name()   # dbg, rel, cov, …
----

`env['toolchain']` / `env['variant']` remain valid. Do not use keyed `env.Toolchain(name)` for
the active handle (that form is deprecated; use `HasToolchain(name)` for registry checks).

[cols="2,2,3",options="header"]
|===
| Cuppa surface | Typical CMake flag / use | Notes

| `env.Toolchain().binary()` or `env['CXX']`
| `-D CMAKE_CXX_COMPILER=…`
| Cuppa-resolved absolute driver (including fetched toolchains)

| `env['CC']`
| `-D CMAKE_C_COMPILER=…`
| When the project also builds C

| `env.Variant().name() == 'dbg'`
| `-D CMAKE_BUILD_TYPE=Debug`
| Mirror `--dbg`

| `'rel'`
| `-D CMAKE_BUILD_TYPE=Release`
| Mirror `--rel` — do **not** hard-code Release for every Cuppa variant

| `'cov'`
| `-D CMAKE_BUILD_TYPE=RelWithDebInfo`
| Cuppa `--cov` instruments *Cuppa* compiles (gcov/llvm-cov). A pure CMake tree does
  **not** get that instrumentation unless the project adds its own coverage flags

| `env.StdCpp(...)` / `--stdcpp` / toolchain default
| `-D CMAKE_CXX_STANDARD=…`
| Mapped by `cmake_configure_args` when `env['stdcpp']` is a known dialect
  (`c++20` → `20`, …). Tokens such as `c++latest` are omitted; `c++2c` / `c++26`
  map to `26` when your CMake is new enough

| `publisher.package_variant()` (or the same token Cuppa uses in package stems)
| Subdirectory for `-B` (for example `_build/<variant_token>`)
| Keeps dbg/rel/cov (and toolchain) configure trees from clobbering each other

| `env['abs_build_dir']`
| Destination for copied libs / completion markers under the sconscript variant
| Good `Command` targets beside Cuppa's `working/` layout

| `env['abs_final_dir']` and paths under `final/`
| `CMAKE_INSTALL_PREFIX` and/or `Install()` destinations
| Large third-party trees often install once under `final/`, then publish from that prefix

| `--parallel` / `env['job_count']`
| `cmake --build … --parallel N` via `env.CMakeBuild`
| With Cuppa `--parallel`, `CMakeBuild` passes `--parallel` with
  `env['job_count']` — the same affinity-aware count as SCons `-j` after the
  wrapper leaves cores free for the OS (e.g. 14 on a 16-core host). Never bare
  `--parallel` (that lets Ninja use all logical CPUs and oversubscribe the
  mask). Without Cuppa `--parallel`, it still passes `--parallel 1`. Override
  with `jobs=N` or omit with `jobs=False`. Nested oversubscribe is possible if
  several CMake builds run under SCons `-j` at once; use `jobs=` then.

| Generator (`-G Ninja`, …)
| Default: `Ninja` when `ninja` is on `PATH`; else omit `-G`. Pass
  `generator='…'` to force a generator, or `generator=False` to omit `-G`
| Shared by `cmake_configure_args` and `env.CMakeConfigure`

| `cuppa -c` / SCons clean
| Removes configure/build/install stamps **and** the CMake `-B` tree
| `CMakeConfigure` / `CMakeBuild` / `CMakeInstall` register `env.Clean` on the
  absolute `-B` path (including trees under location-dependency checkouts).
  Without that, clean only removes Cuppa copies/stamps and the next build
  looks like a no-op ninja rebuild.
|===

==== Pattern A — small library: configure, build, install, publish

Sketch: CMake produces a static archive; Cuppa copies or installs headers/libs into a package
tree under `final/`, then `PublishPackage`.

[source,python]
----
Import( 'env' )
import os
from cuppa.package_managers.gitlab import GitlabPackagePublisher

# Source tree already available (location dependency, extract step, …)
widget_src = env.BuildWith( 'widget_src' ).local_sub_path()

package_dir = os.path.join( env['abs_final_dir'], 'package' )
publisher = GitlabPackagePublisher(
    env,
    source_include_dir = os.path.join( package_dir, 'include' ),
    source_lib_dir     = os.path.join( package_dir, 'lib' ),
    registry           = 'https://gitlab.example/api/v4/projects/1',
    package            = 'widget',
    version            = '1.0.0',
)

cmake_build_dir = os.path.join( '_build', publisher.package_variant() )
configure = env.CMakeConfigure(
    widget_src,
    working_dir = widget_src,
    build_dir = cmake_build_dir,
    extra_defines = { 'WIDGET_BUILD_TESTS': False },
)
built = env.CMakeBuild(
    configure,
    build_dir = cmake_build_dir,
    working_dir = widget_src,
)

# Install or copy headers/libs into package_dir, then:
# env.PublishPackage( installed_nodes, publisher )
----

When `PublishPackage` is sourced from the include `Install` only, order the library
Install with `Requires(installed_include, installed_lib)` under `--parallel` — do not
use `Depends` for that edge (headers should not re-copy when only the `.a` changes).
See xref:methods/staging-files.adoc#package-staging-with-install[Staging files].

==== Pattern B — install prefix: CMake install, then publish

Sketch: CMake installs into a prefix under `final/`; `GitlabPackagePublisher` points
`source_include_dir` / `source_lib_dir` at that prefix.

[source,python]
----
Import( 'env' )
import os
from cuppa.package_managers.gitlab import GitlabPackagePublisher

# extraction_folder = … Dir under env['build_dir'] after download/extract …
install_prefix = env.Dir( os.path.join( env['final_dir'], 'installed' ) )
publisher = GitlabPackagePublisher(
    env,
    source_include_dir = os.path.join( str( install_prefix ), 'include' ),
    source_lib_dir     = os.path.join( str( install_prefix ), 'lib' ),
    registry           = 'https://gitlab.example/api/v4/projects/1',
    package            = 'widget',
    version            = '2.28.0',
)

cmake_out = os.path.join( '_build', publisher.package_variant() )
configure = env.CMakeConfigure(
    extraction_folder,
    working_dir = extraction_folder,
    source_dir = '.',
    build_dir = cmake_out,
    install_prefix = install_prefix,
    extra_defines = { 'BUILD_TESTING': False },
)
built = env.CMakeBuild(
    configure,
    build_dir = cmake_out,
    working_dir = extraction_folder,
)
installed = env.CMakeInstall(
    built,
    build_dir = cmake_out,
    working_dir = extraction_folder,
    target = install_prefix,
)
# env.PublishPackage( installed, publisher )
----

Shared libraries that ship host tools (for example a protobuf plugin) should embed
install RPATH for the packaged `bin/` → `lib/` layout, and a **build-tree** RPATH
when codegen runs during `CMakeBuild` (tools and `.so` files are often siblings
under `-B`, not `bin/` / `lib/`):

[source,python]
----
from cuppa.buildsys.cmake import cmake_install_rpath_defines

# Prefer env.CMakePrefixPathFor / env.PackageBin / env.PackageLib when prefixes
# come from BuildWith packages (order matters for find_package — more specific first).
# CMakeConfigure picks Ninja when ninja is on PATH (generator=False to omit -G).
protobuf_lib = env.PackageLib( 'protobuf' )
extra_defines = {
    'CMAKE_PREFIX_PATH': env.CMakePrefixPathFor( 'protobuf' ),
    'Protobuf_PROTOC_EXECUTABLE': env.PackageBin( 'protobuf', 'protoc' ),
    'BUILD_SHARED_LIBS': True,
}
extra_defines.update( cmake_install_rpath_defines(
    extra_install=[ protobuf_lib ],
    extra_build=[ protobuf_lib ],
) )
----

Raw absolute dirs still work with `cmake_prefix_path(dir_a, dir_b)` when you are
not resolving through `BuildWith`.

Consumers that `BuildWith` a GitLab package get `lib/` (and `bin/` when present)
prepended to the construction environment automatically (`LD_LIBRARY_PATH` /
`DYLD_LIBRARY_PATH` / `PATH`), matching Conan. That covers `--test` / `--run`
and tools invoked from a package prefix; it does **not** replace build-tree
RPATH inside the publisher's own unfinished CMake tree.

[NOTE]
====
`GitlabPackagePublisher.build_package` stages include/lib (and modules, when
present) under `final/<package>/<version>/`. Staging is created when missing
and **refreshed when the source tree is newer** than the staged copy (same-path
source and stage are left alone). `publisher.sources()` lists include and lib
when those paths sit **outside** `abs_final_dir`; trees under the final
directory are omitted to avoid SCons dependency cycles — wire the install or
library node through `env.PublishPackage(source, publisher)` instead. Packaging
a large install prefix still **duplicates** disk use on the first package; see
https://github.com/ja11sop/cuppa/issues/209[#209] for in-place packaging
follow-on.
====

[#conan-package-publishing]
== Conan 2 publishing (optional)

Cuppa can package libraries it has already built and export them into a Conan 2 cache (and optionally upload to a remote).
Conan does **not** drive the compile: Cuppa remains the orchestrator.

Use `ConanPackagePublisher` with the same `env.PublishPackage(...)` method used for GitLab:

[source,python]
----
Import('env')
from cuppa.package_managers.conan import ConanPackagePublisher

lib = env.BuildStaticLib('mylib', 'mylib.cpp')

publisher = ConanPackagePublisher(
    env,
    name = 'mylib',
    version = '1.2.3',
    user = 'myorg',          # optional → mylib/1.2.3@myorg/stable
    channel = 'stable',
    remote = 'artifactory',  # required only for upload
    remote_url = None,       # optional: conan remote add if missing
    source_include_dir = 'include',
    source_lib_dir = env['abs_final_dir'],
    shared = False,          # optional; None = infer from staged libs
    requires = None,         # optional; generated recipe only
    # conanfile = 'conanfile.py',  # optional hand-written recipe override
)

env.PublishPackage(lib, publisher)
----

`source_include_dir` / `source_lib_dir` (and `source_modules_dir` / `conanfile=`) use the same VariantDir path resolution as GitLab publishing above.

Without `--publish-package`, Cuppa stages headers/libs, writes a minimal `conanfile.py` (unless `conanfile=` is set), and runs `conan export-pkg` into the local Conan cache (settings match the active toolchain and variant via the same mapping as `conan_deps`).

With `--publish-package`, Cuppa also runs `conan upload` to `remote=` (and may `conan remote add` when `remote_url=` is set and the remote is missing).

=== Generated recipe options and requires

When Cuppa generates the recipe:

* `shared=True/False` sets Conan `options.shared` / `default_options` and `package_type`, and passes `-o shared=…` to `export-pkg`. When omitted, Cuppa infers static vs shared from staged library files.
* `requires=['fmt/12.1.0', …]` embeds those dependencies on the generated recipe. At `export-pkg` time they must already be in the local Conan cache if you are `--offline` (otherwise remotes may be used by Conan).

=== Hand-written `conanfile=`

Pass `conanfile='conanfile.py'` to copy a recipe you author into the stage instead of generating one.
Cuppa still stages `include/` and `lib/` and still supplies settings / name / version / user / channel on `export-pkg`.
Declare `requires`, `package()`, and `package_info()` in that recipe yourself.
`requires=` on the publisher is ignored when `conanfile=` is set (Cuppa logs a warning).

Hand-written recipes must still only **package** prebuilt artefacts — do not call Cuppa or compile from `build()`.
If you override `package()` and ship modules, copy staged `modules/` (Cuppa still stages BMIs into the recipe folder when `final/modules/module-map.json` exists).

=== Packaged modules (BMI)

When the producer builds with `--modules`, `BuildLib` installs BMIs under `final/modules/` with `module-map.json`.
`ConanPackagePublisher` copies that tree into the Conan package (same layout as GitLab generic packages).
`cuppa.conan_deps` consumers automatically call `load_packaged_modules` when a dependency’s package contains `modules/module-map.json` and the consumer build uses `--modules`.
BMI extensions remain toolchain-family specific (`.gcm` / `.pcm` / `.ifc`).

Optional ctor: `source_modules_dir=` to point at a modules tree explicitly; otherwise `\{source_lib_dir}/modules` is used when `module-map.json` is present.

[NOTE]
====
Reuse `--publish-package` for both GitLab and Conan publishers.
If several `PublishPackage` nodes appear in the graph, each publisher runs when the flag is set.
====

=== Authentication

Cuppa does not store Conan credentials.
Configure remotes and login before the Cuppa job (or in CI):

[cols="2,3"]
|===
| Mechanism | Notes

| `CONAN_LOGIN_USERNAME` / `CONAN_PASSWORD` | Common for non-interactive `conan remote login`
| GitLab CI | Often `ci_user` + `CI_JOB_TOKEN` against a GitLab Conan remote
| Pre-login | `conan remote login <name>` already done by the user or pipeline
|===

=== Offline behaviour

With `--offline`, `export-pkg` may still update the **local** Conan cache.
Upload is refused with a clear error (remotes are not contacted for publish).
Recipes with `requires` still need those packages already cached locally under `--offline`.

=== Consumer round-trip

A second Cuppa project can require the published reference through existing `cuppa.conan_deps` / `conan_dependency` (see xref:dependencies/conan.adoc#conan-2-consumer-optional[Conan packages]).
Settings fidelity matters: consume with the same toolchain, variant, arch, and {cpp} dialect that produced the package.

[WARNING]
====
GitLab's Conan 2 package registry may still be marked under development.
Treat it as one possible remote; Artifactory and other Conan 2 remotes are equally valid targets.
====

Components / multi-lib `cpp_info.components` remain deferred (tracked as https://github.com/ja11sop/cuppa/issues/125[#125]).
Conan packages may include Cuppa `modules/module-map.json` + BMIs for parity with GitLab generic packages; consumers load them automatically via `conan_deps` when `--modules` is enabled.
