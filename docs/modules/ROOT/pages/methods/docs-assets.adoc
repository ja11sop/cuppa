= Documentation and asset methods
:description: Templates, AsciiDoc, Markdown, SCSS, and redirect capture

Builders that turn documentation, templates, and assets into variant outputs under `final/`
(or related trees).

== Behaviour summary

[cols="1,3"]
|===
| Returns | Build nodes for generated artefacts
| Evaluation | Build action (configure registers a builder; the build runs it)
| Output paths | Caller target, or emitter-derived under `final/` mirroring the source tree
  (same-basename nested sources stay distinct — https://github.com/ja11sop/cuppa/issues/233[#233]).
  Jinja uses the same mirror idea. `CompileScss()` defaults match that layout too.
| Progress | Yes where emitters create action nodes (`NotifyProgress.add`)
|===

[#how-these-builders-work]
== How these builders work

Several Cuppa methods on this page (and `CreateVersion()`) follow the same shape:

. At **configure** time (while the `sconscript` runs), the method registers a named SCons
  `Builder` on the environment — action (and sometimes emitter) objects that know how to
  read inputs and write outputs.
. It then **invokes** that builder with `target` / `source`, which adds nodes to the build graph.
. At **build** time, SCons runs the action when the target is out of date.

That is why you pass destinations and sources up front (as with `Build()`), rather than expanding
or converting eagerly in Python during configure. The work participates in Depends, progress,
and rebuild-when-inputs-change like any other emitter.

== Methods at a glance

[cols="2,3"]
|===
| Method | Role

| `ExpandTemplateFile()`
| Python `str.format` expansion for small `.in` files

| `RenderJinjaTemplate()`
| Jinja2 rendering (`variables=` / `variables_file=`)

| `MarkdownToHtml()` / `AsciidocToHtml()`
| Doc conversion builders

| `CompileScss()`
| SCSS → CSS

| `RunAndRedirectToFile()`
| Capture subprocess stdout to a file
|===

== `ExpandTemplateFile()`

[source,python]
----
Import('env')
import os

out_txt = os.path.join(env['abs_final_dir'], 'expanded.txt')
env.ExpandTemplateFile(out_txt, 'data/template.txt.in', name='cuppa')
----

Extra keyword arguments become format fields (`\{name}` in the template).
The method registers an `ExpandTemplateFile` builder whose action reads the source and writes
`str.format(**kwargs)` into the target.

== `RenderJinjaTemplate()`

[source,python]
----
Import('env')
import os

env.RenderJinjaTemplate(
    [os.path.join(env['abs_final_dir'], 'rendered.txt')],
    ['data/template.j2'],
    variables={'name': 'cuppa'},
)
----

When you omit an explicit target list, the emitter derives destinations from the template names
(dropping `.j2` / `.jinja` suffixes) under `final/`, preserving a path offset from the project
base when possible.

== Doc and stylesheet converters

`MarkdownToHtml()`, `AsciidocToHtml()` (when you omit an explicit HTML target), and
`CompileScss()` (when you omit an explicit CSS target) place outputs under `final/` while
**mirroring** the source directory tree:

[source,python]
----
Import('env')

# doc/a/readme.md → …/final/doc/a/readme.html
# doc/b/readme.md → …/final/doc/b/readme.html
env.MarkdownToHtml(['doc/a/readme.md', 'doc/b/readme.md'])

# styles/a/app.scss → …/final/styles/a/app.css
env.CompileScss([], ['styles/a/app.scss', 'styles/b/app.scss'])
----

`RunAndRedirectToFile()` uses the same mirror rule for captured stdout files (default
extension `.out`). Pass an explicit target list when you need a different layout
(for example CSS next to the SCSS source, or a flat name under `final/`).

`AsciidocToHtml()`, `CompileScss()`, and `RunAndRedirectToFile()` follow the same builder
pattern described above; see the integration pages below for worked examples.
