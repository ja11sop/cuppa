= Test and run methods
:description: BuildTest, Test, Benchmark, and Run

Cuppa's test and run methods build (when needed) and execute programs under `--test`,
`--benchmark`, or `--run`. They share runners, working-directory rules, and Depends vocabulary
with the rest of the Methods surface.

== Behaviour summary

[cols="1,3"]
|===
| Returns | Nodes for built test/benchmark binaries; run helpers are side-effect oriented
| Evaluation | Build action / post-build runners
| Output paths | Binaries under `final/`; object paths follow `Compile()` mirroring under `working/`
| Progress | Yes for build emitters; runners participate through attached actions
|===

== Everyday test sconscript

A common Cuppa project pattern is: pull dependencies, build each test, copy selected outputs for
artefacts, then collate coverage and HTML reports.

[source,python]
----
Import('env')
import os

env.BuildWith('boost_package').use_libs(['boost_unit_test_framework'])
env.MergeFlags('-DBOOST_ASIO_NO_DEPRECATED')

artefacts_dir = os.path.join(env['abs_artefacts_root'], env['flat_build_base'])
coverage_dir = os.path.join(artefacts_dir, 'coverage')
test_dir = os.path.join(artefacts_dir, 'tests')

tests = []
coverage_files = []
for name in ['message', 'pipeline']:
    test = env.BuildTest(name, [name + '.cpp'], cov_exclude_dependencies=True)
    tests.append(test)
    env.CopyFiles(artefacts_dir, env.Filter(test, ['*.log', '*.json']))
    coverage_files.append(env.CollateCoverageFiles(test, destination=coverage_dir))

reports = env.GenerateHtmlTestReport(tests, link_style='gitlab')
env.CollateTestReportIndex(reports, destination=test_dir)
env.CollateCoverageIndex(coverage_files, destination=coverage_dir)
----

Notes:

* Prefer `env['abs_artefacts_root']` (and `env['artefacts_root']`) over hard-coded `#_artifacts/…`
  so custom `--artefacts-root` / configure settings are honoured. `artifacts_root` is the same path.
* `Filter()` here selects **outputs of the test node** (logs/JSON), not a `Glob()` of sources.
* `MergeFlags()` / `BuildWith()` are documented with
  xref:methods/flags-and-toolchain.adoc[Flags and toolchain] and
  xref:methods/dependencies-and-profiles.adoc[Dependencies and profiles].
* Coverage and HTML report methods: xref:methods/coverage.adoc[Coverage] (and the hub until that
  page is fully migrated).

For `cwd`, shell spawn, and `--use-shell`, see xref:methods/custom-commands.adoc[Custom commands].

== Testing with `BuildTest()`

`env.BuildTest(target, source, …)` builds a program and, when `--test` or `--force-test` is active, runs it through the configured runner.

[source,python]
----
Import('env')

env.BuildTest('unit_tests', ['tests.cpp'])
----

Run tests:

[source,sh]
----
cuppa -D --dbg --test --show-test-output
----

`--show-test-output` prints runner output instead of only the pass/fail summary.

Preferred parameters:

[cols="2,3"]
|===
| Parameter | Role

| `runner`
| Runner name (default from `cuppa.run(default_runner=…)`; often `process`, `boost`, or `patched_boost`)

| `expected`
| Expected outcome string (default `'passed'`)

| `expected_exit_code`
| Override the expected process exit code

| `build_depends_on`
| Extra Depends for the *build* (compile/link)

| `test_depends_on`
| Extra files/nodes associated with the *test run* (rebuild/re-run when they change)

| `working_dir`
| Directory in which to run the test

| `command`
| Override the command used to invoke the test binary (use this for CLI arguments)

| `cov_include_patterns` / `cov_exclude_patterns`
| Narrow coverage instrumentation when combined with `--cov`
|===

IMPORTANT: `test_depends_on` adds nodes to the test builder's source list so the build engine re-runs the test when those files change.
It is *not* passed as command-line arguments to the test program.
Use `command` (or a wrapper) when the program must receive paths on argv.
For broader Depends / Requires patterns, see xref:methods/depends.adoc[Depends].

Deprecated aliases (still accepted; prefer the names above):

[cols="2,3"]
|===
| Alias | Prefer instead

| `depends_on`
| `build_depends_on`

| `data`
| `test_depends_on`
|===

When both a preferred name and its alias are supplied, the lists are merged.

Toolchain-specific aliases such as `BuildBoostTest` appear when the toolchain advertises those runners.

== Testing with `Test()`

`env.Test(program, …)` attaches a test action to an *existing* binary (for example one produced by `Build()`).

[source,python]
----
Import('env')

prog = env.Build('unit_tests', ['tests.cpp'])
env.Test(prog, depends_on=['fixtures/input.txt'])
----

Preferred parameters:

[cols="2,3"]
|===
| Parameter | Role

| `depends_on`
| Extra files/nodes associated with the test run (rebuild/re-run when they change)

| `runner` / `expected` / `expected_exit_code` / `command` / `working_dir`
| Same meaning as on `BuildTest()`
|===

Deprecated aliases:

[cols="2,3"]
|===
| Alias | Prefer instead

| `data`
| `depends_on`
|===

When both `depends_on` and `data` are supplied, the lists are merged.
`depends_on` / `data` are *not* program argv — use `command` for that.

Toolchain-specific aliases such as `BoostTest` appear when the toolchain advertises those runners.

== Benchmarks with `BuildBenchmark()`

`env.BuildBenchmark(target, source, …)` builds a program and, when `--benchmark` or `--force-benchmark` is active, runs it through the configured runner.

Preferred parameters mirror `BuildTest()`, with explicit Depends names:

[cols="2,3"]
|===
| Parameter | Role

| `build_depends_on`
| Extra Depends for the *build* (compile/link)

| `benchmark_depends_on`
| Extra files/nodes associated with the *benchmark run*
|===

Deprecated aliases: `depends_on` → `build_depends_on`; `data` → `benchmark_depends_on`.

== Benchmarks with `Benchmark()`

`env.Benchmark(program, …)` attaches a benchmark action to an existing binary.

Preferred: `depends_on` for run-side Depends.
Deprecated alias: `data`.

[#generic-runs-with-run]
== Generic runs with `Run()`

`Run()` is Cuppa's **process runner** for binaries (and similar commands) under Cuppa actions
(`--run` / `--force-run`, and also alongside `--test` / `--benchmark`). It uses the shared runner
machinery (exit codes, `working_dir`, retries, optional `command` / `command_args`) and only
schedules work when the matching variant action is active.

[source,python]
----
Import('env')

env.Build('tool', ['tool.cpp'])
env.Run('tool', command_args=['--self-check'], depends_on=['config.json'])
----

Preferred: `depends_on` for run-side Depends; `command_args` for argv.
Deprecated alias: `data`.

=== `Run()` versus `Command()`

[cols="1,3"]
|===
| Prefer | When

| `Run()`
| You are executing a **built program** (or a fixed command line) as a Cuppa run/test/benchmark
  action, with runner semantics and flags such as `--run` / `--test`.

| `Command()`
| You need a **general build-graph action** — generate a file, wrap an external tool (CMake,
  code generators), write a marker, or any custom step that should rebuild when inputs change.
  `Command()` is the engine's swiss-army builder; it is not gated on `--run`.
|===

For `cwd`, spawn colouring, and `--use-shell` with `Command()`, see
xref:methods/custom-commands.adoc[Custom commands] (including
xref:methods/custom-commands.adoc#when-to-use-command[When to use Command()]).
