= Build methods
:description: env.Build, Compile, and BuildLib families

Cuppa's build methods produce variant-aware programs, object files, and libraries under the
active toolchain and `_build/` layout. They participate in progress reporting when they emit
action nodes (see xref:methods.adoc#progress-tracking-and-variant-scoping[Progress tracking]).

== Behaviour summary

[cols="1,3"]
|===
| Returns | SCons nodes (objects, programs, libraries)
| Evaluation | Build action (configure wires the graph; the build executes it)
| Output paths | Object outputs mirror the source tree under `working/` (https://github.com/ja11sop/cuppa/issues/213[#213]); linked binaries and libraries land under `final/`
| Progress | Yes — via `NotifyProgress` on emitted targets
|===

== Building a program with `Build`

`env.Build(target, source, …)` produces a variant-aware executable.
Cuppa compiles sources (via `Compile`), links a `Program`, and installs it under the variant's `final/` directory.

[source,python]
----
Import('env')

env.Build('hello', ['hello.cpp'])
----

`target` is the logical program name (cuppa may append a variant suffix depending on options).
`source` is a file, list of files, or nodes from `Compile` / `Module`.
Additional keyword arguments are forwarded to the underlying link step (for example `LIBS`, `LIBPATH`).

[WARNING]
====
Prefer `env.Build` over calling the engine's
https://scons.org/doc/production/HTML/scons-man.html[Program] builder directly.

A bare `env.Program(...)` is **not** Cuppa variant-aware: it does not follow Cuppa's
`_build/…/<toolchain>/<variant>/…/final/` layout, does not participate in Cuppa progress
reporting the same way, and does not pick up the multi-variant / multi-toolchain grid
(`--dbg` / `--rel` / `--cov`, `--toolchains=…`) the way `Build` does.

[source,python]
----
# Avoid in Cuppa projects:
# env.Program('hello', ['hello.cpp'])

# Prefer:
env.Build('hello', ['hello.cpp'])
----

The same idea appears in xref:quickstart.adoc[Quickstart] and xref:concepts.adoc[Concepts].
====

Build it:

[source,sh]
----
cuppa -D --dbg
----

`--dbg` selects the debug variant.
`-D` walks upward until cuppa finds the `sconstruct`, then builds the active `sconscript` files.

You can also pass library and dependency-related kwargs that cuppa understands when composing programs:

[source,python]
----
Import('env')

env.Build(
    'app',
    ['main.cpp', 'util.cpp'],
    LIBS=['m'],
    depends_on=[other_nodes],   # optional extra Depends edges
)
----

For packaging order after the binary exists (copy into a docker or artefacts tree), see
xref:methods/depends.adoc[`Requires`] with xref:methods/files-and-templates.adoc[`CopyFiles`].

== Compiling objects with `Compile`

`env.Compile(source, …)` (and `CompileStatic` / `CompileShared`) turns sources into object files without linking.
Use this when you need objects for custom link steps, or when you want to share objects across targets.

[source,python]
----
Import('env')

objs = env.Compile(['a.cpp', 'b.cpp'])
env.Build('app', objs)
----

Object paths mirror nested sources under `working/` so two `detail/foo.cpp` files in different
trees do not collide.

[WARNING]
====
Prefer `env.Compile` (or `CompileStatic` / `CompileShared`) over calling the engine's
https://scons.org/doc/production/HTML/scons-man.html[Object] builder directly.

A bare `env.Object(...)` is **not** Cuppa variant-aware: object outputs will not reliably land
under the variant `working/` tree with Cuppa's mirrored nested paths, and they will not share
the same toolchain / modules / progress behaviour as `Compile`.

[source,python]
----
# Avoid in Cuppa projects:
# objs = env.Object(['a.cpp', 'b.cpp'])

# Prefer:
objs = env.Compile(['a.cpp', 'b.cpp'])
----
====

When `env['modules']` is true (see xref:cxx-modules.adoc[{cpp} Modules]), `Compile` delegates to the modules compile path so interface units produce BMIs and consumers receive the right consume flags.

== Building libraries with `BuildLib`

`env.BuildLib`, `BuildStaticLib`, and `BuildSharedLib` build libraries into `final/`.

[source,python]
----
Import('env')

env.BuildStaticLib('mathlib', ['math.cpp'])
env.AppendUnique(LIBPATH=[env['abs_final_dir']])
env.Build('app', ['main.cpp'], LIBS=['mathlib'])
----

`AppendUnique` for `LIBPATH` / `LIBS` belongs with the rest of the flag story on
xref:methods/flags-and-toolchain.adoc[Flags and toolchain].

With `--cxx-modules` enabled, library builds that contain named module interfaces also install BMIs under `final/modules/` and write `module-map.json` for consumers (see xref:cxx-modules.adoc#packaged-modules[Packaged modules]).

NOTE: On Windows, MSVC *module* export is not the same as *DLL* export.
A shared library may need `__declspec(dllexport)` (or a module-definition file) before the linker produces an import `.lib`.
