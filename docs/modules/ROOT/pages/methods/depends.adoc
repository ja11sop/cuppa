= Depends, Requires, and Alias
:description: Ordering build and test actions with Depends, Requires, and Alias

Cuppa `Build`, `BuildTest`, and `CopyFiles` already wire many edges for you.
`Depends`, `Requires`, and `Alias` are the explicit graph tools you reach for when the default
edges are not enough — packaging order, database fixtures, “always regenerate this node”, or a
named group of targets.

Upstream reference (optional, unversioned):
https://scons.org/doc/production/HTML/scons-user/apd.html[SCons user guide — Functions and Environment Methods].

== Behaviour summary

[cols="1,3"]
|===
| Returns | Side effects on the DAG; `Alias` returns alias nodes
| Evaluation | Configure-time graph wiring
| Output paths | N/A
| Progress | No — by themselves they do not emit Cuppa progress nodes
|===

== `Depends` versus `Requires`

Both express “A needs B”, but Cuppa projects use them in different situations:

[cols="1,3"]
|===
| Call | Typical Cuppa use

| `Depends(target, dependency)`
| Ensure a *test or tool* rebuilds or re-runs when an input changes — SQL scripts, generated
  properties, scenario files, or another node's outputs. Closely related to
  `BuildTest(..., test_depends_on=…)` / `build_depends_on=…` on
  xref:methods/test-run.adoc[Test and run].

| `Requires(target, prerequisite)`
| Ensure a *packaging or install step* cannot finish before another product exists — for example
  copying a binary into a docker tree only after `Build` / `CreateVersion` has produced it under
  `final/`.
|===

Prefer the Cuppa kwargs (`test_depends_on`, `build_depends_on`) when you are attaching fixtures to
`BuildTest` / `Test`. Use `env.Depends` / `env.Requires` when you are ordering nodes that are not
covered by those kwargs (install copies, custom `Command` chains, wait/update helpers).

== Ordering packaging after a binary

Service sconscripts often build a program, copy config beside it under `final/`, then require that
a further copy into a docker or artefacts tree waits for the binary:

[source,python]
----
Import('env')
import os

objects = env.Compile('main.cpp')
version = env.CreateVersion('version.cpp', namespace='app')
program = env.Build('service', objects + version)

env.CopyFiles(env['final_dir'], ['config.json', 'logging.properties'])

docker_variant = '#_artifacts/' + env['flat_build_base'] + '/docker'
env.Requires(
    env.CopyFiles(docker_variant, [os.path.join(env['final_dir'], 'service')]),
    program,
)
----

Without `Requires`, the copy of `service` can race the link step under parallel builds.

== Test fixtures with `Depends`

When a test needs database scripts or a generated properties file:

[source,python]
----
Import('env')

test = env.BuildTest('db_roundtrip', ['db_roundtrip.cpp'])
# dbscripts / update_properties are nodes produced earlier in the sconscript
env.Depends(test, [dbscripts, update_properties])
----

If the files should participate in Cuppa's test-run Depends vocabulary instead, pass them as
`test_depends_on=` on `BuildTest` so the runner re-executes when they change — see
xref:methods/test-run.adoc[Test and run].

== `AlwaysBuild` (related)

Some projects mark a regenerate step with `AlwaysBuild` so properties or intermediate HTML rebuild
every run, then `Depends` tests on that node. Prefer that only when the node is cheap and must not
be considered up-to-date from timestamps alone.

== `Alias`

`Alias` names a group of targets for the command line (`cuppa -D alias_name`). Cuppa's own
progress and variant selection usually make aliases optional; use them when you want a stable
human-facing name for a bundle of install or doc nodes. Unused in many Cuppa fleets — keep it in
your toolbox for large trees.
