= Dependencies and build-profile methods
:description: BuildWith, Using, and BuildProfile

Cuppa dependencies and build-time profiles are applied on the environment before you call
`Build()` / `BuildTest()`. Deep tutorials for location, GitLab, and Conan packages live under
xref:dependencies.adoc[Dependencies].

== Behaviour summary

[cols="1,3",options="header"]
|===
| Axis | Detail

| Returns | `BuildWith()` returns the dependency instance (or a list); `Using()` returns a factory or
  `None`; `BuildProfile()` returns nothing useful (mutates `env` only)
| Evaluation | Configure-time
| Output paths | N/A (dependency trees under `--dependencies-root`)
| Progress | No (env / selection only)
|===

== Everyday pattern

[source,python]
----
Import('env')

env.BuildWith('boost')
env.BuildProfile('quad_float')   # example built-in profile
env.Build('app', ['main.cpp'])
----

After `BuildWith()`, projects often add defines with `MergeFlags()` — see
xref:methods/flags-and-toolchain.adoc[Flags and toolchain].

== `BuildWith()`

`BuildWith(dependencies)` applies one or more named dependency factories registered in
`cuppa.run()` (Boost, location packages, GitLab / Conan packages, custom plugins, …).

**Returns:** the dependency *instance* when you pass a single name, or a list when you pass several.
Keep the return value when you need APIs on that instance — library selection, local paths, version
strings — rather than discarding it:

[source,python]
----
Import('env')

boost = env.BuildWith('boost')
boost.use_libs(['filesystem', 'system'])

# Location / package dependencies often expose install roots:
widget = env.BuildWith('widget')
# e.g. widget.local_sub_path('include') → path under the downloaded / develop tree
headers = widget.local_sub_path('include')
env.AppendUnique(CPPPATH=[headers])
----

Where the dependency provides libraries, chain `.use_libs([...])` on the returned instance (Boost
source builds, `boost_package`, and other `package_dependency` flavours). See
xref:dependencies/builtins/boost.adoc[Boost] and xref:dependencies.adoc[Dependencies].

=== Untyped names and type selectors

When more than one supply chain can mean the same short name (for example a GitLab package
registered as `widget_lib_package` alongside an archive or built-in `widget_lib`), an
**untyped** `BuildWith('widget_lib')` resolves by precedence among **project-available**
candidates:

1. GitLab — registry key `[gitlab]widget_lib` when used, else the legacy `\{name}_package`
   form (`widget_lib_package`, and Boost’s familiar `boost_package`)
2. Short name / archive — `widget_lib`, or `[archive]widget_lib` / `[source]widget_lib` when
   registered that way

A candidate is project-available when it appears in `auto_enable_dependencies` /
`import_dependencies` (legacy: `default_dependencies` / `dependencies`), or
was already applied earlier in this sconscript via `BuildWith`. Always-on built-ins such as
archive `boost` stay in the factory registry for opt-in use; registry presence alone does not
beat a project-available GitLab package.

Explicit tokens bypass precedence: `[archive]widget_lib` / `[source]widget_lib`,
`[gitlab]widget_lib`, or the literal legacy key `widget_lib_package`. `[conan]…` is not selected
for untyped names yet.

`use_libs([...])` is the uniform way to link libraries from whichever flavour was resolved.
Built-ins such as xref:dependencies/builtins/quince.adoc[Quince] only ask for `boost` and call
`use_libs` — they do not branch on package vs archive.

Passing several names returns a list (order matches the call):

[source,python]
----
Import('env')

deps = env.BuildWith(['boost', 'widget'])
----

== `Using()`

`Using(name)` looks up a dependency **factory** by name without applying it. Returns the factory,
or `None` if that name is not registered in `cuppa.run()`.

Useful for existence checks or custom wiring before `BuildWith()`:

[source,python]
----
Import('env')

boost_factory = env.Using('boost')
if boost_factory is None:
    raise Exception('boost dependency is not registered in cuppa.run()')
env.BuildWith('boost').use_libs(['filesystem'])
----

`Using()` does not mutate include paths or link libraries — call `BuildWith()` to apply the
dependency to `env`.

== `BuildProfile()`

`BuildProfile(profiles)` applies one or more named **build profiles** registered with Cuppa
(lightweight env tweaks such as floating-point modes). This is **not** the same as {cpp} Profiles
(`--cxx-profiles` / `std::init`) — see xref:cxx-profiles.adoc[{cpp} Profiles].

**Returns:** nothing used by callers (the method mutates `env` / toolchain flags in place). Discard
the call result:

[source,python]
----
Import('env')

env.BuildProfile('quad_float')
env.BuildProfile(['profile_a', 'profile_b'])
----

Default profiles from `cuppa.run(auto_enable_profiles=…)` (legacy: `default_profiles`) are
applied automatically before each sconscript runs; call `BuildProfile()` in the sconscript for
extras.
