= Location dependencies
:description: location_dependency — paths, archives, VCS URLs, folder naming, and develop

Create a lightweight dependency with `cuppa.location_dependency()` (also aliased as `header_library_dependency`):

[source,python]
----
import cuppa

MyHeaders = cuppa.location_dependency(
    'my_headers',
    location = 'https://example.com/my_headers/archive/main.zip',
    include = 'include',
)

cuppa.run(
    import_dependencies = [ MyHeaders ],
    auto_enable_dependencies = [ MyHeaders ],
)
----

`include` adds user include paths; `sys_include` adds system include paths (`SYSINCPATH`).
Either may be a string or a list. If you omit both, cuppa uses the retrieved tree root as a
system include.

Locations may be filesystem paths, archive URLs, or VCS URLs (for example `git+https://<...>@branch`).
Cuppa keeps checkouts and extracted archives under `--dependencies-root` and the downloaded
archives themselves under `--downloads-root`, both shared between projects by default. See
xref:build-layout.adoc[Build layout] for the defaults and for how to move them.

VCS folders use a canonical `stem@<branch>` spelling once the branch is known — including the
default branch (`--location-default-branch`, usually `master`). An older unqualified stem is
kept if it is the only copy on disk (cuppa does not move or delete it). When both exist, resolve
uses the canonical folder. Dependency-management commands
(`--list-dependencies`, `--remove-dependencies`, `--purge-dependencies`, wipe / force-wipe)
record that pair at **debug** log level and surface it in their trees: remove-coloured
`@master (unqualified)` (or `@main (unqualified)`, <...>) leaves and a dry-run
`--force-wipe-dependencies=` hint using the `name/@` shorthand (bare `@` means the unqualified
stem, not `@master`) after the report footer. Ordinary builds prefer the canonical folder
quietly — they do not print Location warnings or wipe hints for this case.
`--list-dependencies` merges inventory tokens with any Location notices unless
`--list-scope=compact` (compact hides unused siblings, so notices and wipe candidates for
those leaves are omitted). The label uses
`--location-default-branch` (default `master`); it does
not inspect HEAD inside the unqualified clone. Drop `-n` after confirming. Under `--offline`,
candidates whose inventory `used_by` names another project are omitted from that hint.
When you force-wipe such a stem and inventory still records another project's use, cuppa
warns but explains that proceeding is safe when the canonical `stem@<default>` folder is also
present. See xref:dependencies/managing/removing.adoc#force-wipe-dependencies[Force-wiping named leaves].

With `--develop`, location dependencies that define a develop path use the local tree instead of fetching.
Check those copies with xref:dependencies/managing/develop.adoc#checking-your-develop-copies[`--list-develop`].

When that tree is also a Cuppa project, `--stage-develop` nest-builds it.
If the nested (or previously built) tree leaves a package-shaped stage at
`_build/.../final/<name>/<version>/{include,lib}`, tip **consumes that prefix**
(and optional `modules/` BMIs) instead of compiling the checkout as sources.
Produce the stage with `env.StageLocationDevelop` in the location project; see
xref:dependencies/managing/develop.adoc#location-tip-consume-stage-prefix[Working with develop copies]
for producer/tip listings and the common shapes (nest+link, discover-only,
header-only path-swap, clean then missing stage, one declaration instead of dual).
Without a usable stage, tip keeps classic path-swap includes.

Relative locations ending in `@` participate in `--location-match-*` branch/tag behaviour (see
xref:cli/dependencies-and-develop.adoc[Dependencies and develop]).

Location factories can declare `storage_paths()` so listing and removal see the owned tree without
retrieving it. See xref:dependencies/authoring/extending.adoc[Writing your own dependencies].
