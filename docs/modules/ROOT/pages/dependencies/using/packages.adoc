= Package dependencies
:description: package_dependency overview — consume registry archives

`cuppa.package_dependency()` downloads a prebuilt archive from a package registry and lays it
out under `--dependencies-root` per toolchain / variant / architecture.

Today the supported `package_manager` is GitLab generic packages — see
xref:dependencies/using/gitlab.adoc[GitLab packages] for authentication, lookup overrides,
`version="latest"`, and the Boost package extension. Publishing Cuppa-built libraries is a
different workflow: xref:dependencies/publishing/packages.adoc[Publishing packages].

[source,python]
----
import cuppa

MyPkg = cuppa.package_dependency(
    'mypkg',
    package_manager = 'gitlab',
    registry = 'https://gitlab.example.com/api/v4/projects/123',
    package = 'mypkg',
    version = '1.2.3',
)

cuppa.run(
    import_dependencies = [ MyPkg ],
    # Import above; auto-BuildWith in every sconscript (same factory or MyPkg.name()):
    auto_enable_dependencies = [ MyPkg ],
)
----

Pin `version` to a concrete string, or use `version = 'latest'` (or omit / `None`) to resolve
the newest version **published in that registry** for the package name at configure time.
Offline reuse of that pin is documented under
xref:dependencies/using/gitlab.adoc#version-latest[Registry latest].
A missing package or an unresolved `latest` fails during configure, before compile.

On the publish side, the same floating tokens may appear on
``GitlabPackagePublisher``: the publisher-tree seed can keep ``"latest"`` while
the staged archive and registry upload always record a concrete pin — see
xref:dependencies/publishing/packages.adoc#publish-version-latest[Publisher version latest].

== Develop vs package downloads

`--develop` affects *location* develop paths and package develop flags where defined.
It does *not* invent a local substitute for a missing registry archive: the matching package
must exist in the registry or already be cached under the dependencies and downloads roots.

A package's `develop` path names the package tree to build against — the directory `include/`
and `lib/` hang off — and replaces the download and extract steps entirely when `--develop` is
active. Set it on the dependency, or per run with `--<name>-<manager>-develop=PATH`:

[source,python]
----
widget = cuppa.package_dependency(
        'widget',
        registry = REGISTRY,
        version  = '1.2',
        develop  = '../../widget',
)
----

A relative path is anchored to the directory holding your `sconstruct`, not to the directory you
ran cuppa from, so it means the same thing from anywhere in the project and matches the path
xref:dependencies/managing.adoc[`--list-develop`] reports. `~` is expanded, and an absolute path
is used as given.

== Saying where a package comes from

`package_source` names the repository a package is published from. A package dependency names a
registry rather than a repository, so without it cuppa knows where to fetch the built artefact
but not where the sources live:

[source,python]
----
widget = cuppa.package_dependency(
        'widget',
        registry       = REGISTRY,
        version        = '1.2',
        develop        = '../../widget',
        package_source = 'git@gitlab.example:packages/widget@develop',
)
----

It is metadata: nothing about consuming the package reads it. Two workflows do.
xref:dependencies/managing/develop.adoc#package-dependencies[`--clone-develop`] uses it to create
the develop working copy above, and xref:dependencies/publishing/packages.adoc#build-and-publish-dependencies[cascade]
uses it to find the project that publishes the package. An optional `@branch` pin may be given,
and `--<name>-<manager>-package-source=` overrides the declaration for one run.

**Precedence** (shared by `--clone-develop` and cascade): CLI override →
`package_dependency(..., package_source=…)` (or `boost_package.define(..., package_source=…)`)
→ matching edge in the tip's `cuppa-publish.json`. Publisher-edge
`package_source` on a traveling / `dependencies=` entry still wins when present
on that edge.

A project that publishes already declares the same field on its `PublishPackage` dependency
edges, and a publisher build stages those in `cuppa-publish.json`, so declaring it here is for
consumers that do not publish (and so cascade need not require the field twice).
