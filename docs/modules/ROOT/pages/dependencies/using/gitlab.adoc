= GitLab packages
:description: Consume GitLab generic registry packages, including version latest and boost_package

Cuppa consumes GitLab **generic** package archives through `cuppa.package_dependency()` with
`package_manager = 'gitlab'`. See xref:dependencies/using/packages.adoc[Package dependencies] for the
factory overview.

Package archive downloads use the shared transfer-progress reporter (percent, bar, rate, ETA)
over HTTPS with registry auth headers — `wget` is not required on `PATH` for the fetch.

The `registry` argument is the GitLab project Packages API root
(`https://gitlab.example.com/api/v4/projects/<id-or-path>`). Cuppa appends
`/packages/generic/...` for archive URLs. You may also pass a URL that already ends with
`/packages/generic`; listing for `version="latest"` normalises either form.

== Authentication

[cols="3,7"]
|===
| Mechanism | Notes

| `GITLAB_REGISTRY_TOKEN` | Personal or project access token with package read (and write if publishing)
| `CI_JOB_TOKEN` | Used automatically in GitLab CI when available
| `--<name>-gitlab-custom-token` | Point at another env var / token setting for that package
|===

The `cuppa` launcher redacts env values whose names contain `TOKEN` in logged output.

To **publish** a Cuppa-built library to the same registry, see
xref:dependencies/publishing/packages.adoc[Publishing packages].
Archive stems include `toolchain.package_name()`, so `--toolchain-identity=major` looks for
`gcc15_<...>` rather than `gcc153_<...>` unless you keep `full`. If the preferred stem is missing
(`404`), Cuppa tries the other identity (full vs major) and the other OS encoding
(include vs omit) before failing, and logs every stem it attempted. Disable that with
`--package-gitlab-identity-fallback=off`. Publish still emits one stem.

Publish with `--package-gitlab-os-identity=omit` writes `\{package\}_\{tool_variant\}` (no OS
segment). Consume prefers that shape when the same flag is set, and with fallback on also
tries the include form after a `404`. An explicit `--package-gitlab-os-override` always
looks up the include shape for that OS id.

[#consume-overrides]
== Lookup overrides

Host identity does not have to match the archive you fetch. OS and toolchain overrides change
**lookup** only. `--package-gitlab-os-identity` also changes what `env.PublishPackage` writes.

[cols="3,7"]
|===
| Option | Role

| `--package-gitlab-os-override=<id>` | Force the OS segment for every GitLab package
| `--package-gitlab-os-override-<name>=<id>` | Force the OS segment for one named dependency (`debian` while the host is `ubuntu`)
| `--package-gitlab-toolchain-override-<name>=<token>` | Force the toolchain token for one named dependency (`gcc152` or `gcc15`)
| `--package-gitlab-identity-fallback=on\|off` | After a `404`, try the other toolchain identity and the other OS encoding (include vs omit). Default `on`
| `--package-gitlab-os-identity=include\|omit` | Preferred stem shape: include OS id (default) or omit it
|===

Resolution order is: explicit per-package OS and toolchain overrides (then the project-wide OS
override), then the current toolchain identity plus the preferred OS encoding (host OS, or omit),
then the alternate full vs major token with that encoding, then the other OS encoding. Success is
an ABI bet the project owns — Cuppa does not treat Debian archives as equivalent to Ubuntu ones
unless you ask for that stem.

xref:cli/dependencies-and-develop.adoc[Dependencies and develop] lists the flags.
xref:toolchains/overview.adoc#toolchain-identity[Build and package identity] covers layout
identity. Publishing with omit is documented in xref:dependencies/publishing/packages.adoc[Publishing packages].

[#version-latest]
== Registry `latest`

`version = 'latest'` (or `None` / omitted where the factory allows) means the newest version
**available in that GitLab registry** for the package name — not the newest upstream software
release.

Cuppa lists versions with the GitLab Packages API
(`GET <...>/packages?package_type=generic&package_name=<...>`), picks the highest version string, then
downloads with the usual stem / override / identity-fallback rules. Auth uses the same
`GITLAB_REGISTRY_TOKEN` / `CI_JOB_TOKEN` (or custom token) as archive download. Listing needs a
token that can call the Packages API (a deploy-token that only fetches generic files may be
insufficient).

The same floating tokens appear on the **publish** side
(``GitlabPackagePublisher(version="latest")``): the publisher-tree seed may keep
``"latest"`` while the staged archive and registry upload always record a concrete
pin. Resolve order prefers an active ``BuildWith``, then (for package ``boost``)
upstream Boost latest, then this same registry-latest helper. That is a general
facility for any GitLab package publisher — see
xref:dependencies/publishing/gitlab.adoc#publish-version-latest[Publisher version latest].

[source,python]
----
Widget = cuppa.package_dependency(
    'widget',
    registry = 'https://gitlab.example.com/api/v4/projects/123',
    package  = 'widget',
    version  = 'latest',
)
----

=== Remembered version and `--offline`

Online, `"latest"` means “newest in the registry **now**.” Offline, Cuppa cannot re-query the
registry, so it needs a remembered concrete version to honour the same dependency declaration.

After a successful registry list/select, Cuppa stores that **version string** (for example
`1.10`) under a `gitlab_package_latest_*` key. The suffix is a short hash of
`registry|package` so keys stay unique; it is **not** a content hash of the archive.

Where the key is written follows the same downloads-root scoping as source Boost’s
`boost_latest_version`:

* If `--downloads-root` is under the project tree → project `configure.conf`
* Otherwise (the default shared `~/.cuppa/downloads`) → `~/.cuppaconfig`

Shared download cache ⇒ shared “what latest meant” memory; project-local downloads ⇒
project-local memory. That is intentional: offline replay of `"latest"` should match how
archives are shared on the machine.

With `--offline`:

* If a remembered version exists for that registry+package → pin to it and continue into the
  normal package fetch (archive under **this** run’s `--downloads-root`, extract under
  `--dependencies-root`).
* If none is remembered → configure fails clearly (cannot honour `"latest"` offline).
* If a version is remembered but the archive is missing from this downloads root → configure
  fails later with the usual offline missing-archive error. Cuppa does **not** silently fall
  back to an older on-disk version; that would change the pin.

Online, Cuppa still queries the registry. If that check cannot run — the host is
unreachable (DNS, connection), or the response is HTTP 401, 403, or 5xx — **and** a
remembered version exists **and** that version's extract is on disk, configure **warns**
once and reuses the pin. The pin is not updated. The warning names the dependency, the
error (`HTTP 401 - unauthorized`, or that the registry was unreachable), and the
remembered version. `--offline` is a different mode: it does not try the network at all.
Under `--terse-output` that same decision is the durable `[version]` child
`· latest · unverified · using remembered 1.92`. The mid-dots stay muted.
`unverified` uses the warning background and the terminal's own foreground.
`using remembered 1.92` is warning-coloured text.
The logger warning is not repeated. A live list prints `· latest · retrieved as 1.92`. No pin, an empty extract,
HTTP 404, an empty
registry, or a check that cannot run with nothing to reuse is
`· latest · error: retrieve failed, no version available` and still stops configure.
Publishing `version="latest"` does not reuse the pin; it still needs a live registry list.

So the remembered value is “what registry latest resolved to,” not “proof the archive is on
disk.”

[#package-download-freshness]
== Package download freshness

Cache keys are still **package + version + stem**. Online configure adds a
cheap check before reusing a cached archive: Cuppa `HEAD`s the generic package
file URL (same auth as download) and compares the response to a small sidecar
next to the archive. GitLab's `X-Checksum-Sha256` is preferred; otherwise
`Last-Modified` and `Content-Length` are used.

* Match → reuse the archive and extract (no durable terse line for the check).
* Different identity, or no sidecar yet → clear that archive and extract, then
  download again (existing `[collect]` / `[extract]` terse children).
* Check cannot run (network / auth / missing headers) → **warn once** and keep
  the cached extract. Under `--terse-output` that is a `[collect]` child with a
  warning remark (`unverified · using cached archive`).
* `--offline` → no `HEAD` (existence-only reuse).
* xref:cli/inspect-and-maintain.adoc#refresh-downloads[`--refresh-downloads`]
  still force-clears and re-fetches.

This applies to **every** version string, including floating tags such as
`develop` and same-version semver overwrites. It is not limited to the name
`develop`.

[#boost-package]
== Boost package

`cuppa.packages.boost_package.define(...)` builds a `boost_package` dependency backed by the
registry. It is the worked example of a package **extension** (`use_libs`, Boost.Test runner
hooks). Aside from Boost-specific `patched` (default `True`), keyword arguments are forwarded
to `package_dependency` — including `registry`, `version`, `variant`, `develop`, and
`package_source` — so new common factory options do not require a parallel `define` update.
`package` is always `boost`. Consuming and publishing workflows are documented below; see also
xref:dependencies/using/builtins/boost.adoc[Boost (source)] for version resolution when building from
source.

Unpinned `version` (`None` or `'latest'`) uses **registry** latest, same as a generic
`package_dependency`. To pin the upstream Boost release from boost.org and then fetch that
version from the registry, pass `version = cuppa.packages.boost_package.latest_release()`
explicitly (accept a configure `404` if the registry has not published that release).

=== Consuming in a project

Declare the package in the ``sconstruct`` with ``import_dependencies`` and
``auto_enable_dependencies`` so every sconscript gets ``BuildWith`` automatically.
Boost.Test runners then take version and patched-test flags from this package and do not
extract source Boost. Set ``GITLAB_REGISTRY_TOKEN`` (or rely on ``CI_JOB_TOKEN`` in GitLab CI)
for registry access.

[source,python]
----
import cuppa

# WidgetPrj = cuppa.location_dependency( 'widget', include='include', location='#' )

BoostPackage = cuppa.packages.boost_package.define(
    registry = 'https://gitlab.example.com/api/v4/projects/dependencies%2Fregistry',
    # version omitted → registry latest; or version = '1.91'
    # or version = cuppa.packages.boost_package.latest_release()  # upstream then registry
    # package_source = 'git@gitlab.example:packages/boost@develop',  # optional; clone-develop / cascade
    # develop = '/home/user/coding/boost',  # optional; same as package_dependency
)

cuppa.run(
    import_dependencies = [
        BoostPackage,
    ],
    auto_enable_dependencies = [
        BoostPackage,
    ],
    default_runner = 'boost',
)
----

In a sconscript, link against selected libraries with the same ``use_libs`` shape as source Boost:

[source,python]
----
Import('env')

env.BuildWith('boost_package').use_libs([
    'log',
    'log_setup',
    'program_options',
    'system',
    'unit_test_framework',
])
----

`BuildWith` also prepends the package ``lib/`` directory (and ``bin/`` when it
exists) to the construction environment so shared libraries resolve for host
tools and ``--test`` / ``--run`` without hand-rolled ``LD_LIBRARY_PATH``.

To **publish** Boost into the registry from the source ``boost`` dependency, see
xref:dependencies/publishing/gitlab.adoc#publishing-boost-from-source[Publishing Boost from source].

=== Minimal define (reference)

[source,python]
----
import cuppa

BoostPkg = cuppa.packages.boost_package.define(
    registry = 'https://gitlab.example.com/api/v4/projects/123',
    version = '1.85',
)

cuppa.run(
    import_dependencies = [BoostPkg],
    auto_enable_dependencies = [BoostPkg],
)
----

When ``version`` is omitted, the package helper selects a registry version according to its own
rules; pinning ``version=`` in ``define`` is separate from source Boost's ``--boost-version=``.

Use ``package.use_libs([...])`` helpers where provided to link the correct libraries for
the active toolchain/variant. ``use_libs`` resolves **static or shared** artefacts under
the package ``lib/`` directory (prefer static when both exist, unless the package manifest
sets ``link``). Prefer this over hand-rolled ``LIBPATH`` / ``SHAREDLIBS``. The built-in
source ``boost`` dependency accepts the same call shape —
``env.BuildWith('boost').use_libs([...])`` — so switching supply chains does not require
rewriting sconscripts beyond the dependency name.

Small packages may also declare ``default_use_libs`` in ``cuppa-publish.json`` (via
``GitlabPackagePublisher(..., default_use_libs=[...])``). Auto-enable /
``auto_enable_dependencies`` (legacy: ``default_dependencies``) then link that set
without an explicit ``use_libs`` call. An explicit ``use_libs([...])`` **replaces**
the default contribution for that package; ``use_libs([])`` clears it (headers and
runtime ENV only). Fat packages such as ``google_cloud_cpp`` should publish an empty
default (or omit a heuristic match) so auto-enable never links every library under
``lib/``.

When ``default_use_libs`` is omitted, Cuppa may apply a narrow heuristic: a single
linkable stem, or one stem matching the package slug / BuildWith name; otherwise it links
nothing. Prefer publishing explicit metadata.

==== Public compile defines

The package carries one list of public compile defines. ``BuildWith`` applies
that list as ``CPPDEFINES`` when it adds the package headers. ``use_libs``
does not add or remove them, including ``use_libs([])``. A consumer can
change ``CPPDEFINES`` afterwards.

Write the list on the publisher when the package is not built with CMake:

[source,python]
----
public_defines = [ 'WIDGET_HAS_TLS=1' ]
----

When the package is installed with CMake, do not copy the defines into the
sconscript. Pass the marker and publish asks CMake, after install, for each
imported target's ``INTERFACE_COMPILE_DEFINITIONS`` (including defines that
arrive through ``INTERFACE_LINK_LIBRARIES``):

[source,python]
----
from cuppa.buildsys.cmake import cmake_public_defines

publisher = GitlabPackagePublisher(
    env,
    # ...
    public_defines = cmake_public_defines(),
)
----

``[]`` publishes none. Omitting the argument publishes none; it does not
guess. The answer is stored as a list:

[source,json]
----
"public_defines": ["USE_OS_TZDB=1", "ONLY_C_LOCALE=0", "HAS_STRING_VIEW=1"]
----

==== Pkg-config (defines and cflags)

Pkg-config remains valid when a package ships a usable ``.pc``. It is not
how ``public_defines`` is filled.
When a package needs other cflags alongside linking, publish the directory
that holds the ``.pc`` files. The path is relative to the package root, and
it is written even when that path is ``lib/pkgconfig``. A missing key means
do not run pkg-config.

[source,python]
----
publisher = GitlabPackagePublisher(
    env,
    # ...
    pkg_config_dir = 'lib/pkgconfig',
)
----

[source,json]
----
"pkg_config_dir": "lib/pkgconfig"
----

A consumer ``pkg_config_dir`` replaces the published directory. ``""`` turns
pkg-config off for that dependency. With a directory in force, ``use_libs`` /
defaults run ``pkg-config --libs --cflags`` through SCons ``ParseConfig`` for
the requested stems (including any ``-D`` entries in the ``.pc``). Without
one, Cuppa links resolved static/shared artefacts under ``lib/`` and adds
includes only.

``CMakeInstall`` rewrites ``*.pc`` files under the install prefix so
``prefix=${pcfiledir}/...`` and paths under that prefix use ``${prefix}``.
The extract can move without those files still pointing at the build
machine. A prefix outside the package tree is left alone. A file that
already uses ``${pcfiledir}`` is left alone. A tree that was not installed
by CMake can call ``env.RelocatePkgConfig(source, prefix=...)``.
Consume does not rewrite: a published ``.pc`` that still has an absolute
prefix keeps that path. Use ``use_libs`` / ``default_use_libs`` when you
only need stems and headers.

To link every static or shared library present under a GitLab package's ``lib/`` directory,
call ``use_all_libs()`` (do not pass an empty ``use_libs([])`` when you mean “all” — empty
clears the package's link contribution):

[source,python]
----
env.BuildWith('widget').use_all_libs()
----

Large multi-lib packages may publish **named library groups** in ``cuppa-publish.json``
(via ``GitlabPackagePublisher(..., lib_groups={...})``). Tokens in consumer
``use_libs([...])`` and in traveling-manifest edge ``use_libs`` may be **leaf stems
and/or group names**; groups expand (nested groups recurse) before linking. Group
names take precedence when a token matches both a group and a leaf stem; the group
body may still include that same-named stem as a concrete member.

Two authoring styles:

* **Opaque / Boost-like** — the group *is* the API (may shadow a leaf name) so
  consumers always get the full, ordered set.
* **Convenience** — group names avoid leaf stems (e.g. ``kms libs``,
  ``cloud storage``) so cherry-picked leaves stay available.

[source,python]
----
env.BuildWith('mega_package').use_libs([
    'kms libs',         # convenience group → several concrete libs
    'cloud storage',    # named feature group (leaf ``storage`` still usable)
    'standalone_leaf',  # ordinary stem
])

env.BuildWith('mega_package').show_libs_for('cloud storage')
env.BuildWith('mega_package').show_all_libs()
----

``show_libs_for(token)`` returns the concrete stems that token expands to (and logs
them at configure time). ``show_all_libs()`` returns a catalogue of each group →
expanded leaves plus any ungrouped linkable stems under ``lib/``.

[#transitive-package-dependencies]
=== Transitive package dependencies

A published GitLab archive includes ``cuppa-publish.json`` next to ``include/`` and
``lib/`` (identity, dependency edges including ``package_source``, optional
``default_use_libs`` / ``link`` / ``lib_groups`` / ``library_prefix`` /
``pkg_config_dir`` / ``public_defines``). When you ``BuildWith`` package **A**, Cuppa reads that
file (if present) and ``BuildWith``s each listed dependency **B** so B's headers (and
packaged modules) are on the include path. Legacy extracts that only ship
``cuppa-dependency.json`` are still read as a fallback. **B**'s ``default_use_libs`` are
**not** applied for a transitive include-only ``BuildWith`` — only for a primary /
auto-enabled dependency. When you later link A with
``A.use_libs(...)`` or ``A.use_all_libs()``, Cuppa also applies each edge's ``use_libs``
against B (expanding B's groups when declared).

Publish the edges with ``GitlabPackagePublisher(..., dependencies=[...])``. Optional
package-level fields on the same publisher / manifest:

* ``default_use_libs`` — stems (or group tokens) linked on primary BuildWith / auto-enable
* ``link`` — ``prefer_static`` (default), ``prefer_shared``, ``static``, or ``shared``
* ``lib_groups`` — mapping of group name → concrete library stems (see above)
* ``library_prefix`` — prepended to ``use_libs`` stems and ``.pc`` names (``boost_``). A consumer ``library_prefix`` replaces it; ``""`` clears it
* ``pkg_config_dir`` — directory of ``.pc`` files, relative to the package root (``lib/pkgconfig``, ``share/pkgconfig``). Written whenever the package uses pkg-config. A missing key does not mean ``lib/pkgconfig``. A consumer ``pkg_config_dir`` replaces it; ``""`` turns pkg-config off

Publishers always stage ``cuppa-publish.json`` (at least ``package`` / ``version``).
Omit ``dependencies`` / ``default_use_libs`` / ``link`` when the package is standalone
with no defaults — those keys are simply absent from the document.

[source,python]
----
publisher = GitlabPackagePublisher(
    env,
    source_include_dir = '#/include',
    source_lib_dir     = env['abs_final_dir'],
    registry           = 'https://gitlab.example/api/v4/projects/1',
    package            = 'widget',
    version            = '1.0.0',
    default_use_libs   = [ 'widget' ],
    dependencies = [
        'fmt',
        {
            'name': 'boost_package',
            'package': 'boost',
            'use_libs': ['system'],
        },
    ],
)
----

* ``name`` — Cuppa ``BuildWith`` / registry name. A bare string entry is treated as ``name``.
* ``package`` — GitLab Packages slug when it differs from the hyphenated form of ``name``.
  If only ``name`` is given, Cuppa sets ``package`` to ``name`` with ``_`` replaced by ``-``
  (``opentelemetry_cpp`` → ``opentelemetry-cpp``). If only ``package`` is given, ``name``
  is derived the other way. Pass both when the slug is not that transform.
* ``version`` — exact pin (``1.28.0`` / ``==1.28.0``), minimum (``>=1.28.0``), or
  ``latest``. Optional when the edge ``name`` is already applied via ``BuildWith`` /
  auto-enable; Cuppa fills it from that package at publish time. Explicit pins always
  win. Publish-time ``latest`` on a dependency still becomes a **concrete** pin in the
  traveling artefact (same as publisher seed latest); a declared ``>=`` minimum may be
  written through as a soft bound. See xref:#version-ranges[Version ranges].
* ``registry`` — omit or ``""`` means ``"same"`` (A's registry URL).
* ``use_libs`` — optional; applied against B when A is linked.

Consumers still only need to import / auto-enable **A**. Transitive names are not added to
``auto_enable_dependencies``. Incompatible version bounds on the same name (exact mismatch,
or an exact pin outside another parent's minimum) raise ``StopError``. Compatible minima
are intersected (the tighter floor wins). Cycles in the dependency graph also fail clearly.

[#version-ranges]
=== Version ranges (exact / minimum)

GitLab package edges accept a **small** bound grammar — not pip / PEP 440:

[cols="3,7"]
|===
| Spelling | Meaning

| ``1.28.0`` or ``==1.28.0``
| Exact pin (unchanged)

| ``>=1.28.0``
| Minimum inclusive; resolve to one concrete version

| ``latest``
| Named float → concrete via registry list + remember
|===

Unsupported spellings (``~=``, ``^``, comma lists, exclusions, wildcards) fail clearly at
publish normalise or consume apply. Diamond parents **intersect** bounds; empty
intersection names both parents. Selection prefers a satisfying on-disk / remembered
version; ``--refresh-downloads`` may move to a higher satisfying registry version.
If that refresh cannot run (unreachable host, HTTP 401/403/5xx) and a local version
already satisfies the bound, configure warns and keeps it, the same way an unverified
``latest`` reuses its pin. HTTP 404 on the refresh is a hard stop.
``--list-dependencies`` shows soft edges as ``bound → concrete`` when a resolved extract
is known.

Design: https://github.com/ja11sop/cuppa/blob/master/design/archive/gitlab-package-version-ranges.md[`gitlab-package-version-ranges`].

``--list-dependencies`` treats the traveling-manifest **closure** of tip-selected GitLab
extracts as referenced: under each tip version a ``requires`` group nests on-disk package
trees (sizes and toolchains). Nested packages keep label-style ``requires`` edges. When nothing
is tip-selected, edges still appear as labels under each walked version (no live registry
required — plant extracts under the dependencies root to preview the tree). JSON includes the
same edges on flat ``entries[].requires``; the nested tree appears under ``tree``. Doc samples:
xref:dependencies/managing/list-dependencies.adoc#list-dependencies[Listing dependency trees]
(``list-dependencies-requires`` / ``list-dependencies-requires-resolve`` partials). Design:
https://github.com/ja11sop/cuppa/blob/master/design/archive/list-deps-requires-closure.md[`list-deps-requires-closure`].

See also xref:dependencies/publishing/packages.adoc[Publishing packages].

Integration coverage: xref:integration/test-packages.adoc[].
