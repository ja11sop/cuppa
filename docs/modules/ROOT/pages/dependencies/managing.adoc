= Managing dependencies
:description: List, remove, purge, inventory, and develop working copies

[#which-listing]
== Which listing for which question

Cuppa has several read-only reports that answer different questions. `--develop` is a *build*
switch; `--list-develop` is a *report* about working copies. They are easy to mix up.

[cols="3,3,4"]
|===
| You want to know… | Use | Looks at

| What is under the shared dependencies root, and which trees this project would use | `--list-dependencies` (optional `--list-scope`) | `--dependencies-root` (for example `~/.cuppa/dependencies` or a legacy `~/_cuppa/_download`)
| What archives sit under the downloads root, and which trees they feed | `--list-downloads` (optional `--list-scope`) | `--downloads-root` (for example `~/.cuppa/downloads` or a legacy `~/_cuppa/_cache`)
| Branch, cleanliness, and ahead/behind of configured develop working copies | `--list-develop` | Develop paths from the sconstruct
| What is under `_build` | `--list-builds` | `--build-root`
|===

**Inspecting dependency storage** — omit `--develop`:

[source,shell]
----
cuppa -Q -D --list-dependencies
----

Resolve marks the tree this project would use (without develop) as `referenced`, and sibling
branches or other leftovers as `unreferenced`. That is the listing to use before reclaiming disk.

**Inspecting develop checkouts** — also omit `--develop` unless you want the banner to say it is
active; the table is the same either way:

[source,shell]
----
cuppa -Q -D --list-develop
----

**`--list-dependencies --develop` is uncommon.** Passing `--develop` makes resolve point at
working copies, so cache trees for those identities are no longer `in use`; the dependency name
row shows `develop` instead (the branches themselves stay unmarked). Use that only when you care
how the storage table would look under a develop resolve — not as the default storage listing,
and not instead of `--list-develop`.

[source,shell]
----
# Storage under a develop resolve (optional)
cuppa -Q -D --list-dependencies --develop
----

[#list-dependencies]
== Listing dependency trees

`--list-dependencies` walks the dependencies root and prints a hierarchical table: size,
last used, remark (`in use` / `N used` when more than one leaf is selected / `missing` /
`develop`), and dependency identity. Before the walk it prints `Collating dependency tree...`
(text and verbose only; omitted for JSON). When inventory sizes are missing or only sampled
estimates, it prints a short notice and upgrades those trees to exact sizes (the first run on a
large root can take a while; later runs reuse the cache). Pass `--exact-sizes` to force a full
remeasure of every tree. Rows are grouped referenced first then unreferenced,
then by type (repository dependencies, gitlab packages, source archives, …), then by short name or
registry name, with branch or version children underneath. On-disk paths are omitted by
default; pass `--list-format=verbose` to add a LOCATION column, or `--list-format=json` for a
machine-readable tree (plus flat `entries`). Default dependencies that are expected but absent
appear as `missing`. Referenced section roll-ups separate `dependencies in use`,
`missing dependencies` (when any expected trees are absent), and only then
`potentially stale dependencies` for other non-selected referenced leaves. It exits without
building (exit 0 even when some rows are missing). See
xref:integration/test-list-dependencies.adoc[`test_list_dependencies`] for the integration
scenario.

[source,shell]
----
cuppa -Q -D --list-dependencies
cuppa -Q -D --list-dependencies --list-scope=referenced
cuppa -Q -D --list-dependencies --list-scope=compact
cuppa -Q -D --list-dependencies --list-format=verbose
cuppa -Q -D --list-dependencies --list-format=json
cuppa -Q -D --list-dependencies --exact-sizes
----

Example `--list-format=json` output (shortened fixture: one referenced leaf and one
unreferenced leftover; `tree` mirrors the text hierarchy and `entries` is a flat list of

`--list-scope` selects which part of the listing to show. The values nest:

* `all` (default) — referenced section, then unreferenced
* `referenced` — resolved identities only, **including** unused siblings under those
  identities (other versions / branches next to `in use`). For GitLab packages the identity
  is the registry name (for example `boost_package`); siblings share the on-disk package
  folder (`boost/<version>`), so an unused version stays in this section rather than under
  `unreferenced`
* `compact` — a refinement of `referenced`: resolve-selected leaves only
  (`in use` / `missing` / develop-shadowed). No unused siblings, and never the
  unreferenced section
* `unreferenced` — leftover identities this project does not resolve

`compact` therefore implies `referenced`; it is not an orthogonal axis from
`--list-format`. You can still combine any scope with `verbose` or `json`. Persist a
preference in `~/.cuppaconfig` or `configure.conf` as `list_scope = 'referenced'`.
`--list-dependencies-scope` remains as a deprecated alias.

[#list-downloads]
== Listing downloads

`--list-downloads` walks the downloads root and prints a hierarchical table of cached archives
together with the dependency trees they regenerate. Before the walk it prints
`Collating downloads tree...` (text and verbose only). Rows are grouped referenced first then
unreferenced, then by type, then by identity. Under each identity the archive leaf is the file
under `--downloads-root`; an `[E]` child shows the matching tree under
`--dependencies-root` (GitLab toolchain folder, or `name/version` for HTTP source archives).
Parent `SIZE` values roll up **archive** bytes only so the footer answers how much download
cache would be reclaimed. Extract sizes stay on the `[E]` leaf for impact.

`--list-scope` filters the same nested way as `--list-dependencies`
(`all` / `referenced` / `compact` / `unreferenced`). `--list-format=verbose` adds LOCATION
(archive path and extract path). `--list-format=json` includes `tree`, flat `entries` with
`kind` `archive` or `product`, `archive_count`, `scope`, and archive-only `total_bytes` /
`unreferenced_bytes`. See
xref:integration/test-list-downloads.adoc[`test_list_downloads`].

[source,shell]
----
cuppa -Q -D --list-downloads
cuppa -Q -D --list-downloads --list-scope=referenced
cuppa -Q -D --list-downloads --list-scope=compact
cuppa -Q -D --list-downloads --list-format=verbose
cuppa -Q -D --list-downloads --list-format=json
----

Under `--list-format=verbose` a LOCATION column is added. What it shows depends on the type:

* *Location dependencies* — bare repository URL on the identity; `URL@branch` on each branch leaf.
* *GitLab packages* — empty on the identity; registry `…/package/version` on the version row;
  archive basename on each toolchain leaf.
* *Source archives* (Boost source tarballs, GitHub release zips, and similar) — short name such as

not the GitLab registry URL on the version row). A footer explains the mark in verbose mode
whenever such archives are present. If re-extracting a dependency fails, remove the corrupt
archive under downloads; deleting only the dependency tree is not enough.

[#remove-dependencies]
== Removing dependency trees

`--remove-dependencies=name1,name2` and `--remove-all-dependencies` delete trees under the
dependencies root for the named registry dependencies (or every default dependency), scoped to
the current toolchain / variant / location-match selection — the same options that decide where
cuppa writes. They exit without building. Downloads, develop working copies, and unreferenced
trees that are not named stay put; siblings for other toolchains or branches are reported as
left behind. SCons `-n` is a dry run.

Names are the keys this project uses: `default_dependencies` plus names registered from the
sconstruct’s `dependencies=[…]` list. Built-in factories that module scan always registers
(`boost`, `qt4`, …) are **not** removable unless the project names them that way. On-disk folder
names and listing short names are rejected. An unknown or unused name prints an error (rejected name error-coloured and emphasised) and a
ruled tree of dependencies that *can* be removed for the current selection (the in-use /
referenced picture from `--list-dependencies`, without unreferenced leftovers), after
`Collating dependency tree...`. See
xref:integration/test-remove-dependencies.adoc[`test_remove_dependencies`].

Tokens may also use the shared `[selector]name[/qualifier]` form described in
xref:#dependency-tokens[Dependency tokens] — for example `[source]boost` or
`[gl]boost_package/1.91` — to restrict by storage bucket and optional leaf qualifier.

Source Boost (the `boost` dependency that builds with b2) stores headers and all toolchain
variant products inside one extract folder. When that dependency implements selection-scoped
`storage_clean` (Boost does), `--remove-dependencies=boost` deletes only the b2 **stage** and
matching Boost.Build toolset directories under `--build-dir` (`bin.<abi>`) for the current
toolchain / variant / arch selection — not the whole `bin.<abi>` tree. The extract root,
headers, and the `b2` binary stay in place so a later build does not need to re-download the
tarball. Other stage trees and other toolsets' intermediates under the same extract are reported
as left behind. Removal leaves use honest scopes: cuppa-precise for stage
(`clean/build.c{plus}{plus}2c [clang211/debug/x86_64]`) and Boost.Build toolset **family** for bin
(`clean/bin.c{plus}{plus}2c [clang-linux-21*/debug]` — major family ± patch dirs such as `clang-linux-21.1`,
not a cuppa minor like `clang211`). The identity SIZE is the full extract (same basis as
`--list-dependencies`). Products and a muted `source assets` leaf hang under an `[E]` extract
row (`---` nothing going, `-✔-` partial, `✔✔✔` everything under it going). Empty `bin.<abi>`
husks with no toolset children stay on disk but are omitted from the table. The freed-space
summary reports the remaining archive size after product removal.
`--boost-patched` selects the `patched/` home; without it, `clean/` is active and `patched/`
products show as leftovers.
After a live product clean, cuppa refreshes that extract's inventory with an exact size, and the
verify hint is `cuppa -Q -D --list-dependencies` (listing upgrades any remaining missing or
estimated inventory sizes to exact on encounter).
Dependencies without `storage_clean` still remove their
whole owned tree under the dependencies root (for example GitLab `boost_package` removes the
selected package variant folder). Dependency authors declare those trees with `storage_paths()`
and optional `storage_clean()` — see xref:dependencies/extending.adoc[Writing your own dependencies].

[source,shell]
----
cuppa -Q -D --remove-dependencies=boost_package
cuppa -Q -D --dbg --toolchains=gcc --remove-dependencies=boost_package
cuppa -Q -D --dbg --remove-dependencies=boost
cuppa -Q -D --dbg --remove-dependencies='[source]boost'
cuppa -Q -D -n --remove-dependencies=widget
cuppa -Q -D --remove-all-dependencies
----

[#dependency-tokens]
== Dependency tokens

`--remove-dependencies`, `--purge-dependencies`, `--wipe-dependencies`, and
`--force-wipe-dependencies` share one token grammar:

[source,text]
----
[selector]name
[selector]name/qualifier
name
name/qualifier
----

* **Selector** (optional) restricts the match to one storage bucket, using the same axis as
  `--list-dependencies` type groups. Aliases: `[source]` / `[sa]` / `[archive]` for source
  archives; `[gl]` / `[gitlab]` for GitLab packages; `[repo]` / `[vcs]` / `[repository]` for
  repository (VCS) trees; `[conan]` / `[cn]` for Conan. `[gh]` is reserved. Quiet alias
  `[location]` still maps to repository.
* **Untyped** tokens match across **all** buckets on purpose (for example source Boost and a
  GitLab package that share a name).
* **Qualifier** is the leaf shown in the list tree (`1.91.0`, `@11.1.1`). Shell / `fnmatch`
  wildcards (`*`, `?`, `[…]`) are accepted on the name and/or qualifier; quote them so the shell
  does not expand them.
* Remove / purge / wipe still require **project-used** names; force-wipe does not.
* Reports nest **summary → type → identity → version → leaves**, matching `--list-dependencies`
  on the identity/version axis. A summary root shows **removing** / **wiped** vs **remaining**
  bytes. Version marks follow extract rollups (`✔✔✔` full, `-✔-` partial, `---` untouched).
  Match versions with `name/qualifier` tokens (for example `boost/1.8*`), not a glued name like
  `boost*1.8*`.

[source,shell]
----
cuppa -Q -D -n --remove-dependencies='[source]boost'
cuppa -Q -D -n --wipe-dependencies='[gl]boost_package/1.91'
cuppa -Q -D -n --force-wipe-dependencies='[source]boost/1.8*'
----

[#purge-dependencies]
== Purging dependencies and downloads

`--purge-dependencies=name1,name2` and `--purge-all-dependencies` do everything
`--remove-dependencies` / `--remove-all-dependencies` do, then delete the matching archives
under the downloads root for the **same names and selection** (`--toolchains`, variants,
location-match). `--purge-all-dependencies` means every **project-used** name — not every leftover
toolchain tarball on disk. Unreferenced clang archives stay, just as `--list-downloads` shows them.

Do not combine any `--purge-*` flag with any `--remove-*` flag in one invocation (name lists are
not merged). Unknown names use the same hint tree as remove. A missing download is not a failure:
remove still runs and the report notes there was no archive to delete. Develop working copies are
never deleted; downloads for that name may still be purged. SCons `-n` is a dry run.

Source Boost with `storage_clean` still leaves the extract (headers / `b2` / the other patch home);
the **download file** is deleted. That reclaims download space; the next build keeps using the
extract. For a full clear-down of the extract (and matching downloads) so the next build
re-downloads and re-extracts, use xref:#wipe-dependencies[`--wipe-dependencies`].

The report nests download → `[E]` → source assets and products (the same pairing as
`--list-downloads`). `[E]` uses a partial mark when the extract stays. Remove-without-purge uses
the same `[E]` subtree directly under the identity. Leftover other-selection extracts **and**
leftover downloads are called out like today’s leftover trees. Freed space includes download
bytes. Verify with `cuppa -Q -D --list-downloads` (a subdued note remains when archive-clean left
source assets — `--list-dependencies` is still useful there).

[source,shell]
----
cuppa -Q -D --purge-dependencies=boost_package
cuppa -Q -D --dbg --toolchains=gcc --purge-dependencies=boost_package
cuppa -Q -D --dbg --purge-dependencies=boost
cuppa -Q -D -n --purge-dependencies=widget
cuppa -Q -D --purge-all-dependencies
----

[#wipe-dependencies]
== Wiping dependencies (clear-down)

`--wipe-dependencies=name1,name2` clears the **whole extract** for the named **project-used**
dependencies under the **current selection**, plus matching downloads. Unlike purge, source Boost
with `storage_clean` does **not** stop at product clean — the extract goes too. The next build
without `--offline` re-downloads and re-extracts as usual.

For wiping **every** project-used name in the current selection, use
`--force-wipe-all-dependencies` (the `force-` prefix marks how wide that is). For specific old
versions or branches visible in the list tree (including unused siblings under a referenced
identity), use xref:#force-wipe-dependencies[`--force-wipe-dependencies`].

Do not combine any wipe / force-wipe flag with `--remove-*` or `--purge-*`, or with another wipe
mode, in one invocation. Develop working copies are never deleted. SCons `-n` is a dry run.
Missing trees / downloads are not a failure.
When inventory `used_by` names another project, `--wipe-dependencies` emits the same judgement-tree
notices as force-wipe (warning on dry-run, past-tense note after a real wipe). See
xref:contributing/report-patterns.adoc[Report patterns].

[source,shell]
----
cuppa -Q -D --wipe-dependencies=boost
cuppa -Q -D --dbg --wipe-dependencies=boost_package
cuppa -Q -D -n --wipe-dependencies=widget
cuppa -Q -D --force-wipe-all-dependencies
----

Verify with `--list-dependencies` and `--list-downloads`.

See xref:integration/test-wipe-dependencies.adoc[`test_wipe_dependencies`].

[#force-wipe-dependencies]
== Force-wiping named leaves

Old Boost versions and unused location branches often sit under the **referenced** section as
siblings of the leaf marked `in use` — they are **not** in `unreferenced`. Naming them from the
list tree is the reclaim path:

[source,shell]
----
cuppa -Q -D --list-dependencies
cuppa -Q -D -n --force-wipe-dependencies=boost/1.86.0,boost/1.87.0
cuppa -Q -D --force-wipe-dependencies=boost/1.86.0,boost/1.87.0
----

Tokens are `[selector]name` or `[selector]name/qualifier` (selector optional) as shown in the
tree — see xref:#dependency-tokens[Dependency tokens]. Examples: `boost/1.86.0`,
`[source]boost/1.8*`, `fmt/@11.1.1`, `widget/@` (unqualified stem — listed as
`@master (unqualified)`). Bare project-used identity names belong on
`--wipe-dependencies`. Matching downloads are wiped too. Referenced /
unreferenced / `in use` do **not** block the wipe — the long flag name is the acknowledgement.
Inventory `used_by` naming another project prints a warning and still proceeds.
A token with no matching leaf (or a matched path that is already gone) does **not** abort the
rest of the list: other tokens still wipe, and each miss appears in the judgement tree (warning
on dry-run, past-tense note after a real wipe). Ambiguous non-wildcard tokens still fail hard.

When both an unqualified stem and `stem@<default>` exist, dependency-management commands
(list / remove / purge / wipe) note the pair at debug log level. Those commands also print a
dry-run `--force-wipe-dependencies=` hint with `name/@` tokens after the report footer
(except `--list-dependencies`, which colours the unused `@<default> (unqualified)` leaf with
the remove accent and ends with that hint in its footer). Under `--list-scope=compact` the
sibling is hidden, so Location notices and wipe candidates for it are omitted — use
`referenced` or `all` to inspect them. Under `--offline`, candidates with inventory `used_by`
from another project are omitted from that hint. Confirm with `-n`, then drop `-n` to wipe. If
inventory still records another project's use of the unqualified path, force-wipe reports it
after the report table (judgement tree, like other removal notices). On a dry-run (`-n`) that
notice is a warning in the present tense so you can still abort; after a real wipe it becomes a
past-tense note (`wiped…`, `removing the copy was safe`) and explains that proceeding was safe
when the canonical folder is present.

Exact tokens must resolve to exactly one leaf (zero or multiple → error with candidates).
Shell / `fnmatch` wildcards (`*`, `?`, `[…]`) on either side wipe **all** matching leaves —
useful for a version series:

[source,shell]
----
cuppa -Q -D -n --force-wipe-dependencies='boost/1.8*'
cuppa -Q -D --force-wipe-dependencies='boost/1.8*'
----

Quote the token in the shell so `*` is not expanded by the shell before cuppa sees it.
Dry-run (`-n`) lists every matched path and size before you drop `-n`. Same-identity
siblings that are **not** matched (for example `boost/1.90.0` when wiping `boost/1.8*`)
stay in the report without a remove remark, so the identity parent is not marked as fully
removed and the final size includes what remains. A wildcard that matches nothing exits
non-zero. Full regular expressions are not accepted (dots in versions stay literal under
`fnmatch`).

Location example (unused `@11.1.1`, keep `@master` in use):

[source,shell]
----
cuppa -Q -D --force-wipe-dependencies=fmt/@11.1.1
----

Unqualified stem duplicate (listed as `@master (unqualified)`; `@` is the wipe shorthand):

[source,shell]
----
cuppa -Q -D -n --force-wipe-dependencies=widget/@
cuppa -Q -D --force-wipe-dependencies=widget/@
----

Mixed archive + location tokens:

[source,shell]
----
cuppa -Q -D --force-wipe-dependencies=boost/1.86.0,boost/1.87.0,fmt/@11.1.1
----

[#force-wipe-unreferenced-dependencies]
== Force-wiping unreferenced dependencies

`--force-wipe-unreferenced-dependencies` clears every dependency **tree** and matching
**download** this resolve marks as `unreferenced` — a rare blunt orphan sweep. Prefer
xref:#force-wipe-dependencies[`--force-wipe-dependencies`] when reclaiming specific old Boost
versions under a referenced identity.

[source,shell]
----
cuppa -Q -D --list-dependencies --list-scope=unreferenced
cuppa -Q -D -n --force-wipe-unreferenced-dependencies
cuppa -Q -D --force-wipe-unreferenced-dependencies
----

Verify with:

[source,shell]
----
cuppa -Q -D --list-dependencies --list-scope=unreferenced
cuppa -Q -D --list-downloads --list-scope=unreferenced
----

== Checking your develop copies

`--develop` substitutes a working copy on disk for a retrieved dependency and says nothing about the state of that copy.
You can be building your feature branch against a dependency parked on someone else's spike branch, or against a copy that has not been pulled for months, and the only symptom is a compile error that makes no sense, a test that fails only on your machine, or one that passes only on your machine.
A develop path that does not exist is not checked at all today: the swap happens regardless and the failure surfaces much later as a missing include.

`--list-develop` reports what you are actually building against.
It runs after dependency registration and exits without building.
One row appears for every dependency that has a develop location configured, whether or not `--develop` is active, plus a count of those that have none:

[source,shell]
----
cuppa -Q -D --list-develop
cuppa -Q -D --list-develop --list-format=json
----

`--list-format=json` emits a single object with `current_branch`, `default_branch`,
`develop_active`, `without_develop`, `would_update` (names `--update-develop` would
fast-forward as of the last fetch), `worst_severity`, and `entries` for each develop copy
(observed state, `severity` / `status`, `state` summary, and `notes`). Exit status is still
non-zero when a develop path does not exist.

The checked-in fragment is generated by
`python -m scripts.generate_doc_samples list-develop`; the generator uses the same formatter as
`--list-develop`. Add `--preview` to write a standalone page under `_docs_build/samples/`.

The table is the inventory of what you are building against.
Every judgement then hangs from the summary line as one tree, grouped by severity with the worst first, so reading down the tree is reading a work list: what stops the build, then what needs a decision, then what is only worth knowing.
The summary line matches the removal/wipe judgement intro: an emphasised location count, then always `[N errors][N warnings][N notes]` (zeros muted; non-zeros coloured), then the ok count and how many dependencies are not using develop.
Each severity heading counts the dependencies beneath it, and each dependency is named once, with a gap on the stem above each name so that a dependency and its reasons read as one block.
A reason too long for the line is wrapped to the table's right edge and the stem is carried down through the wrapped lines, so the report keeps one right edge and the tree stays a tree.
Paths are shown the way the table shows them, with `..` segments resolved and your home directory written as `~`, because a develop location written relative to the `sconstruct` resolves to a path that is hard to recognise.
Where the console cannot encode box drawing characters the tree falls back to ASCII.
No remote is contacted, so the option remains available with `--offline`.

The last line appears when `--update-develop` would do something with what has just been observed, and names the copies it would fast-forward.
The decision behind it is the one `--update-develop` uses, so the line cannot offer an update that the option then declines to make.
It can understate, because `--update-develop` fetches before deciding and a fetch can find copies that are behind without your knowing yet, which is why the line says so.
Nothing is printed when every copy would be left alone.

On a colour console the `ok` and `note` rows recede, so the rows at full strength are exactly the ones wanting attention.
Receding is done by reduced intensity rather than by a background colour, so it works on either console, and a terminal that ignores it simply shows a plain table.
On a light console reduced intensity applied to black text can look untouched, so grey is used there instead; set `CUPPA_CONSOLE_BACKGROUND=light` to say which console you have, since most terminals do not report it (see xref:configuration.adoc#_environment_variables[Environment variables]).
In the judgement tree the severity, the dependency name, and the values are coloured and the prose is left plain, so a dependency or branch name can be found without reading every line.

The report is written to standard output rather than to the log, because it is the result you asked for rather than commentary on producing it.
That means a quieter build does not take pieces out of it, and `-Q` gives you the report on its own:

[source,shell]
----
cuppa -Q -D --list-develop
cuppa -Q -D --list-develop --raw-output > develop.txt
----

Severity appears in the `STATUS` column as well as in colour, so it survives `--raw-output` and can be searched for.
It is the value of the option:

[cols="1,1"]
|===
| Situation | Severity

| Branch equals the branch being built, or the default branch | ok
| Any other branch, or detached HEAD | warning
| Behind upstream, or diverged | warning
| Ahead or modified, on the branch being built | note — this is the intended workflow
| Ahead or modified, on the default branch | warning — local work that no other build will see
| No upstream tracking branch | note — ahead and behind cannot be answered
| Not a working copy | warning
| Path does not exist | error
|===

Local work is only benign where the rest of the world will find it.
Uncommitted or unpushed changes on a branch that matches the branch being built are the intended workflow: when that branch is pushed, `--location-match-current-branch` selects it and everyone else's build sees the same code.
The same changes sitting on the default branch are a trap.
Your build works, because `--develop` reads the working copy; every build that does not use `--develop` resolves the dependency to the published default branch and compiles something else.
The warning names the remedy: put the work on a branch named for the branch you are building, commit it, and push it.

The exit status is zero for a report, and non-zero when a develop path does not exist, because that build cannot succeed and a CI job should hear about it.

=== Cloning missing develop copies

`--clone-develop` creates configured develop paths that are missing or empty.
It clones from the dependency's **unexpanded** git URL (so tokens never land in `.git/config`), checks out a branch that `--list-develop` will call ok, and recurses submodules.
Git clone progress is streamed at INFO or finer (`--progress`, on the controlling terminal when available; quieter verbosity levels suppress it).
It refuses non-empty destinations and locations that pin a tag or revision (develop copies must not be detached).
`--offline` is an error; `-n` prints the plan.

[source,shell]
----
cuppa -D --clone-develop
cuppa -D --clone-develop --update-develop
----

A `--develop` build that fails because a develop path is missing names this option in the error.

=== Aligning develop copies onto a feature branch

When a feature spans the consumer project and several local develop dependencies, put those copies on the same branch name, then return them to the *develop base* (home) when the work is done.

Git does not record which branch a feature was created from, so cuppa does not guess a parent.
Two settings describe home:

[cols="2,3,5"]
|===
| Notion | Option | Role

| Published default
| `--location-default-branch` (default `master`)
| What non-`--develop` builds resolve to; `--list-develop` treats uncommitted work here as a trap

| Develop base
| `--location-base-branch`
| Where `--checkout-develop-branch` creates a missing feature from, and where bare `--reset-develop-branch` returns. When unset, base is the published default
|===

[mermaid]
....
flowchart TD
    master["published default\n(location-default-branch)"]
    base["develop base / home\n(location-base-branch)"]
    feature["feature branch\n(checkout-develop-branch)"]
    master -.->|"simple repos: base unset\nbase ≡ default"| base
    base -->|"create missing feature\nfrom updated base"| feature
    feature -->|"bare --reset-develop-branch"| base
....

For a long-running integration line off `master`, set the base once (CLI or `configure.conf`):

[source,shell]
----
cuppa -D --location-base-branch=integration --save
----

That setting matches this history shape — features fork from and merge back to the middle line, while `master` stays the published default:

[mermaid]
....
%%{init: { 'gitGraph': { 'mainBranchName': 'master' } } }%%
gitGraph
  commit id: "on master"
  branch integration
  checkout integration
  commit id: "develop home"
  branch feature_orders
  checkout feature_orders
  commit id: "feature work"
  checkout integration
  merge feature_orders
....

When `--location-base-branch` is unset, base is the published default and the shape is the familiar feature-off-default line:

[mermaid]
....
%%{init: { 'gitGraph': { 'mainBranchName': 'master' } } }%%
gitGraph
  commit id: "on default"
  branch feature_orders
  checkout feature_orders
  commit id: "feature work"
  checkout master
  merge feature_orders
....

Typical feature workflow:

[mermaid]
....
sequenceDiagram
    participant Dev as Developer
    participant Cuppa as cuppa
    participant Copies as Develop copies
    Dev->>Cuppa: --checkout-develop-branch=current
    Cuppa->>Copies: switch to feature (create from base if needed)
    Dev->>Dev: commit and push in each repo
    Dev->>Cuppa: -Q -D --list-develop
    Cuppa->>Dev: report dirty / unpushed / ok
    Dev->>Cuppa: --reset-develop-branch
    Cuppa->>Copies: checkout base, then fetch and fast-forward
....

[source,shell]
----
cuppa -D --checkout-develop-branch=current
# ... commit and push in each repo ...
cuppa -Q -D --list-develop
cuppa -D --reset-develop-branch
----

`--checkout-develop-branch=NAME` switches every develop git working copy to `NAME` (`current` means the consumer project's current branch).
Clean copies left on a stale feature branch move via the develop base and a pull first, then create or track `NAME`.
Dirty or unpushed copies are left alone and reported — use `--list-develop` to see outstanding commits before you abandon a branch.

`--reset-develop-branch` returns each copy to a target, then fetches and fast-forwards where `--update-develop` would:

* bare flag, or `=base` — the develop base (`--location-base-branch`, else the published default)
* `=default` — `--location-default-branch` even when base differs
* `=current` — the consumer project's current branch
* `=NAME` — that branch name

It does not delete leftover feature branches.

[mermaid]
....
flowchart LR
    subgraph home [Home policy]
      D["default\nmaster"]
      B["base\nintegration"]
    end
    F[feature_orders]
    F -->|"--reset-develop-branch"| B
    F -->|"--reset-develop-branch=default"| D
    F -->|"--reset-develop-branch=current"| C[consumer current]
....

`--list-develop` treats a copy as on an acceptable branch when it is on the consumer's current branch, the published default, or the develop base.

=== Updating develop copies

`--update-develop` answers the next question after `--list-develop` tells you a copy is behind.
It fetches each git working copy (with streamed `--progress` at INFO or finer when the network is used), then fast-forwards only those that are clean and strictly behind their upstream.
Everything else is skipped and reported with the reason: ahead, diverged, modified, detached, no upstream, not a working copy, or path missing.

[source,shell]
----
cuppa -D --update-develop
cuppa -D --update-develop -n
----

It prints the table before acting, then what it did to each copy, then the table again if anything moved, so the effect is visible rather than inferred.
It never stashes, resets, rewrites history, or switches branches.
A fast-forward of a clean tree discards nothing and leaves nothing to recover from.
`--offline` makes `--update-develop` an error rather than a silent no-op, because options in this family that need the network refuse `--offline`.
`-n` / `--no-exec` shows the plan and changes nothing; because no fetch happens, the plan is judged as of your last fetch, and the report says so.
Updating several repositories is not atomic: a failure in one is reported, the rest continue, and the exit status is non-zero.

Subversion, Mercurial, and Bazaar copies appear in the `--list-develop` table with branch and revision from the existing SCM support; ahead, behind, and modified are reported as unknown, and `--update-develop` leaves them alone.
