= Methods
:description: Cuppa environment methods for building, testing, libraries, and reporting

Methods are registered on each cuppa environment and called from `sconscript` files after `Import('env')`.
They differ from raw SCons builders (`Program`, `Object`, `StaticLibrary`) by understanding variants, toolchains, progress reporting, cuppa's `_build/` layout, and (when enabled) C++20 modules.

This page focuses on the build surface you use every day.
For the vocabulary behind methods, see xref:concepts.adoc[Concepts].
For compiler defaults applied underneath these calls, see xref:toolchains.adoc[Toolchains].

== Prerequisites

* Cuppa installed and a project with `cuppa.run()` in `sconstruct` (xref:quickstart.adoc[Quickstart])
* Familiarity with `Import('env')` in a `sconscript`
* A C++ toolchain available to cuppa (`gcc`, `clang`, or `vc` on Windows)

== Progress tracking and variant scoping

Cuppa wires build progress through `cuppa.progress.NotifyProgress` so each build variant reports begin/start/finish/end in a predictable order.

`NotifyProgress` is attached to methods that emit build action nodes (`Build`, `Compile`, `Test`, coverage collation, doc builders, and so on).
Methods that only mutate env state or select nodes (`StdCpp`, `BuildWith`, `Filter`, `RecursiveGlob`, `ImportModules`, etc.) do **not** call it directly.

Progress nodes form a dependency chain that constrains when targets may run:

[mermaid]
....
flowchart TD
    SB[SconstructBegin] --> B[Begin sconscript]
    B --> ST[Starting variant]
    ST --> T[Method targets]
    T --> F[Finished variant]
    F --> E[End sconscript]
    E --> SE[SconstructEnd]
....

`Begin` / `End` are keyed by sconscript file.
`Starting` / `Finished` are keyed by the variant path (`parent of env['build_dir']`).
In cuppa's normal layout that path already includes the sconscript segment, so different sconscripts get distinct Starting/Finished nodes without a composite key.

Practical rules when adding or changing methods:

* If a method creates SCons action nodes, wire `NotifyProgress.add(env, targets)` (or delegate to a method that already does).
* If a method only configures env or returns filtered/existing nodes, do not add progress wiring.
* Keep progress wiring on the same variant env that creates the nodes.

== Core build methods

=== Building a program with `Build`

`env.Build(target, source, …)` produces a variant-aware executable.
Cuppa compiles sources (via `Compile`), links a `Program`, and installs it under the variant's `final/` directory.

In this tutorial you will declare a small program and build the debug variant.

[source,python]
----
Import('env')

env.Build('hello', ['hello.cpp'])
----

`target` is the logical program name (cuppa may append a variant suffix depending on options).
`source` is a file, list of files, or nodes from `Compile` / `Module`.
Additional keyword arguments are forwarded to SCons `Program` (for example `LIBS`, `LIBPATH`).

Build it:

[source,sh]
----
cuppa -D --dbg
----

`--dbg` selects the debug variant.
`-D` walks upward until cuppa finds the `sconstruct`, then builds the active `sconscript` files.

You can also pass library and dependency-related kwargs that cuppa understands when composing programs:

[source,python]
----
Import('env')

env.Build(
    'app',
    ['main.cpp', 'util.cpp'],
    LIBS=['m'],
    depends_on=[other_nodes],   # optional extra SCons Depends edges
)
----

=== Compiling objects with `Compile`

`env.Compile(source, …)` (and `CompileStatic` / `CompileShared`) turns sources into object files without linking.
Use this when you need objects for custom link steps, or when you want to share objects across targets.

[source,python]
----
Import('env')

objs = env.Compile(['a.cpp', 'b.cpp'])
env.Build('app', objs)
----

When `env['modules']` is true (see xref:cxx-modules.adoc[C++ modules]), `Compile` delegates to the modules compile path so interface units produce BMIs and consumers receive the right consume flags.

=== Building libraries with `BuildLib`

`env.BuildLib`, `BuildStaticLib`, and `BuildSharedLib` build libraries into `final/`.

[source,python]
----
Import('env')

env.BuildStaticLib('mathlib', ['math.cpp'])
env.AppendUnique(LIBPATH=[env['abs_final_dir']])
env.Build('app', ['main.cpp'], LIBS=['mathlib'])
----

With `--modules` enabled, library builds that contain named module interfaces also install BMIs under `final/modules/` and write `module-map.json` for consumers (see xref:cxx-modules.adoc#packaged-modules[Packaged modules]).

NOTE: On Windows, MSVC *module* export is not the same as *DLL* export.
A shared library may need `__declspec(dllexport)` (or a module-definition file) before the linker produces an import `.lib`.

=== Testing with `BuildTest`

`env.BuildTest(target, source, …)` builds a program and, when `--test` or `--force-test` is active, runs it through the configured runner.

[source,python]
----
Import('env')

env.BuildTest('unit_tests', ['tests.cpp'])
----

Run tests:

[source,sh]
----
cuppa -D --dbg --test --show-test-output
----

`--show-test-output` prints runner output instead of only the pass/fail summary.

Preferred parameters:

|===
| Parameter | Role

| `runner`
| Runner name (default from `cuppa.run(default_runner=…)`; often `process`, `boost`, or `patched_boost`)

| `expected`
| Expected outcome string (default `'passed'`)

| `expected_exit_code`
| Override the expected process exit code

| `build_depends_on`
| Extra SCons Depends for the *build* (compile/link)

| `test_depends_on`
| Extra files/nodes associated with the *test run* (rebuild/re-run when they change)

| `working_dir`
| Directory in which to run the test

| `command`
| Override the command used to invoke the test binary (use this for CLI arguments)

| `cov_include_patterns` / `cov_exclude_patterns`
| Narrow coverage instrumentation when combined with `--cov`
|===

IMPORTANT: `test_depends_on` adds nodes to the test builder's source list so SCons re-runs the test when those files change.
It is *not* passed as command-line arguments to the test program.
Use `command` (or a wrapper) when the program must receive paths on argv.

Deprecated aliases (still accepted; prefer the names above):

|===
| Alias | Prefer instead

| `depends_on`
| `build_depends_on`

| `data`
| `test_depends_on`
|===

When both a preferred name and its alias are supplied, the lists are merged.

Toolchain-specific aliases such as `BuildBoostTest` appear when the toolchain advertises those runners.

=== Testing with `Test`

`env.Test(program, …)` attaches a test action to an *existing* binary (for example one produced by `Build`).

[source,python]
----
Import('env')

prog = env.Build('unit_tests', ['tests.cpp'])
env.Test(prog, depends_on=['fixtures/input.txt'])
----

Preferred parameters:

|===
| Parameter | Role

| `depends_on`
| Extra files/nodes associated with the test run (rebuild/re-run when they change)

| `runner` / `expected` / `expected_exit_code` / `command` / `working_dir`
| Same meaning as on `BuildTest`
|===

Deprecated aliases:

|===
| Alias | Prefer instead

| `data`
| `depends_on`
|===

When both `depends_on` and `data` are supplied, the lists are merged.
`depends_on` / `data` are *not* program argv — use `command` for that.

Toolchain-specific aliases such as `BoostTest` appear when the toolchain advertises those runners.

=== Benchmarks with `BuildBenchmark`

`env.BuildBenchmark(target, source, …)` builds a program and, when `--benchmark` or `--force-benchmark` is active, runs it through the configured runner.

Preferred parameters mirror `BuildTest`, with explicit Depends names:

|===
| Parameter | Role

| `build_depends_on`
| Extra SCons Depends for the *build* (compile/link)

| `benchmark_depends_on`
| Extra files/nodes associated with the *benchmark run*
|===

Deprecated aliases: `depends_on` → `build_depends_on`; `data` → `benchmark_depends_on`.

=== Benchmarks with `Benchmark`

`env.Benchmark(program, …)` attaches a benchmark action to an existing binary.

Preferred: `depends_on` for run-side Depends.
Deprecated alias: `data`.

=== Generic runs with `Run`

`env.Run` is a generic process runner activated by `--run` / `--force-run` (and also available alongside test/benchmark actions).

[source,python]
----
Import('env')

env.Build('tool', ['tool.cpp'])
env.Run('tool', command_args=['--self-check'], depends_on=['config.json'])
----

Preferred: `depends_on` for run-side Depends; `command_args` for argv.
Deprecated alias: `data`.

== Custom commands and working directories

Cuppa colours compiler and tool output by replacing SCons `SPAWN` with a processor that runs each command as an *argv list* (not through a shell).
That is the right default for parallel builds, quoting, and safety — but it means **multi-part shell strings do not work**.

=== What fails

Do *not* write actions like:

[source,python]
----
# Avoid: "cd … && …" needs a shell; argv splitting breaks it
env.Command(target, source, Action("cd $DIR && $COMMAND"))
----

The same problem appears with shell metacharacters that only a shell would expand (for example quoting tricks around linker `-Wl,-rpath='$ORIGIN'` when the quotes are meant for the shell rather than for the linker argv).

SCons Builder `chdir=` is also a poor fit under parallel builds: Python has one process-wide current directory, so worker threads interfere with each other.
SCons documents that limitation for `-j`.

=== Prefer `cwd` (parallel-safe)

Pass a working directory into the *subprocess*, not by changing the SCons process directory.

For tests and runs, use the existing `working_dir` parameter on `BuildTest`, `Test`, `BuildBenchmark`, `Benchmark`, and `Run`:

[source,python]
----
Import('env')

env.BuildTest(
    'cwd_probe',
    ['cwd_probe.cpp'],
    working_dir=env['abs_final_dir'],  # process cwd; no "cd && …"
)
----

For a custom `env.Command`, use a Python action (or cuppa's helper) that calls the tool with `cwd=`:

[source,python]
----
Import('env')
import os
from cuppa.utility.command import run

tool = env.Build('tool', ['tool.cpp'])
marker = env.File(os.path.join(env['abs_final_dir'], 'tool.done'))
# Basename only: working_dir supplies the directory. Avoid './' or '.\\' prefixes —
# shlex.split (posix) would treat '\\t' in '.\\tool.exe' as an escape on Windows.
tool_cmd = 'tool{} --self-check'.format(env['PROGSUFFIX'])

env.Command(
    marker,
    tool,
    run(tool_cmd, working_dir=env['abs_final_dir'], completion_file=marker),
)
----

`cuppa.utility.command.run` splits the command with `shlex`, resolves a relative executable against `working_dir` when that file exists, and runs it via cuppa's incremental subprocess helper with `cwd=working_dir`.
Pass a basename such as `tool` / `tool.exe` (via `env['PROGSUFFIX']`) rather than `./tool` or `.\\tool.exe` — the latter is mangled by posix `shlex` on Windows (`\\t` becomes a tab escape).
That stays correct under `--parallel` / SCons `-j` because each process gets its own working directory without `os.chdir` in the build process.

You can also use a small Python `Action` that builds an argv list and passes `cwd=` to `subprocess` (or to `IncrementalSubProcess.Popen2`) yourself.
Python actions do not go through the coloured `SPAWN` path as shell strings.

=== When `--use-shell` is appropriate

`--use-shell` makes cuppa join the argv list and run with `subprocess` `shell=True` on the **IncrementalSubProcess** path used by colourised POSIX `SPAWN` (and by helpers such as `cuppa.utility.command.run`).

That can unstick a legacy multi-part shell action or shell-only quoting on that path, but:

* It is *not* the default (enabling it by default has broken Linux builds in the past)
* Prefer rewriting the action with `working_dir` / `cwd=` / a Python callable instead
* Treat it as an escape hatch for tools you do not control, not as the recommended pattern

Platform note for issue #14-style `Action("cd … && …")` strings:

* **POSIX + colourised output (default):** cuppa replaces `SPAWN` with `posix_spawn`, which runs argv via `IncrementalSubProcess` — multi-part shell strings fail (`cd` is treated as the executable).
* **POSIX + `--raw-output`:** colourised `SPAWN` is not installed; SCons' default shell spawn can run `cd … && …` (still not recommended for parallel-safe builds).
* **Windows + colourised output (default):** cuppa's `windows_spawn` wraps native SCons `PSPAWN` for colouring; it does *not* use the argv `IncrementalSubProcess` path, so shell-style strings may still succeed. Do not take that as a reason to use `cd &&` in portable sconscripts.

See xref:cli-reference.adoc[CLI reference] for the flag.

Integration coverage for these examples: xref:integration/test-custom-commands.adoc[].

== Dependencies and profiles

[source,python]
----
Import('env')

env.BuildWith('boost')
env.BuildProfile('quad_float')   # example built-in profile
env.Build('app', ['main.cpp'])
----

* `BuildWith` applies named dependency factories (Boost, location packages, GitLab packages, …)
* `Using` looks up a dependency factory by name
* `BuildProfile` applies named profiles (lightweight env tweaks)

See xref:dependencies.adoc[Dependencies] and xref:packages.adoc[Packages].

== Versioning and sources

|===
| Method | Role

| `env.CreateVersion(…)`
| SCM-aware generated version sources

| `env.GlobFiles` / `env.RecursiveGlob`
| Source discovery relative to the sconscript

| `env.TargetFrom(path)`
| Derive a target basename from a path

| `env.CopyFiles` / `env.CopyFilesAs`
| Filtered install/copy helpers
|===

Example -- collect sources and name the binary from a path:

[source,python]
----
Import('env')

sources = env.RecursiveGlob('*.cpp', start='src')
env.Build(env.TargetFrom('src/apps/server.cpp'), sources)
----

== Dialect, modules, and flags

|===
| Method | Role

| `env.StdCpp(standard)`
| Set the C++ dialect for this env (for example `'c++20'`, `'c++23'`)

| `env.Modules()` / `--modules`
| Enable C++20 modules for this env / all variants

| `env.HeaderUnit(path)`
| Register a header for BMI compilation (`'include/h.hpp'` or `'<span>'`)

| `env.Module(name, interface=…, implementation=…)`
| Compile/register a named module; objects link into a later `Build` in the same env

| `env.ImportModules(dir)`
| Load `modules/module-map.json` + BMIs from a packaged library

| `env.Filter` / `ReplaceFlags` / `RemoveFlags`
| Flag list manipulation
|===

Dialect and modules interact with toolchain defaults documented in xref:toolchains.adoc[Toolchains].
A full modules walkthrough is in xref:cxx-modules.adoc[C++ modules].

[source,python]
----
Import('env')

env.StdCpp('c++20')
env.Modules()
env.Module('math', interface='math.cppm', implementation=['math.cpp'])
env.Build('app', ['main.cpp'])
----

== Coverage

|===
| Method | Role

| `env.Coverage(program, sources, …)`
| Run coverage tooling for a binary (active with `--cov` / related actions)

| `env.CollateCoverageFiles(sources, destination=…)`
| Collate coverage HTML/JSON

| `env.CollateCoverageIndex(…)`
| Master coverage index across tests/toolchains
|===

IMPORTANT: `--cov` does *not* imply `--test`. For a typical coverage workflow:

[source,sh]
----
cuppa -D --cov --test --toolchains=gcc
----

See xref:testing-coverage.adoc[Testing and coverage].
Coverage instrumentation is supported for GCC and Clang; MSVC does not participate.

== Test reporting plugins

When the corresponding plugins are loaded (shipped with cuppa via `cuppa.method.plugins`):

* `env.GenerateHtmlTestReport(…)`
* `env.CollateTestReportIndex(…)`
* Bitten XML report generation (`GenerateBittenReport`)

These activate in concert with `--test`.
