= Toolchains
:description: Selecting, listing, and fetching compilers; links to GCC, Clang, and MSVC defaults

Cuppa discovers installed compilers at configure time and registers matching toolchain names.
When you call `env.Build` / `env.Compile`, the active toolchain applies a documented set of
default flags for the selected *variant* (`--dbg`, `--rel`, `--cov`).

Start with xref:toolchains/overview.adoc[Toolchains overview] for how discovery, selection,
variants, and dialects fit together. This hub provides the detailed selection, inventory,
fetched-archive, and shared {cpp} language-level reference. Per-family defaults, dialects, and
flag explanations live on the child pages:

== Selecting toolchains

[source,sh]
----
cuppa -D --toolchains=gcc,clang
cuppa -D --toolchains=gcc15,clang21
cuppa -D --toolchains=gcc*
----

Names are matched with fnmatch-style wildcards.
If you omit `--toolchains`, cuppa uses the platform default toolchain.

Prefer a family alias (`gcc`, `clang`, `vc`) for everyday builds; pin versioned aliases in CI for reproducibility.

Layout and package stems use `toolchain.name()` / `package_name()`, which follow
`--toolchain-identity=` (`full` keeps `gcc153`; `major` uses `gcc15`). Selection aliases are
unchanged. See xref:toolchains/overview.adoc#toolchain-identity[Build and package identity].

When debugging detection, use `--verbosity=debug` and `--dump`.

[#list-toolchains]
== Listing toolchains

`--list-toolchains` prints an inventory of compilers Cuppa can offer on this machine, then exits
(no build). Output is a ruled tree with two sections (normal typeface labels):

* **discovered** — PATH / distro probes (`gcc15`, `clang18`, …).
* **registered** — managed installs from `--toolchain-archive=` / `--clang-root=` / `--gcc-root=`
  (and cached rediscovery under `dependencies_root/toolchains/{clang,gcc}/`), with non-colliding
  session names such as `gcc17_gcc_snapshot_…` or `clang24_profiles_…`.

Within each section the hierarchy is **family → version → driver → name(s)**. Several Cuppa names
can share one driver (for example `gcc153`, `gcc15`, and `gcc`). The platform default name is marked
`(default)`. Driver paths use `~/…` when under the home directory.

`SIZE` / `LAST USED` show `--` for **discovered** compilers in this release (PATH installs are not
inventoried yet). Registered rows use on-disk size / newest mtime under the extract when available.

Force-wipe of toolchain dependencies applies only to **registered** rows. Discovered PATH compilers
are not Cuppa-owned.

[source,sh]
----
cuppa -Q -D --list-toolchains
cuppa -Q -D --list-toolchains --list-format=verbose
cuppa -Q -D --list-toolchains --list-format=json
----

With `--list-format=verbose`, each driver also shows `available dialects:` (every `-std=` name
available for that compiler version — working-draft name first within each generation, e.g.
`c{plus}{plus}2c` before `c{plus}{plus}26`, then older generations; Cuppa default marked),
`usable features:` (dialect-inclusive shorthand such as `all c{plus}{plus}2c`, plus any
still-gated extras like `coroutines`, plus opt-in `modules (experimental)` when Cuppa can
enable modules for that tool), Clang `stdlib choices:` when applicable, and
`default invocations:` for `dbg` / `cov` / `rel` (`c{plus}{plus}`, `c`, `link` templates with
`<sources>` / `<objects>` / `<static_libs>` / `<dynamic_libs>` placeholders). Each template is
shown as a quoted string (`c{plus}{plus}: "-Wall … <sources>"`); the surrounding quotes are
subdued like placeholders. Cuppa default link libraries (for example `-lpthread -lrt`, and Clang
`libc{plus}{plus}` extras) appear as normal `-l` tokens before the matching placeholder — see
xref:toolchains/gcc.adoc#gcc-default-linux-libraries[GCC] and
xref:toolchains/clang.adoc#clang-default-linux-libraries[Clang] for why those defaults exist.
Label keys use notice/yellow colour; variant names (`dbg` / `cov` / `rel`) and flag values
are normal text; commas, `(default)` / `(experimental)` qualifiers, quotes, and placeholders are
subdued. Horizontal rules span the full width of the widest content line (verbose dialect /
invocation rows included).

`--list-format=json` emits a nested payload (`sections` → `families` → `versions` → `drivers` →
`names`, plus `wipe_applies_to`). Verbose fields appear under each driver’s `describe` object.

`--list-dependencies` toolchain leaves show the same Cuppa session name you pass to `--toolchains=`
(for example `clang24_profiles_…`), while the on-disk folder remains
`toolchains/<family>/<qualifier>/`.

[#fetched-toolchains]
== Fetched toolchain archives (Clang and GCC)

Cuppa can download or point at compiler installs and register them as **toolchain dependencies** — the same idea as other dependencies (cached under the downloads / dependencies roots), without putting URLs in `--toolchains=`.

You can keep **several Clang and several GCC** installs registered at once and compare them in one run with a multi-toolchain selection, for example `--toolchains=gcc15,gcc16_gcc_snapshot_20260725_1_amd64,clang24_profiles_2026_08_07_27`.

=== Managed archives (`--toolchain-archive=`)

Clang Release tarballs / zips and Debian **gcc-snapshot** `.deb` packages:

[source,sh]
----
cuppa -D --dbg \
  --toolchain-archive=https://github.com/cppalliance/clang/releases/download/profiles-2026-08-07-27/clang-profiles-linux-x86_64.tar.gz

cuppa -D --dbg \
  --toolchain-archive=https://deb.debian.org/debian/pool/main/g/gcc-snapshot/gcc-snapshot_20260725-1_amd64.deb
----

What happens:

* **Family detection:** basename tokens `clang` / `gcc` when present; otherwise cuppa lists archive members (or peeks a `.deb` `data.tar.*`) for `bin/clang{plus}{plus}` / `bin/g{plus}{plus}`; extension is only a last resort (`.deb` → gcc, other → clang). Ambiguous URL downloads land under `downloads_root/toolchains/_staging/` until the family is known, then move to `toolchains/{clang,gcc}/`.
* **Clang** installs: cached under `downloads_root/toolchains/clang/<qualifier>/`, extracted under `dependencies_root/toolchains/clang/<qualifier>/`, probed for `bin/clang{plus}{plus}`, registered as `clang\{major}_\{sanitised_tag}` (for example `clang24_profiles_2026_08_07_27`).
* **GCC** installs: cached under `downloads_root/toolchains/gcc/<qualifier>/`, extracted with `ar` + `data.tar.*` for `.deb` (or normal unpack for tarballs), probed for nested `bin/g{plus}{plus}`, registered as `gcc\{major}_\{sanitised_stem}` (for example `gcc16_gcc_snapshot_20260725_1_amd64`).
* Names avoid colliding with distro `clang24` / `gcc15`.
* If you omit `--toolchains=`, toolchains prepared in **this** session are selected automatically.
* `--offline` requires the archive (or extract) to be present already.
* Large HTTP fetches show **transfer progress** at INFO (percent, ASCII bar, bytes, rate, ETA) on a rewriting line on the controlling terminal when available (so progress still works when the `cuppa` launcher pipes scons stdio), or as periodic lines in CI. The same reporter is used for location/Boost archive downloads. Extracting a large toolchain `.deb` logs start/elapsed and shows the same progress shape while unpacking `data.tar*`.

Debian package index: https://packages.debian.org/sid/gcc-snapshot — pool files live under `pool/main/g/gcc-snapshot/` on any Debian mirror.

On later runs you do not need to pass `--toolchain-archive=` again.
Cuppa scans `dependencies_root/toolchains/{clang,gcc}/*/`, registers each install that still has a usable driver, and skips a derived name that is already in the pre-registered toolchain list.
Select cached toolchains by name (or wildcard):

[source,sh]
----
cuppa -D --dbg --test --toolchains=clang24_profiles_2026_08_07_27,gcc16_gcc_snapshot_*
----

Cached discovery only makes toolchains *available*; it does not auto-select them.
Auto-select still applies only when you pass `--toolchain-archive=` / `--clang-root=` / `--gcc-root=` in the current session and omit `--toolchains=`.

=== External prefixes (`--clang-root=` / `--gcc-root=`)

For an install cuppa did not download (for example a hand-extracted snapshot tree):

[source,sh]
----
cuppa -D --dbg --clang-root=/path/to/clang/install
cuppa -D --dbg --gcc-root=/path/to/gcc/prefix
----

Cuppa probes `bin/clang{plus}{plus}` or `bin/g{plus}{plus}`, registers `clang\{major}_local_\{hash}` or `gcc\{major}_local_\{hash}`, and **persists a small registration** under `dependencies_root/toolchains/{clang,gcc}/local_…/` (`cuppa-toolchain.json` pointing at the external prefix). Later sessions discover that registration and reuse the short name without re-passing `--*-root=`.

Force-wipe of an external registration removes the **link under cuppa storage**, not the external prefix itself.
Owned archive extracts (downloaded by cuppa) are removed fully on force-wipe.

Use `--clang-stdlib=libstdc{plus}{plus}` (the Linux default) with slim Profiles Release tarballs that do not ship libc{plus}{plus}.

After a successful session that prepared an archive or root, cuppa logs the shorthand reuse flag near the end of the output, for example `--toolchains=gcc16_gcc_snapshot_20260725_1_amd64`.

[#fetched-toolchain-storage]
=== Listing and clearing toolchain archives

Toolchain installs appear under `--list-dependencies` / `--list-downloads` as storage type **toolchain** (`toolchains/<family>/<qualifier>/`), not as a mistaken top-level source archive named `toolchains`.
The list-dependencies **leaf label** is the Cuppa session name (`gcc17_gcc_snapshot_…`), aligned with
`--toolchains=` / `--list-toolchains`. For a compiler-oriented inventory (including PATH drivers),
prefer xref:toolchains.adoc#list-toolchains[`--list-toolchains`].

Which management flags apply:

* `--list-dependencies` / `--list-downloads` — yes. When you pass `--toolchains=…` (or auto-select via archive/root flags), that extract or registration is marked **referenced** / `in use`. Other cached installs stay unreferenced. Verbose LOCATION shows `[D]` when the matching archive still exists under `downloads_root/toolchains/…`.
* `--force-wipe-dependencies=[toolchain]clang/profiles_*`,
  `--force-wipe-dependencies=[toolchain]gcc/gcc_snapshot_*`, or the session name
  (`[toolchain]clang24_profiles_…` / `[toolchain]gcc16_…`) — yes.
* `--force-wipe-unreferenced-dependencies` — yes for installs that are not the active selection.
* `--remove-dependencies` / `--purge-dependencies` / `--wipe-dependencies` (and the `*-all-*` forms) — no; those only target **project-used** dependency names from the current selection (`default_dependencies` / `BuildWith`), not compiler installs.

Design notes: `design/archive/toolchains-as-dependencies.md`.

[#c-language-level]
== {cpp} language level

Each toolchain picks a high-compliance default dialect for its compiler version
(see xref:toolchains/gcc.adoc[GCC], xref:toolchains/clang.adoc[Clang], and
xref:toolchains/msvc.adoc[MSVC]): the newest `-std=` / `-std:` Cuppa supports for
that tool, with language features that dialect already enables. Cuppa does **not**
add redundant feature gates (for example GCC `-fconcepts` / `-fcoroutines`) once
the chosen dialect includes them. {cpp}20 modules remain opt-in via `--modules`
because they change the compile model rather than only unlocking syntax inside
the same dialect.

Verbose listing summarises that policy under `usable features:`:

* Older compilers where a feature is only behind a Cuppa `-f*` gate list the name
  directly (for example `concepts` on GCC 8–9).
* Newer compilers use dialect-inclusive shorthand (`all c{plus}{plus}2a, coroutines`,
  `all c{plus}{plus}2c`).
* When Cuppa can enable modules for the tool, append `modules (experimental)`
  (still requires `--modules` to turn on).

Override globally with `--stdcpp=…` or per env with `env.StdCpp('c{plus}{plus}20')`.

When you omit `--stdcpp` / `StdCpp`, Cuppa’s default is effectively **`c{plus}{plus}latest`**:
each toolchain selects the newest `-std=` / `-std:` Cuppa supports for that compiler version
(preferring the working-draft name, such as `c{plus}{plus}2c` on modern GCC/Clang). You do not
need to pass `--stdcpp=c{plus}{plus}latest` to get that behaviour. MSVC is the exception among
the built-in families: its Cuppa default is `-std:c{plus}{plus}20` unless you override it (see
below).

Allowed `--stdcpp` / `StdCpp` choices:

[cols="1,4"]
|===
| Choice | Meaning

| `c{plus}{plus}latest`
| Explicit “newest the tool accepts” request. On MSVC this is `-std:c{plus}{plus}latest`.
  On GCC/Clang Cuppa passes `-std=c{plus}{plus}latest` when you ask for it; omitting
  `--stdcpp` already picks Cuppa’s highest known dialect for that tool, which is the usual
  practical equivalent.

| `c{plus}{plus}2c`
| Working-draft spelling for {cpp}26; Cuppa’s preferred default on modern GCC/Clang

| `c{plus}{plus}26`
| ISO {cpp}26 once the compiler treats that token as the frozen standard

| `c{plus}{plus}2b`
| Working-draft spelling for {cpp}23

| `c{plus}{plus}23`
| ISO {cpp}23 (on MSVC, Cuppa maps this to `-std:c{plus}{plus}latest` — see below)

| `c{plus}{plus}2a`
| Working-draft spelling for {cpp}20

| `c{plus}{plus}20`
| ISO {cpp}20 (MSVC Cuppa default)

| `c{plus}{plus}1z`
| Working-draft spelling for {cpp}17 on older GCC/Clang

| `c{plus}{plus}17`
| ISO {cpp}17

| `c{plus}{plus}1y`
| Working-draft spelling for {cpp}14 on older GCC/Clang

| `c{plus}{plus}14`
| ISO {cpp}14

| `c{plus}{plus}0x`
| Working-draft spelling for {cpp}11 on older GCC/Clang

| `c{plus}{plus}11`
| ISO {cpp}11

| `c{plus}{plus}03`
| ISO {cpp}03 (same core language as {cpp}98, with library and defect-report updates)

| `c{plus}{plus}98`
| ISO {cpp}98
|===

With `--modules`, cuppa raises the dialect to at least {cpp}20 when the dialect the build would
otherwise use is lower, and only for a compile that actually builds, declares, or imports a
module. The toolchain default counts towards that floor, so a compiler defaulting to `c{plus}{plus}2c`
keeps `c{plus}{plus}2c`; `--modules` never lowers a dialect. When you have asked for a lower dialect
explicitly (`--stdcpp=c{plus}{plus}17 --modules`), cuppa raises it to {cpp}20 and warns, because the
variant path still names the dialect you requested -- pass `--stdcpp=c{plus}{plus}20` or later to keep the
two consistent.

On MSVC, pre-{cpp}14 aliases map to `-std:c{plus}{plus}14` with a warning (MSVC has no matching `-std:` for those dialects).
`c{plus}{plus}23` / `c{plus}{plus}2b` map to `-std:c{plus}{plus}latest` (many MSVC toolsets ignore unknown `-std:c{plus}{plus}23`, which breaks `import std`).
Cuppa passes MSVC standard flags in *hyphen* form (`-std:c{plus}{plus}20`) so SCons on Windows does not treat `/std:…` as a filesystem path.

== Tips

* Prefer naming a family (`gcc`, `clang`, `vc`) in everyday builds; pin versions in CI for reproducibility.
* Coverage and test grids should run gcc and clang as separate invocations (or clearly separated report trees), not as one blended instrumentation set.
* Override defaults with `env.StdCpp`, `env.ReplaceFlags` / `RemoveFlags`, or `env.AppendUnique(CXXFLAGS=…)` after you understand the family baseline pages.
* When debugging toolchain detection, use `--verbosity=debug` and `--dump`.
* For per-flag explanations and upstream option links, open the family page for your compiler.
