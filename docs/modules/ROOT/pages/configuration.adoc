= Configuration
:description: Persisting CLI options in configure.conf and ~/.cuppaconfig

Cuppa can remember command-line choices so you do not re-type local paths and defaults every build.

== Configuration files

|===
| File | Scope

| `configure.conf` (beside the `sconstruct`, or path from `--use-conf`) | Project
| `~/.cuppaconfig` | Global (loaded first; project file overrides)
|===

Format is `key = value` lines; values are parsed with `ast.literal_eval`.

== Managing configuration

|===
| Option | Effect

| `--show-conf` | Print loaded settings
| `--save-conf` | Write current CLI options to the project conf
| `--update-conf` | Merge current CLI into the project conf
| `--remove-settings=a,b` | Drop listed keys from the project conf
| `--clear-conf` | Delete the project conf
| `--save-global-conf` / `--update-global-conf` / `--clear-global-conf` / `--remove-global-settings` | Same operations on `~/.cuppaconfig`
| `--use-conf=PATH` | Use an alternate project conf path
|===

Example -- save develop + offline as project defaults:

[source,sh]
----
cuppa -D --develop --offline --save-conf
----

Storage choices are worth saving this way too. A project that must keep everything it retrieves
inside its own directory can record that once rather than relying on everyone remembering the
flag:

[source,sh]
----
cuppa -D --storage-root=_cuppa --save-conf
----

Every later build in that project then resolves its dependencies and downloads roots under
`_cuppa`. See xref:build-layout.adoc[Build layout] for what those roots hold.

Conf-only operations skip a normal build when you are only saving or clearing settings.

You can also seed defaults in code:

[source,python]
----
cuppa.run(
    default_options = {
        'develop': True,
        'offline': True,
    },
)
----

Keys in `configure.conf` and in `default_options` use the same names as each flag's internal
option key (underscores, not dashes). Command-line flags still override saved or coded defaults
when you pass them explicitly.

=== HTML report source links without CI flags

Projects that publish Profiles or test HTML from CI often need ``remote`` link resolution and
extra host suffixes for self-hosted GitLab, GitHub Enterprise, or other corporately named git
hosts. You do not need to repeat those flags on every pipeline job if you record them once in the
project.

**Option A — commit `configure.conf` beside the `sconstruct`:**

[source,python]
----
reports_link_style = 'remote'
reports_gitlab_hosts = ['git.corp.example']
reports_github_hosts = ['github.corp.example']
reports_remote_provider_hints = True
----

Create or update that file once from the command line:

[source,sh]
----
cuppa -D --reports-link-style=remote \
  --reports-gitlab-hosts=git.corp.example \
  --save-conf
----

Then commit `configure.conf`. Later builds and CI jobs pick up the same settings with no extra
flags. Inspect loaded values with `--show-conf`.

**Option B — set defaults in the `sconstruct`:**

[source,python]
----
cuppa.run(
    default_options = {
        'reports_link_style': 'remote',
        'reports_gitlab_hosts': ['git.corp.example'],
    },
)
----

Use this when the project should always carry the policy in code rather than a separate conf
file. Profiles-only overrides use the key ``cxx_profiles_report_link_style`` the same way.

These settings are **session-wide** for HTML reports. They do not replace the host embedded in a
``location_dependency(..., location=...)`` URL; they tell cuppa which **provider blob URL shape**
to use when resolving ``remote`` links for a given hostname. See
xref:cli-reference.adoc#reports-link-style[HTML report source links] for the full flag list and
behaviour (mapped providers, unmapped partial links, and provider hint links).

=== {cpp} Profiles diagnostic cap without CI flags

Profiles inventory runs (``--cxx-profiles-report`` or ``env.CollateCxxProfilesIndex()``) imply
unlimited per-TU diagnostics on Clang/GCC unless you override them. For enforce-only builds that
are not generating a report, record unlimited diagnostics once:

[source,python]
----
cxx_disable_error_limit = True
----

Or set an explicit cap:

[source,python]
----
cxx_error_limit = 20
----

When inventory mode is active but you want the compiler default cap, pass
``--cxx-default-error-limit`` on the command line or set ``cxx_default_error_limit = True`` in
``configure.conf``. Keys match the internal option names (underscores). See
xref:cxx-profiles.adoc#violation-inventory-report-cxx-profiles-report[Violation inventory report]
and xref:cli-reference.adoc[CLI reference] for precedence.

== Environment variables

|===
| Variable | Use

| `GITLAB_REGISTRY_TOKEN` | Authenticate to a GitLab package registry
| `CI_JOB_TOKEN` | GitLab CI job token for registry access
| Per-package custom token | Via `--<name>-gitlab-custom-token` (option names a token-bearing setting)
| `PATH` / `PKG_CONFIG_PATH` | How much of your shell environment reaches build/test/run subprocesses depends on `--propagate-env`, `--propagate-path`, and `--merge-path` (see xref:cli-reference.adoc#environment-propagation[Environment propagation]). Host `PKG_CONFIG_PATH` is forwarded even when those flags are off.
| `CUPPA_CONSOLE_BACKGROUND` | `light` or `dark`. Tells cuppa which way to make text recede: reduced intensity on a dark console, grey on a light one. Set it when your console is light, because most terminals report nothing and reduced intensity applied to black text on white can look untouched. Where a terminal does set `COLORFGBG`, cuppa reads it, and this variable overrides it.
|===

The `cuppa` wrapper masks environment values whose names match `*TOKEN*` in build output.
