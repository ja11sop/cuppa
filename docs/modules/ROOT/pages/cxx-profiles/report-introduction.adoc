= Violation report — Introduction
:description: Generate cxx-profiles-index.html, offline regen, JSON export, and core report vocabulary

The **C++ Profiles violation report** is a read-only HTML and JSON inventory of Profiles
diagnostics captured during a cuppa build. It helps you triage rule violations before fixing
sources — it does not rewrite code.

This page is the starting point for the report feature: how to produce artefacts, regenerate
them offline, and read shared vocabulary. It is **not** the guide for the **Overview** tab on
`cxx-profiles-index.html` — that tab has its own page,
xref:cxx-profiles/report-overview.adoc[Overview tab].

Use xref:cxx-profiles/report.adoc[Violation report reading guide] as the index of tab-specific
guides (By-Rule, By-File, By-Build, By-Sconscript).

[#prerequisites]
== Prerequisites

Before generating a report you will need:

* xref:cxx-profiles.adoc#how-cuppa-enables[Profiles enabled] on a Profiles-capable Clang
  (`--cxx-profiles` and usually `--cxx-profiles-enforce=`)
* A build that compiles translation units under enforce — pair with
  `--cxx-disable-error-limit` when you need the compiler's full diagnostic list rather than its
  default cap (see xref:cxx-profiles.adoc#violation-inventory-report-cxx-profiles-report[Violation inventory report])
* `--cxx-profiles-report` on the same cuppa invocation (same section)

[#generating-during-build]
== Generating the report during a build

Pass `--cxx-profiles-report` together with `--cxx-profiles` or `--cxx-profiles-enforce=`. Cuppa
captures diagnostics while the build runs and writes output at `sconstruct_end` under
`<artifacts-root>/cxx-profiles/` (default `_artifacts/cxx-profiles/`). The construction `env`
exposes `artifacts_root` and `abs_artifacts_root` (see `--artifacts-root=` in
xref:cli-reference.adoc[CLI reference]).

[source,bash]
----
cuppa -D --dbg --toolchains=clang24_profiles_2026_08_07_27 \
  --cxx-profiles --cxx-profiles-enforce=std::init \
  --cxx-disable-error-limit --cxx-profiles-report
----

Optional flags that affect report shape (full list on xref:cxx-profiles.adoc[C++ Profiles]):

* `--cxx-profiles-report=` *path* — explicit report directory (or index file stem)
* `--cxx-profiles-report-root=` *dir* — rebase project-owned paths for display and links
* `--cxx-profiles-report-link-style=local|gitlab|github` — Profiles-only source link override
* `--cxx-profiles-report-context=full|rules-only|off` — Overview `context` in JSON/HTML
  (`full` default; `rules-only` omits tier 1/2 parsed-file denominators; `off` hides the
  Overview tab content)

When context capture is enabled, the session index opens on the **Overview** tab. Other tabs —
**Violations By-Rule**, **By-File**, **By-Build**, and **By-Sconscript** — are always present
when the inventory is non-empty.

[#artefacts]
== Report artefacts

After a successful report build you will find at least:

[cols="1,3"]
|===
| File / directory | Role

| `cxx-profiles-index.html`
| Session index — Overview (when enabled), roll-up tabs, links to scope pages

| `cxx-profiles-index.json`
| Versioned machine-readable session (`schema_version`, `summary`, `report`, optional
  `locations[]`, `context`) — see <<json-export>>

| `cxx-profiles--*.html`
| Per-scope detail pages — one `(sconscript, variant, toolchain)` compile row each

| `by-source/`
| Marked-up source pages with violation anchors (omitted when regen uses
  `--skip-source-pages`)
|===

Generated paths are appended to a project-local `.cuppa-reports` manifest (JSONL). Matching
entries are removed when you run `--clean` or `--remove-builds` with the same report destination
and link options on the command line.

[#offline-regeneration]
== Offline regeneration

Re-render HTML (and optionally rewrite JSON) **without recompiling** using the maintainer script
`scripts/regenerate_profiles_report.py`. This is the usual workflow for template or documentation
iteration, and for CI jobs that only publish HTML from a saved JSON artefact.

**Recommended — from saved JSON:**

[source,bash]
----
python -m scripts.regenerate_profiles_report \
  --from-json _artifacts/cxx-profiles/cxx-profiles-index.json
----

Omit `--sconstruct-dir` to take project paths and link style from JSON `metadata`. Source files
must exist on disk for `by-source/` pages unless `--skip-source-pages` is set.

[cols="1,3"]
|===
| Script flag | Meaning

| `--from-json`
| Positional argument is `cxx-profiles-index.json` (recommended)

| `--sconstruct-dir`
| Project root; default: cwd, or JSON metadata with `--from-json`

| `--artifacts-root`
| Same meaning as cuppa `--artifacts-root` (default `_artifacts`)

| `--report-dir`
| Output directory (default: `<artifacts-root>/cxx-profiles/`)

| `--link-style` / `--reports-link-style`
| Source links for this regen run

| `--cxx-profiles-report-link-style`
| Profiles-only override for this regen run

| `--skip-source-pages`
| Omit `by-source/` marked-up pages

| `--anonymized`
| Regenerate from anonymized JSON; implies `--skip-source-pages` and suppresses file/repo hrefs
  when `metadata.anonymized` is set (see <<sharing-anonymized>>)

| `--write-json`
| Rewrite `cxx-profiles-index.json` after re-render

| `--summary`
| Print capture replay summary (capture replay only; not used with `--from-json`)
|===

Capture replay (`capture.txt` without `--from-json`) remains legacy — parallel `tee` output can
mis-attribute scope. Prefer JSON when a live build already wrote `cxx-profiles-index.json`.

More detail: xref:cxx-profiles.adoc#violation-inventory-report-cxx-profiles-report[Violation inventory report]
on the C++ Profiles hub.

[#json-export]
== JSON export (agents and CI)

`cxx-profiles-index.json` is written alongside the HTML index on every live report build. It is
the stable contract for automation:

* **CI** — archive JSON from the build job; a follow-up job can run
  `regenerate_profiles_report --from-json` to publish HTML without a compiler
* **Agents and tooling** — read `summary`, `report.rollup`, `locations[]`, and `context`
  without parsing HTML; roll-up rows include structured `variant_display` objects for multi-build
  metrics (documented on xref:cxx-profiles/report-by-rule.adoc#json-fields[By-Rule JSON fields])
* **Sharing** — anonymize JSON for out-of-tree review; see <<sharing-anonymized>>

Top-level fields (non-exhaustive):

* `schema_version` — report JSON version
* `summary` — session union totals (`unique_violation_count`, `total_references`, …)
* `report` — serialised scopes, roll-up rules/files, `build_catalog`
* `locations[]` — flat diagnostic inventory when captured (enables full source regen)
* `context` — Overview metrics when context mode is not `off`
* `metadata` — `sconstruct_dir`, link style, enforce list, incomplete scopes; `anonymized` when
  produced by the anonymizer (see <<sharing-anonymized>>)

[#sharing-anonymized]
== Sharing an inventory (anonymized JSON)

When you need to share violation **counts and rule breakdowns** outside your organisation — issue
attachments, public fixtures, conference posts — ship **anonymized JSON plus summary HTML**, not
raw project paths or marked-up source.

An anonymized artefact **never** includes:

* `by-source/` marked-up source pages
* Links to files on disk (`file://`) or repository browse URLs
* Raw diagnostic `message` text (only `normalised_message` remains in `locations[]`)

Numeric Overview `context` fields (translation-unit counts, rule matrices, percentages) are
**unchanged** — only identifying paths and VCS metadata are rewritten.

=== Typical workflow

. Build with `--cxx-profiles-report` (or copy `cxx-profiles-index.json` from CI artefacts).
. Run the anonymizer on the saved JSON.
. Share the anonymized JSON (and optionally HTML regenerated from it).
. Recipients browse inventory tables without access to your tree.

[source,bash]
----
python -m scripts.anonymize_profiles_report \
  --in _artifacts/cxx-profiles/cxx-profiles-index.json \
  --out _artifacts/cxx-profiles/cxx-profiles-index.anonymized.json

python -m scripts.regenerate_profiles_report \
  --from-json _artifacts/cxx-profiles/cxx-profiles-index.anonymized.json \
  --anonymized
----

The regen step writes `cxx-profiles-index.html` with the same roll-up tabs as a live build, but
without source pages or file hrefs. When `metadata.anonymized` is set, output defaults to the
**same directory as the input JSON** (unless you pass `--report-dir=`).

=== What the anonymizer changes

[cols="1,3"]
|===
| Area | Anonymized output

| `metadata.sconstruct_dir`, `cxx_profiles_report_root`
| Generic placeholder root (for example `/home/user/project/widget`)

| `metadata.report_project`, `report_uri`, `report_branch`, `report_revision`
| Empty or placeholders — no hosting identity

| `metadata.link_style`
| `local` (HTML regen does not emit repo browse links)

| `metadata.anonymized`
| `true` (plus `anonymization_version`)

| Paths in `report`, `locations[]`, scope fields
| Same relative **shape** (include trees, `_build/…`, `_cuppa/_download/…`) with directory and
  file stems rewritten via a built-in synonym dictionary; variant tails such as `dbg/x86_64/cxx2c`
  are preserved

| `locations[].message`
| Removed (classifier `normalised_message` only)

| `location_key`
| Recomputed after path and message transforms
|===

Path segments stay **semi-readable** — plausible software tree names, not opaque serials such as
`file-001.hpp`. Multi-part stems (for example `common_types`) are rewritten using dictionary
synonyms (for example `core_elements`).

=== Anonymizer CLI

[source,bash]
----
python -m scripts.anonymize_profiles_report \
  --in _artifacts/cxx-profiles/cxx-profiles-index.json \
  --out _artifacts/cxx-profiles/cxx-profiles-index.anonymized.json
----

[cols="1,3"]
|===
| Flag | Meaning

| `--in`
| Input `cxx-profiles-index.json` from a real Profiles build

| `--out`
| Output anonymized JSON path

| `--mapping-out`
| Optional sidecar `{original_path: anonymized_path}` for internal review — **never** upload with
  the shared JSON

| `--dictionary`
| Optional synonym map JSON (default: built-in offline dictionary shipped with cuppa)

| `--force`
| Re-anonymize input that already has `metadata.anonymized`
|===

=== Regen flags for anonymized JSON

When JSON carries `metadata.anonymized: true`, regen automatically skips `by-source/` pages and
suppresses file hrefs. You can also pass `--anonymized` explicitly (implies
`--skip-source-pages`):

[cols="1,3"]
|===
| Flag | Meaning

| `--anonymized`
| Regenerate from anonymized JSON; omit source pages and file/repo hrefs

| `--skip-source-pages`
| Omit `by-source/` marked-up pages (also set automatically when `metadata.anonymized` is true)
|===

Rule documentation links (`doc_href` to published cuppa Profiles pages) are kept — they point at
public rule reference, not your project.

=== Limits (honest)

Anonymization targets **identity**, not statistical anonymity: directory depth, line numbers, and
counts may still resemble your codebase. Extend the built-in dictionary over time for unusual
domain jargon. Start sharing from **JSON**, not raw console capture — the anonymizer operates on
the saved report envelope only.

[#reading-the-index]
== Reading the index

`cxx-profiles-index.html` is organised as tabs. Each tab has a dedicated Antora page at a
similar level of detail:

[cols="1,3"]
|===
| Tab | Guide

| **Overview**
| xref:cxx-profiles/report-overview.adoc[Overview tab] — summary cards, build inventory load,
  rule concentration, profile matrices (when context capture is enabled)

| **Violations By-Rule**
| xref:cxx-profiles/report-by-rule.adoc[By-Rule tab] — session roll-up by rule

| **Violations By-File**
| xref:cxx-profiles/report-by-file.adoc[By-File tab] — session roll-up by file

| **Violations By-Build**
| xref:cxx-profiles/report-by-build.adoc[By-Build tab] — one build inventory row at a time

| **Violations By-Sconscript**
| xref:cxx-profiles/report-by-sconscript.adoc[By-Sconscript tab] — scope index and detail pages
|===

Per-scope HTML pages use the same single-build table layout as **By-Build** detail (**Build
Refs**, no **Peak Refs**; **Profile** column when multiple profiles appear in one scope).

The sections below define vocabulary and reference metrics used on every tab.

[#profile]
== Profile

A **profile** is a named safety or style contract enforced on your {cpp} translation units —
for example `std::init` (initialization rules from link:https://wg21.link/P4222[P4222]). Cuppa
passes enforced designators through `--cxx-profiles-enforce=` (see
xref:cxx-profiles.adoc#how-cuppa-enables[How cuppa enables Profiles]).

The violation report groups every diagnostic under its **profile** name. Overview **Profile
matrices** list all documented rules for each enforced profile. Roll-up tables include a
**Profile** column when a view spans more than one profile (for example By-Build detail and
per-scope pages).

[#rule]
== Rule

A **rule** is one check inside a profile, identified by `rule_id` (for example
`static_runtime_init`, `ref_to_uninit`). Rules appear in the report as `profile::rule_id` and
link to cuppa rule documentation when available.

Session totals count **distinct rules** — how many `(profile, rule_id)` pairs fired at least once
after unioning builds. Rule rows on By-Rule tables, Overview **Rule concentration**, and profile
matrices are all keyed by rule.

[#violation]
== Violation

A **violation** is one distinct issue site in the codebase, not one printed diagnostic line.

Cuppa assigns each captured diagnostic a **violation identity**:

[source]
----
(sconscript, file, line, column, profile, rule_id)
----

* The same rule on the same line at **different columns** counts as separate violations.
* The same site in **dbg** and **rel** counts as **one** violation in session union totals
  (identity ignores variant).
* **Violations** columns and the index headline use this union count.

A single violation can produce **many diagnostics** during compilation (templates, instantiation
paths, repeated analyser passes). Those repetitions feed **references**, below — they do not
multiply the violation count unless they represent genuinely distinct sites (different line or
column).

[mermaid]
----
flowchart TB
  subgraph session [Session inventory]
    P[Profile e.g. std::init]
    R[Rule e.g. static_runtime_init]
    V[Violation identity<br/>sconscript + file + line + column]
    D[Captured diagnostics<br/>many lines, many refs]
  end
  P --> R
  R --> V
  V --> D
----

[#references]
== References

Each time the analyser attributes another code path to the same diagnostic site, the report
records a **reference**. References measure *how much diagnostic material* the compiler emitted,
not how many distinct bugs exist.

You will see reference totals at several grains:

* Per **scope** (one sconscript + variant compile)
* Per **rule** or **file** row on roll-up tables
* Per **session** in the index headline and Overview cards

Reference **types** (next section) answer different questions from the same underlying captures.

[#reference-metrics]
== Reference types — Union Refs, Peak Refs, and Build Refs

[cols="1,1,3"]
|===
| Column name | JSON field | Meaning

| **Union Refs**
| `summary.total_references` / `rollup.total_references`
| For each violation **identity**, take the **maximum** ref count among individual captured
diagnostic rows, then **sum** across identities. Aligns with **Violations** union semantics.
Multi-build index cells show a **bold total**, then `= common` plus `+N build_id` deltas.
Overview prose may say *union references*; table columns use **Union Refs**.

| **Peak Refs**
| (derived in roll-ups)
| For each identity, take the **maximum per-build inventory total** for that identity (max of dbg
summed refs vs rel summed refs), then sum. Index By-Rule / By-File parent rows and Overview
**Rule concentration** / **Profile matrices** include this column so you can correlate with
By-Rule without opening every row. Often equals **Union Refs**; diverges when one build stacks
multiple diagnostic rows at the same identity.

| **Build Refs**
| `rollup.raw_total_references` (session aggregate)
| **Summed** reference counts from compiling **one build** — no cross-build deduplication.
Overview xref:cxx-profiles/report-overview.adoc#build-breakdown[Build inventory load] variant
rows, **Violating Files** / **Violated Rules** `[ index:refs ]` lists, and per-scope compile
totals use this grain.
|===

[mermaid]
----
flowchart LR
  subgraph identities [Violation identities]
    I1[Identity A]
    I2[Identity B]
  end
  subgraph refs [Union Refs]
    I1 --> R1[max row peak per identity]
    I2 --> R2[max row peak per identity]
    R1 --> SU[Sum = Union Refs]
    R2 --> SU
  end
  subgraph peak [Peak Refs — multi-build]
    I1 --> P1[max per-build sum]
    I2 --> P2[max per-build sum]
    P1 --> SP[Sum = Peak Refs]
    P2 --> SP
  end
  subgraph build [Build Refs — one compile]
    I1 --> B1[sum all rows in build]
    I2 --> B2[sum all rows in build]
    B1 --> SB[Sum = Build Refs]
    B2 --> SB
  end
----

**Violating Files** and **Violated Rules** lists show **Build Refs** at `(index, refs)` grain
(`[ 21:2950 ]`), not **Union Refs**. Use the subtable **Build Refs** column (or the scope-page
equivalent) to decode those lists — not the **Union Refs** column.

[#multi-build-notation]
== Multi-build roll-up notation (index tabs)

When the session catalog lists more than one build (`dbg1`, `rel1`, …), metric cells on the
index **Violations By-Rule** and **By-File** tabs show:

[source]
----
748
= 420
+156 rel1
+172 rel2
----

* The **bold first line** is the session union total (common + all deltas).
* **`= common`** is the strict intersection across every catalog build.
* **`+N build_id`** lines are build-exclusive or build-differing contributions.

Single-build sessions and per-scope detail pages show **plain numbers** instead (see
<<scope-metrics>>).

**Build Refs** list partitions use `total =` + `+N build_id` when builds differ; they never show
a non-zero common **and** non-zero deltas for the same indexed entry.

[#scope-metrics]
== Single-build scope pages and the By-Sconscript index tab

Each **Violations By-Sconscript** row (and each linked detail page) covers **one build**
inventory row: one `sconscript`, one variant/toolchain combination.

=== Index By-Sconscript table

[cols="1,3"]
|===
| Column | Meaning

| **Rules**
| Distinct `(profile, rule_id)` pairs observed in this scope.

| **Violations**
| Distinct violation identities in this scope (union count within the scope).

| **Union Refs**
| **Union Refs** summed across rules in this scope.

| **Build Refs**
| Compile inventory total for this scope (sum of every captured diagnostic ref in this build).
Equals **Peak Refs** for the same scope — both are single-build totals. Shown alongside **Union Refs**
so you can compare union vs compile load and correlate with Overview **Build inventory load**.

| **Profiles** / **Rule Violations**
| Summary lists (unchanged).
|===

=== Scope detail pages (By-Rule / By-File tabs)

Scope detail tables omit the index **Peak Refs** column — **Build Refs** already carries the
single-build compile total. Subtables show **Violations**, **Union Refs**, and **Build Refs** only.
One tab pair covers all profiles; **Profile** is a column on the main tables (same layout as
xref:cxx-profiles/report-by-build.adoc[Violations By-Build] detail).

=== When Union Refs differs from Build Refs in one scope

**Union Refs** can be **lower** when several captured diagnostics share one union identity (same line,
column, and rule, but different normalised messages in the capture dedupe key). **Union Refs** uses the
row peak per identity; **Build Refs** sums every captured row. When each identity comes from at
most one diagnostic row, **Union Refs** and **Build Refs** match.
