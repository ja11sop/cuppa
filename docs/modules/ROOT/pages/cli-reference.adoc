= CLI reference
:description: How Cuppa and SCons command-line options compose

Cuppa presents one command line for selecting a build, running actions, inspecting state, and
maintaining local storage. It extends SCons rather than replacing its parser, so a typical
invocation has four kinds of input:

[source,sh]
----
cuppa [SCons options] [Cuppa options] [VARIABLES] [TARGETS]
----

SCons parses one combined option stream: its built-in options control graph traversal and
execution, while options registered by Cuppa add variants, toolchains, dependencies, reports, and
maintenance actions. Construction variables and target names select project-defined behaviour.
The bracketed groups above describe ownership, not separate parser namespaces; options can be
interleaved.

You can invoke an SConstruct file that imports `cuppa` using either `scons` or `cuppa`.
The `cuppa` entry point is `scons` plus a small wrapper: it appends `--cuppa-mode` as a session
marker, intercepts stdout and stderr to mask environment values whose names contain `TOKEN`,
injects `-i` when a Profiles inventory run needs it, and may restrict CPU affinity when
`--parallel` is set.

Calling `scons` directly against the same project still builds the same graph. It does **not**
install that intercept. Passing `--cuppa-mode` to `scons` yourself only sets the marker; it is
not a substitute for running `cuppa`. Cuppa's own logger still redacts secrets registered
in-process (GitLab package tokens, expanded location URLs) either way.

TIP: Prefer `cuppa` over `scons` in CI and anywhere registry or job tokens may appear in
command lines or logs. See xref:cli/output-and-environment.adoc#cuppa-mode[The `cuppa` wrapper
and `--cuppa-mode`].

== Discovering the available options

Cuppa registers options while the project's `SConstruct` loads. Dependencies and plugins can add
their own options, so the authoritative list is project-specific. Running `cuppa -h` or
`cuppa --help` outside a project tree, or from a nested directory without `-D`, shows only
SCons-native options.

Running the following command from anywhere in a Cuppa project tree will correctly load the project
and print its Cuppa options:

[source,sh]
----
cuppa -D -h
----

The `-D` option finds the top-level `SConstruct` and evaluates the project before `-h` prints its
registered help.

== Common use cases

These commands show the combinations used most often. Cuppa options compose: adding `--offline`
does not change the selected variant, and adding `-Q` changes presentation rather than what is
built.

[TIP]
====
In general you want be able to run Cuppa from anywhere in the project tree so it makes sense
to start all commands as:

[source,sh]
----
cuppa -D [Options] ...
----

In the examples that follow we use this convention.
====

[cols="3,4,3"]
|===
| Goal | Command | Why these options

| Build debug
| `cuppa -D --dbg`
| Find the project and select the debug variant

| Build release
| `cuppa -D --rel`
| Select the optimised release variant

| Build and run tests
| `cuppa -D --dbg --test`
| Build debug test targets, then execute them

| Measure coverage
| `cuppa -D --cov --test`
| Instrument the build and run the tests; `--cov` alone does not execute them

| Build a toolchain matrix
| `cuppa -D --dbg --toolchains=gcc,clang`
| Select more than one discovered toolchain

| Use local dependency copies
| `cuppa -D --dbg --develop --offline`
| Prefer configured develop paths without contacting remotes

| Preview work
| `cuppa -D --dbg -n`
| Construct the graph and print actions without executing them

| Reduce wrapper noise
| `cuppa -D --dbg -Q`
| Suppress SCons reading/building messages while retaining commands and Cuppa output

| Inspect storage
| `cuppa -D -Q --list-dependencies`
| Print dependency inventory instead of building
|===

== Everyday options

[cols="3,7"]
|===
| Option | Purpose

| `-D` | Find the top-level `SConstruct` and build its default targets
| `--dbg` / `--rel` / `--cov` | Select one or more build variants
| `--toolchains=LIST` | Select discovered toolchains by comma-separated name or wildcard
| `--test` / `--run` / `--benchmark` | Execute the corresponding targets after building
| `--scripts=LIST` | Limit which sconscripts contribute targets
| `--parallel` | Choose a hardware-sized SCons job count
| `--develop` | Prefer configured local dependency copies
| `--offline` | Avoid PyPI checks and remote location updates
| `-n` / `--no-exec` | Preview build or maintenance actions
| `-Q` | Suppress SCons progress messages without hiding build commands
|===

== Command output

Output comes from three layers: SCons reports graph progress and build actions, Cuppa reports
selection and structured status, and the invoked compiler, test, or process writes native output.
The controls are deliberately separate. For example, `-Q` quiets SCons without hiding compiler
commands, while `--minimal-output` filters Cuppa's processed diagnostics and
`--show-test-output` exposes test-process streams.

Use `--verbosity=exception` when an exception occurs while reading the project; use
`--verbosity=debug` when the selection or configuration leading to it is unclear. The detailed
output-mode and environment-propagation tables are on
xref:cli/output-and-environment.adoc[Output and environment].
