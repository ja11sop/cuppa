= CLI reference
:description: Cuppa command-line options grouped by concern

Cuppa registers options through SCons `AddOption`.
They appear when you run `cuppa` or `scons` against a project whose `sconstruct` calls `cuppa.run()`.
Standard SCons flags (`-D`, `-j`, `-c`, `-Q`, …) still apply.

== Everyday build control

|===
| Option | Description

| `--dbg` | Debug variant
| `--rel` | Release variant
| `--cov` | Coverage-instrumented variant (does *not* imply `--test`)
| `--test` / `--force-test` | Run test targets
| `--benchmark` / `--force-benchmark` | Run benchmark targets
| `--run` / `--force-run` | Run `Run()` targets
| `--toolchains=LIST` | Comma-separated toolchain names; supports fnmatch wildcards (`gcc*`, `clang21`)
| `--scripts=LIST` / `--projects=LIST` | Limit which sconscripts run
| `--parallel` | Parallel build (`-j` sized to the machine; `cuppa` may restrict CPU affinity)
| `--offline` | Skip PyPI version check and remote repository updates
| `--develop` | Prefer develop locations / develop package paths where configured
| `--stdcpp=STD` | Override C++ dialect (`c++98`, `c++03`, `c++0x`, `c++11`, `c++1y`, `c++14`, `c++1z`)
|===

== Output and diagnostics

|===
| Option | Description

| `--raw-output` | Disable cuppa output processing / colour
| `--standard-output` | Processed output without colour
| `--minimal-output` | Errors and warnings only
| `--ignore-duplicates` | Suppress repeated diagnostics
| `--verbosity=LEVEL` | `trace`, `debug`, `exception`, `info`, `warn`, `error`
| `--show-test-output` | Show test process stdout/stderr
| `--suppress-process-output` | Suppress subprocess stdout/stderr
| `--enable-thirdparty-logging` | Allow logs from third-party modules (for example pip)
| `--dump` | Dump the default environment and exit
|===

TIP: If cuppa fails early while reading sconscripts, re-run with `--verbosity=exception` or `--verbosity=debug`.

== Storage

|===
| Option | Default

| `--build-root` | `_build`
| `--download-root` | `_cuppa`
| `--cache-root` | `~/_cuppa/_cache`
| `--thirdparty=DIR` | Third-party directory hint
|===

== Location / develop workflow

|===
| Option | Description

| `--develop` | Use develop locations for location/package dependencies that define them
| `--list-develop` | Report the state of each configured develop working copy and exit (no network access)
| `--update-develop` | Fetch each git develop working copy and fast-forward those that are clean and behind; refuse under `--offline`
| `--location-default-branch` | Default branch name (default `master`) used in offline / relative location logic and by `--list-develop`
| `--location-match-current-branch` | For relative locations (`path@`), try the current branch
| `--location-explicit-default-branch` | Record the default branch explicitly in local checkouts
| `--location-match-branch` / `--location-match-tag` | Pin relative locations to a branch or tag
|===

Per-dependency location options follow the pattern `--<name>-location`, `--<name>-develop`, `--<name>-include`, `--<name>-sys-include`, `--<name>-branch-path`, and related flags.

See xref:dependencies.adoc#checking-your-develop-copies[Checking your develop copies] for what each state means and what `--update-develop` changes.

== Environment propagation

These flags control how much of your **shell** environment Cuppa passes into build, test, and run subprocesses (compilers, linkers, `BuildTest` / `Run` binaries, and similar).

|===
| Option | Description

| `--propagate-env` | Pass the full parent environment to subprocesses
| `--propagate-path` | Pass only the parent shell `PATH`
| `--merge-path` | Merge the parent shell `PATH` with Cuppa’s managed path (parent entries kept, Cuppa defaults included)
| `--use-shell` | Escape hatch: run coloured `SPAWN` subprocesses with `shell=True` (joins the argv list into one shell command). Prefer `working_dir` / `cwd=` / Python actions instead of multi-part shell strings such as `cd … && …`. See xref:methods.adoc#custom-commands-and-working-directories[Custom commands and working directories].
| `--decider=DECIDER` | SCons decider: `timestamp-newer`, `timestamp-match`, `MD5`, `MD5-timestamp` (default)
| `--runner=NAME` | Test runner (default `process`)
|===

**When to use them**

* Use `--propagate-path` or `--merge-path` when tools you need (for example a Homebrew Clang, or extra utilities) are on your shell `PATH` but not on Cuppa’s default path.
* Use `--propagate-env` when subprocesses need other shell variables as well (credentials, `PKG_CONFIG_PATH` customisations beyond what Cuppa already forwards, locale settings, and so on). Prefer the narrower path flags when only `PATH` matters.
* Without these flags, Cuppa still forwards host `PKG_CONFIG_PATH` when it is set, so system `.pc` discovery continues to work.

**What they are not for**

Dependencies that install their own shared libraries (for example the optional xref:dependencies.adoc#conan-2-consumer-optional[Conan consumer]) add library search paths for `--test` / `--run` themselves. You do **not** need `--propagate-env` for those packages to load at test time.

== Toolchain-specific

Clang:

* `--clang-stdlib={libstdc++,libc++}` (Linux default: `libstdc++`; non-default values tag `toolchain.name()` / `_build` paths, e.g. `clang21-libc++`)
* `--clang-disable-debug-for-auto`

Modules (opt-in; GCC 14+ / LLVM Clang 16+ / MSVC toolset 14.2+):

* `--modules` -- enable named modules, partitions, header units, and `import std` when the toolchain supports it (see xref:cxx-modules.adoc[C++ modules])

Boost (source dependency) includes `--boost-home`, `--boost-location`, `--boost-version`, `--boost-latest`, `--boost-build-always`, `--boost-verbose-build`, `--boost-verbose-config`, `--boost-patch-boost-test`.

== Packages

* `--publish-package` -- enable publish actions from `env.PublishPackage(...)`
* Per-package GitLab options: `--<name>-package-manager`, `--<name>-gitlab-registry`, `--<name>-gitlab-package`, `--<name>-gitlab-version`, `--<name>-gitlab-variant`, `--<name>-gitlab-develop`, `--<name>-gitlab-custom-token`, and related flags

See xref:packages.adoc[Packages].
