= Output and environment
:description: Console modes, diagnostics, subprocess environments, and test runners

A Cuppa command combines SCons progress, Cuppa status, native build commands, and child-process
output. These options let you change one layer without accidentally hiding another.

== Output modes

[cols="3,7"]
|===
| Option | Effect

| `--raw-output` | Disable Cuppa colour and do not install the spawn processor
| `--scons-output` | Do not install the spawn processor; keep Cuppa colour on logs and reports
| `--standard-output` | Keep Cuppa processing but disable colour
| `--minimal-output` | Reduce processed output to errors and warnings. Refused with `--raw-output` or `--scons-output`
| `--terse-output` | One `[ok]`, `[warn]`, or `[error]` line per tool run (`sconscript · variant · action file`). The command is reprinted only on warning or failure. `Progress(...)` lines stay; `-Q` still omits them. Refused with `--raw-output` or `--scons-output`
| `--show-test-cases` | With `--terse-output`, print every test case, not only the failures. Requires `--terse-output`
| `--ignore-duplicates` | Suppress repeated diagnostics recognised by the output processor
| `--show-test-output` | Show stdout and stderr from test processes
| `--suppress-process-output` | Suppress stdout and stderr from invoked processes
| `--enable-thirdparty-logging` | Allow logs from third-party modules such as pip
| `--dump` | Dump the default construction environment and exit
| `-Q` | Suppress SCons reading/building progress and Cuppa info logs. Warnings, commands, and console reports stay
| `-s` / `--silent` / `--quiet` | Also suppress warnings and SCons command lines. Console reports stay
|===

`-Q` is usually the right companion for `--list-*`: it removes SCons framing and info logs while
leaving the inventory intact. Mode banners such as `Running in LIST BUILDS mode` are console
reports, not info logs, so they stay. `--verbosity=LEVEL` overrides the level `-Q` or `-s` would
set. `--minimal-output` filters Cuppa's processed build messages and needs that processor, so it cannot be combined with `--raw-output` or `--scons-output`.

=== Terse output

`--terse-output` prints one status line per tool run. A clean run hides the command. A
warning or a non-zero exit prints the command and the processed output, then the status
line as the summary. It does not imply `--minimal-output`. Combined with it, a clean run
is still one line, and failure output is filtered to errors and warnings. It needs the
spawn processor, so it is refused with `--raw-output` or `--scons-output`.
`Progress(...)` lines stay, the same as without the flag. `-Q` still omits them,
because their description is only built at info verbosity. Under `--parallel` they
interleave with the status lines, as they do in any other parallel build.

A line is `[ok]`, `[warn]`, or `[error]`, then the sconscript, the build cell
(`toolchain_variant_arch_abi`), the action, and the file. The toolchain names its own
tools, so `gcc-ranlib-16` is `index`. A method may name its own action. Anything else is
`run`. A known SCons builder is named from its command: `tar`, `zip`, `text` (`Textfile`
and `Substfile`), `jar`, `javac`, `m4`, `lex`, `yacc`, `swig`, `rpcgen`, `rpm`, and the
TeX tools. `CopyAs` and `CopyTo` are `copy`. A `·` separates the action from the path. A
compile shows the source in the project tree, not the variant working copy, with the
directory subdued and the filename info and bold. `markdown` and `asciidoc` do the same.
A source outside the project is shown from `~` when it lives under the home directory,
otherwise as an absolute path. `copy`, `expand`, `render`, and a run that writes a file
show `source → dest`. The source is subdued, the destination directory is subdued, and
the destination filename is info and bold. `<working>/` and `<final>/` are this
variant's build locations. `<artifacts>/` is this variant's artefact location, either
its flat folder or a report directory that contains this variant and sconscript. Any
other path under the artefacts root is written as itself. Link, archive, and a program
run show the product name. The sconscript leaf is info-coloured and any leading path is
subdued. The action is plain, and in the build cell only the variant name (`dbg`, `rel`,
`cov`) is plain. Status tokens share a six-column field, so `[ok]` lines up with
`[pass]` and `[warn]`. `[error]`, `[xfail]`, and `[xpass]` run one column past it.

Python actions such as copy, SCSS, and CMake get the same line. SCons `Install file:`
and `Install directory:` lines are `copy`, and a clean install is only that status line.
An `Execute` inside another action is a `→` line (`copy`, `move`, `delete`, `mkdir`,
`chmod`, or `run`), and the caller's own description stays hidden. `Touch` stays hidden.
A tool the action starts, such as `asciidoctor`, is hidden on a clean run. If it prints
a warning or an error, or exits non-zero, that command and its output are printed, then
the status line. Other text the action prints while it runs still appears as it happens.
A status line that is not in the action total starts with `→`. That includes a test case
and a nested copy or move.

Before the first action, one subdued line gives the sconscript, variant, and action
totals. `[done]` then reports how many ran, how many were already up to date, the test
cases, and how many nested calls ran. It does not repeat the running tally. A no-op
build is `[done] build up to date`.

==== The running tally

An action line leads with this sconscript and variant's tally and the percent of the
whole build, ` 19/182 · 10%`. The subdued fraction is that one cell, so another
sconscript has its own total. The percent is plain-coloured. It is how many of this
run's actions have been accounted for, out of the actions that are going to run. Counts
reserve three digits and the percent two, and grow past 999 or 99. A `→` line is
indented so `[status]` stays in the same column. Actions SCons finds up to date are
included in both numbers. They are counted when SCons visits them, and that visit does
not print a line.

[NOTE]
====
The percent can differ between runs at the same point in the graph.

Every run starts the count at zero. An action that still has to run adds one when its
line prints. An action left built by a previous run adds its whole count when a worker
visits it, and that visit is silent.

With `--parallel`, several workers visit the graph at once. If most nodes are already
built, those workers are likely to reach built nodes early, and the percent jumps toward
that share before many new lines appear. If only a little is built, the first lines are
often compiles that still have to run, so the percent stays near zero until the walk
reaches the built nodes. The same compile can therefore show `0%` on one run and `66%`
on the next. The fraction in front of the percent (`19/182`) is only that sconscript and
variant. It is not a second reading of the percent.

The closing line uses the same ratio once the jobs have returned: `[interrupted] reached
57%: 1280/2245`.
====

==== Tests

A passing test binary is one `[pass]` badge, in the quieter green. The text is plain
black on a dark console, and the paper colour on a light console. The elapsed time
follows the action. `[fail]`, `[skip]`, `[xfail]`, and `[xpass]` use
that same quiet badge in their own colour. The test name is a badge, like the status. A
`test-case` uses the same text without the badge, and colours only the case leaf. A
multi-case binary ends with `11/12 cases, 40/52 assertions`. A run with no assertion
total says `no assertions`: a notice-yellow badge on the roll-up, with paper-coloured
text on a light console, and on a `test-case` a bold notice in that same dull yellow
rather than bright yellow. A failure prints each failing case (`test-case`) and its assertion text,
then the binary's `[fail]` badge. `--show-test-cases` also prints the cases that passed,
and requires `--terse-output`. `run` and `benchmark` stay `[ok]`.

==== Interrupting a build

Ctrl-C prints `interrupted — finishing in-flight actions...`. Tasks that have already
started are left to finish, and each of those lines leads with `...`. No new tasks are
started. When they have finished, one line says `finished in-flight actions`, then
`[interrupted] reached 57%: 1280/2245 · 80 ran · 1200 up to date`. The fraction is
actions completed against the actions that were going to run, including those already up
to date. `[interrupted]` is notice, not an error. A second Ctrl-C prints `aborted` and
stops what is still running, with no closing line. The per-target `Error -2` lines from
jobs that were still running are dropped. `-Q` does not hide this close: SCons omits its
own `scons: Build interrupted.` line in quiet mode, and Cuppa prints the close when the
jobs return.

`--scons-output` is the spawn half of `--raw-output`: SCons launches child processes, and Cuppa still colours logs and console reports. `--scons-output` together with `--standard-output` is the same outcome as `--raw-output` (no processor, no colour). Neither flag removes Cuppa progress nodes, and the `cuppa` wrapper still masks `*TOKEN*` values.

[[cuppa-mode]]
== The `cuppa` wrapper and `--cuppa-mode`

`cuppa` is not a second build engine. It launches `scons` with your arguments and appends
`--cuppa-mode`. The behaviours that differ from a bare `scons` invocation live in that wrapper,
not in a SCons option handler.

[cols="3,7"]
|===
| Behaviour | Where it runs

| Append `--cuppa-mode`
| Wrapper; session marker on the inner SCons process. Excluded from `--save-conf`. Not read to
  switch colour, verbosity, or masking inside `cuppa.run()`

| Mask `*TOKEN*` environment values on SCons stdout/stderr
| Wrapper pipe. Replaces each matching variable's *value* with its *name* so
  `CI_JOB_TOKEN`, `GITLAB_REGISTRY_TOKEN`, and similar secrets do not land in captured logs

| Inject `-i` / `--ignore-errors` for Profiles inventory
| Wrapper, when `--cxx-profiles-report` or `CollateCxxProfilesIndex()` implies an inventory run
  and you did not already pass `-i`

| Restrict CPU affinity with `--parallel`
| Wrapper (`psutil`), so a hardware-sized `-j` does not saturate the machine

| Colour, output modes, `register_secret` / logger masking
| Inside `cuppa.run()`, whether you started `cuppa` or `scons`
|===

The stdout intercept exists because SCons, compilers, `curl`, and similar tools can echo URLs or
headers that contain a token. Older GitLab CI versions in particular would place that text into
failure logs without redacting `CI_JOB_TOKEN`. Current GitLab and GitHub Actions mask *known*
secrets in the collected job log; that is complementary, not a replacement:

* The wrapper redacts at the process boundary, so local files, piped logs, and CI systems that
  do not mask a given variable still omit the value.
* Host masking only applies to secrets the CI system knows about. A custom `*TOKEN*` variable
  that is not marked masked still needs the wrapper.
* Only environment variable *names* matching `TOKEN` (case-sensitive) are intercepted this way.
  `PASSWORD`, `SECRET`, or `API_KEY` names are not. Empty values are ignored so they cannot
  rewrite every line.
* Direct `scons` still benefits from in-process `register_secret` (package headers, expanded
  location URLs) on Cuppa log lines and exception text. Native SCons and compiler output is
  not piped through `MaskSecrets` unless you used `cuppa`.

Use `cuppa` in CI and on shared machines whenever those tokens may appear. Use `scons` when you
are debugging the SCons process itself and need unfiltered child output. Do not persist
`--cuppa-mode`; it is a session flag, not project policy.

== Verbosity levels

`--verbosity=LEVEL` controls Cuppa's logger threshold. Each level includes the levels below it in
this table.

[cols="2,3,5"]
|===
| Level | Includes | Use

| `trace`
| Trace, debug, exception, info, warning, error
| Maximum internal detail, including source paths and line numbers

| `debug`
| Debug, exception, info, warning, error
| Option resolution, registration, and selection details

| `exception`
| Exception, info, warning, error
| Stack traces for caught exceptions without all debug traffic

| `info`
| Info, warning, error
| Normal default output

| `warn`
| Warning and error
| Problems only

| `error`
| Error and critical
| Failures only
|===

TIP: If Cuppa fails while reading sconscripts, re-run with `--verbosity=exception`. Use
`--verbosity=debug` when the option or registration path leading to the exception is unclear.

At the default `info` level, configure no longer prints the full available-toolchain name list
or each managed-archive registration line. Use
xref:toolchains.adoc#list-toolchains[`--list-toolchains`] for a structured inventory, and
`--verbosity=debug` when you need those registration details in the build log.

[[environment-propagation]]
== Environment propagation

These options control how much of the parent shell environment reaches compiler, linker, test, and
`Run()` child processes.

[cols="3,7"]
|===
| Option | Effect

| `--propagate-env` | Copy the complete parent environment, including `PATH`, into each variant environment
| `--propagate-path` | Copy only the parent shell's `PATH`
| `--merge-path` | Merge parent `PATH` entries with Cuppa's managed path
| `--inherit-process-env` | At each test or `Run()` spawn, merge the current `os.environ`; `env['ENV']` wins on clashes
| `--use-shell` | Run coloured `SPAWN` subprocesses with `shell=True`, joining the argument list into one shell command
|===

Use `--propagate-path` or `--merge-path` when a compiler or utility is available through the shell
but not Cuppa's managed path. Use `--propagate-env` only when subprocesses need additional values
such as credentials, locale settings, or custom package configuration.

`--propagate-env` copies the environment when a variant build environment is created. It does not
see values written to `os.environ` later in a sconscript. Prefer `export_for_subprocess()`, return
an environment dictionary from a `Run()` callable, or use the narrower `--inherit-process-env`
escape hatch.

Cuppa forwards host `PKG_CONFIG_PATH` when it is set even without these options. Dependencies that
install shared libraries, such as the optional
xref:dependencies/using/conan.adoc#conan-2-consumer-optional[Conan consumer], configure their own runtime
search paths; they do not require `--propagate-env`.

`--use-shell` is also an escape hatch. Prefer `working_dir`, `cwd=`, or Python actions over shell
strings such as `cd ... && ...`; see
xref:methods/custom-commands.adoc[Custom commands and working directories].

== Dependency deciders

Cuppa sets SCons' default decider to `MD5-timestamp`. Override it with `--decider=MODE`.

[cols="2,3,5"]
|===
| Mode | Basis | Trade-off

| `timestamp-newer`
| Whether a dependency is newer than its target
| Fastest and least precise; clock and restored-file timestamps matter

| `timestamp-match`
| Whether a dependency timestamp differs from the recorded value
| Detects timestamp changes even when the dependency is not newer

| `MD5`
| File content signature
| Precise content comparison with more hashing work

| `MD5-timestamp`
| Timestamp shortcut backed by content signatures
| Cuppa default; avoids hashing unchanged timestamps while retaining content checks when needed
|===

== Test runners

Select a runner with `--runner=NAME` or `cuppa.run(default_runner=...)`.

[cols="3,7"]
|===
| Runner | Behaviour

| `process` | Default; success follows the child process exit status
| `boost` | Understands Boost.Test output
| `patched_boost` | Boost.Test runner with Cuppa's command-line patches where enabled
|===

Toolchain modules advertise the runners they support. See
xref:testing-coverage.adoc#runners[Testing and coverage: runners] before selecting a non-default
runner.
