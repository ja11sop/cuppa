= Output and environment
:description: Console modes, diagnostics, subprocess environments, and test runners

A Cuppa command combines SCons progress, Cuppa status, native build commands, and child-process
output. These options let you change one layer without accidentally hiding another.

== Output controls

[cols="3,7"]
|===
| Option | Effect

| `--raw-output` | Disable Cuppa colour and do not install the spawn processor
| `--scons-output` | Do not install the spawn processor; keep Cuppa colour on logs and reports
| `--standard-output` | Keep Cuppa processing but disable colour
| `--minimal-output` | Reduce processed output to errors and warnings. Refused with `--raw-output` or `--scons-output`. Ignored with a warning when `--native-output` is set
| `--native-output` | Pass toolchain diagnostic lines through with the tool's own colour. Not a third transcript: works with `--normal-output` or `--terse-output`. Adds toolchain colour flags (GCC `-fdiagnostics-color=always`, Clang `-fcolor-diagnostics`, MSVC `/diagnostics:caret`) and skips Cuppa re-colouring. Cuppa still counts errors and warnings for terse status. Refused with `--raw-output` or `--scons-output`
| `--normal-output` | The normal transcript: each command, with Cuppa's processed tool output. Overrides a terse choice saved in a configuration file. Do not combine with `--terse-output`
| `--terse-output` | One `[ok]`, `[warn]`, or `[error]` line per tool run (`sconscript · variant · action file`). The command is reprinted only on warning or failure. `[progress]` checkpoints replace `Progress(...)` and stay under `-Q`. Refused with `--raw-output` or `--scons-output`. Do not combine with `--normal-output`
| `--terse-output-show-actions` | With `--terse-output`, print the raw SCons action after each status line. For checking the action names. Requires `--terse-output`
| `--show-test-cases` | With `--terse-output`, print every test case, not only the failures. Requires `--terse-output`
| `--ignore-duplicates` | Suppress repeated diagnostics recognised by the output processor
| `--show-test-output` | Show stdout and stderr from test processes
| `--suppress-process-output` | Suppress stdout and stderr from invoked processes
| `--enable-thirdparty-logging` | Allow logs from third-party modules such as pip
| `--dump` | Dump the default construction environment and exit
| `-Q` | Suppress SCons reading/building progress and Cuppa multi-line info logs. Warnings, commands, and console reports stay. On a TTY, diverted info becomes one subdued `Working <spinner> <message>` status line so a long wait does not look hung
| `-s` / `--silent` / `--quiet` | Also suppress warnings and SCons command lines. Console reports stay. The same TTY status line applies when info would otherwise be hidden
|===

`-Q` is usually the right companion for `--list-*`: it removes SCons framing and multi-line info
logs while leaving the inventory intact. Mode banners such as `Running in LIST BUILDS mode` are
console reports, not info logs, so they stay. On an interactive TTY the quiet status line is
cleared before those reports, before warnings or errors, and before build transcript lines
(including `--terse-output`) — so the status line covers gaps between actions and never shares a
row with a real command. Width comes from the controlling terminal (not the `cuppa` launcher's
pipes). Pipelines and CI stay silent — no status spam. Git and download progress bars stay off
under quiet; they are not re-enabled by the status line. `--verbosity=LEVEL` overrides the level
`-Q` or `-s` would set and disables the status line. `--minimal-output` filters Cuppa's processed
build messages and needs that processor, so it cannot be combined with `--raw-output` or
`--scons-output`.

=== Native toolchain output

`--native-output` is a **modifier**, not a third transcript. It chooses how spawned compile and
link diagnostics are drawn under the normal or terse transcript: the toolchain's own lines pass
through (including ANSI colour and caret/note layout when the tool emits them). Cuppa still
classifies those lines (ANSI is stripped only for matching), prints the usual
`= Error N =` / `= Warning N =` banners, and closes with `=== Errors N ===` when the process
fails. It does not restyle Cuppa console reports or mute delegated CMake/Ninja child lines
under `--terse-output` (those are already passthrough text). Prefer it over `--raw-output`
when you want native diagnostics but still need Cuppa progress and status lines. Combining it
with `--minimal-output` keeps `--native-output` and ignores `--minimal-output` with a one-time
warning, because the Cuppa filter would hide non-classified native context lines.

=== Terse output

The transcript is one choice. The default is the normal transcript.
`--terse-output` sets `terse_output = True`, and `--normal-output` saves it as
`False`. Do not pass both; that is an options error. The command line replaces
a saved choice, so a project that has saved terse output can still be
diagnosed with `--normal-output`.
`--show-test-cases` and `--terse-output-show-actions` apply only while the
transcript is terse. A saved copy of either is ignored on a normal run.
Passing either on the command line of a normal run is an error.

`--terse-output` prints one status line per tool run. A clean run hides the command. A
warning or a non-zero exit prints the command and the processed output, then the status
line as the summary. It does not imply `--minimal-output`. Combined with it, a clean run
is still one line, and failure output is filtered to errors and warnings. It needs the
spawn processor, so it is refused with `--raw-output` or `--scons-output`.
`Progress(...)` lines are replaced by a `[progress]` checkpoint when a sconstruct,
sconscript, or variant begins or ends. The scope word is subdued. The percent is the
whole build. `[progress]` is info and bold. Status lines are indented so `[ok]` starts
in the same column. That indent is one space while the cell tally is three digits.
Past 999 the tally is wider, and the progress line takes the extra column instead.
On a sconscript checkpoint the leaf and the directory before it are info, and anything
above that is subdued, so `test/sconscript` is all info and
`test/reference_data/margin_specs/sconscript` mutes `test/reference_data/`. A variant
checkpoint uses that directory rule, and the cell is coloured as on an action line:
subdued, with `dbg`, `rel`, and `cov` left plain. The sconstruct path is always
`~/...` when the file is under the home directory, including when it sits inside the
project. Other paths stay project-relative. `begin` and `end` are bold in the plain ink,
the same as an action. On a dark console that ink is bold white, not the info blue that
bold alone becomes. A middot separates them from the summary. The summary is subdued
apart from the numbers.
A sconstruct line carries the build totals (`40 sconscripts ·
1 variant · 1800/2244 actions`). Before that first begin line, actions SCons already
considers up to date are counted, so the percent includes them. A sconscript line counts
that script's variants and actions. A variant line counts that cell only. Those lines stay
under `-Q`. Without
`--terse-output`, `Progress(...)` is unchanged, and `-Q` still omits it. Under
`--parallel` the checkpoints interleave with the status lines.

A line is `[ok]`, `[warn]`, or `[error]`, then the sconscript, the build cell
(`toolchain_variant_arch_abi`), the action, and the file. The toolchain names its own
tools, so `gcc-ranlib-16` is `index`. A method may name its own action. Anything else is
`run`. A known SCons builder is named from its command: `tar`, `zip`, `text` (`Textfile`
and `Substfile`), `jar`, `javac`, `m4`, `lex`, `yacc`, `swig`, `rpcgen`, `rpm`, and the
TeX tools. `CopyAs` and `CopyTo` are `copy`. A `·` separates the action from the path. The **file** cell follows the action class:

* **Transform** (`compile`, `compile-*`, `markdown`, `asciidoc`): `source → product`.
  The source is the project-tree path (or `~/...` under the home directory), not the
  variant working copy. The product uses `<working>/` when it lives in that cell.
* **Transfer** (`copy`, `move`, `expand`, `render`, and a run that writes a file):
  `source → dest`. Staging a `.a` with `cp` is `copy`, never `archive`.
* **Aggregate** (`link`, `link-shared`, `archive`, `package`, ...): the located
  product (`<final>/management`, or `_build/<fmt>/<variant>/final/libfmt.a` for a
  dependency archive). `index` uses the same path as the archive. Unmapped
  products stay a basename. `run` / `test` / `benchmark` use the same located
  program (`<final>/management`) so a test lines up with the `link` that built
  it. A redirected run stays `program → output`. `test-case` uses the same located
  program prefix (`<final>/management/case`) with the case leaf in the status colour.
* **Delegated** (`cmake-configure`, `cmake-build`, `cmake-install`, `b2`): a short
  summary such as `-B _build/...`, not a stamp name like `cmake.build.complete`.

Colour for both ends of an arrow matches transfer colouring: directories subdued,
filenames info and bold, `→` subdued. `<working>/` and `<final>/` are this variant's
build locations. `<artefacts>/` is this variant's artefact location, either its flat
folder or a report directory that contains this variant and sconscript. Any other path
under the artefacts root is written as itself. Authors may register further tokens
(Boost extract is `<boost>/`). `sconstruct 0% [prepare] ... · resolve · N declared dependencies`
opens SCons reading; maps and `[update]` / `[clone]` / `[collect]` / `[download]`
print live underneath. `[ready]` closes with resolved totals. Those maps
are not repeated on sconstruct begin. Read maps name a kind (`root`,
`repository`, `archive`, `package`). The read summary counts those kinds
(`N dependencies · R repositories · P packages · A archives`). When traveling-manifest
packages join the maps, that becomes
`N dependencies (D declared, T transitive) · ...`. Those extra maps append
`· transitive` (info colour); declared maps stay unmarked.
Package identity is `name/version`; `<packages>` is
the extract dir for this cell and prints on variant begin as
`<dependencies>/gcc16_rel_x86_64_cxx2c` (package tool variant, which may be
`rel` while the project cell is `dbg`). Each later `[progress] ... · begin` prints
location maps for that scope. They lead with `→ [location]` (bold muted grey, not notice yellow, not
bold plain action ink, not the info+bold `[progress]` badge) and repeat sconscript · variant so `--parallel` can split them from the
begin line. Variant maps are `<packages>` (when a package extract exists),
`<variant>`, `<working>`, `<final>`, and `<artefacts>`
(`<working>` / `<final>` paths substitute `<variant>` for the tool-variant
directory). Boost and other extract trees nest under `<dependencies>` when they
sit in that root. GitLab package extracts nest under `<packages>`
(`<packages>/<boost_package>/...`) using the registration `_name`. The path uses the
same colour roles as the progress path: sconscript leaf info, `dbg` / `rel` /
`cov` plain, last component info+bold. Root and package maps
(`~/_cuppa/_download`, `abseil-cpp/20250814.2`) paint every path segment
and the slashes between them info+bold. A nested parent token on the value
(`<dependencies>/gcc16_rel_x86_64_cxx2c`) stays subdued. The sconscript leaf is info-coloured and
any leading path is subdued. The action is bold in the plain ink. On a dark console that
is bold white, so it does not turn info-blue or compete with the filename. In the build
cell only the variant name (`dbg`, `rel`, `cov`) is plain. Status tokens share a
six-column field, so `[ok]` lines up with `[pass]` and `[warn]`. `[error]`, `[xfail]`,
and `[xpass]` run one column past it.
`--terse-output-show-actions` appends the raw SCons action, subdued, after the status
line. It is off unless you are checking a name, and it requires `--terse-output`.

==== Delegated builders

A long foreign graph (CMake/Ninja, Boost `b2`) is announced before its child lines:

[source]
----
delegate     0% [launch] gcc16_dbg_x86_64_cxx2c · cmake-build · -B _build/x --parallel 1
             → [1/75] Building CXX object ...
   2/  8 ·  25% [done]  gcc16_dbg_x86_64_cxx2c · cmake-build · -B _build/x --parallel 1
----

`delegate` is the scope word (a handoff, not a sconstruct/variant checkpoint).
`[launch]` marks the commence. Fields after the badge mirror the counted close line
(`sconscript · variant · action · summary` when sconscript is present) so a long muted
wall can be reattached under `--parallel`. A clean close uses `[done]` (complement of
`[launch]`); ordinary unit actions still use `[ok]`. `[warn]` / `[error]` are unchanged.
Child lines use the same `→` indent as nested `Execute` / `test-case`, with subdued
text and no Cuppa status badge. The full argv stays hidden on a clean run and is
reprinted on failure. Prefer `env.Install` / `CopyFiles` / labelled `Command` for
staging copies so they stay ordinary `copy` transfers, not a delegated launch.

A tool that is built once for every variant (Boost bootstrap `build-b2`, the
toolchain `.jam`) may label itself `shared_across_variants` instead of the
triggering build cell. That is an author override on the node
(`label_terse_action(..., shared=True)`), not something Cuppa infers from
`Depends`. `shared` is plain; `_across_variants` is subdued. Bootstrap's file
cell is the extract product (`<boost>/b2`). Copying the engine binary there is
an uncounted nested `copy` (`→ ... · copy · <boost>/.../engine/b2 → <boost>/b2`)
and does not itself close the `[launch]` span.

A method names its own action. A compiler command is spelled from the tool, not from a
method label. Anything still unnamed is `run`.

[cols="2,1"]
|===
| Method or tool | Word

| `CreateVersion` | `version`
| `AsciidocToHtml` | `asciidoc`
| `MarkdownToHtml` | `markdown`
| `CMakeConfigure` | `cmake-configure`
| `CMakeBuild` | `cmake-build`
| `CMakeInstall` | `cmake-install`
| `Coverage` | `coverage`
| `CollateCoverageFiles` | `collate-coverage`
| `CollateCoverageIndex` | `coverage-index`
| `CopyFiles`, `CopyFilesAs`, `StageLocationDevelop`, `Copy`, `Install` | `copy`
| `DownloadExtract` | `download`
| `RemoveEmptyDirs` | `remove-empty`
| `ExpandTemplateFile` | `expand`
| `CompileScss` | `compile-scss`
| `RenderJinjaTemplate` | `render`
| `Test` | `test`
| `Benchmark` | `benchmark`
| `Run` | `run`, or `test` / `benchmark` when that is the variant action
| `RunAndRedirectToFile` | `run`
| `GenerateHtmlTestReport` | `test-report`
| `CollateTestReportIndex` | `test-index`
| `GenerateBittenReport` | `bitten-report`
| C++ profiles merge | `profiles`
| C++ module map | `module-map`
| package amend (`--amend-package-manifest`) | `amend`
| `Build`, `Compile`, link | `compile`, `link`, `link-shared`
| static library | `archive`, then `index`
| Boost bootstrap (`BuildB2`) | `build-b2`
| Boost `b2` library build | `b2`
| Boost toolset config | `boost-toolset`
| `PublishPackage` archive | `package`
| `PublishPackage` upload | `publish`
| `InstallPackage` | `install`
| `Textfile`, `Substfile` | `text`
| `tar` / `gtar` | `tar`
| `zip` | `zip`
| `jar`, `javac`, `javah`, `rmic` | the tool name
| `m4`, `lex` / `flex`, `yacc` / `bison`, `swig`, `rpcgen` | `m4`, `lex`, `yacc`, `swig`, `rpcgen`
| `rpm` / `rpmbuild` | `rpm`
| TeX tools (`latex`, `pdflatex`, `tex`, `pdftex`, `dvips`, `dvipdf`, `gs`, `bibtex`, `biber`, `makeindex`) | the tool name
| nested `Execute` of copy, move, delete, mkdir, chmod | that word
| anything else | `run`
|===

Python actions such as copy, SCSS, and CMake get the same line. SCons `Install file:`
and `Install directory:` lines are `copy`, and a clean install is only that status line.
An `Execute` inside another action is a `→` line (`copy`, `move`, `delete`, `mkdir`,
`chmod`, or `run`), and the caller's own description stays hidden. `Touch` stays hidden.
A tool the action starts, such as `asciidoctor`, is hidden on a clean run. If it prints
a warning or an error, or exits non-zero, that command and its output are printed, then
the status line. Other text the action prints while it runs still appears as it happens.
A status line that is not in the action total starts with `→`. That includes a test case
and a nested copy or move.

The sconstruct `begin` checkpoint carries the sconscript, variant, and action totals.
`[completed]` then reports how many ran, how many were already up to date, the test
cases, and how many nested calls ran. It does not repeat the running tally. A no-op
build is `[completed] build up to date`. A clean delegated close uses `[done]` instead
of `[ok]`; see <<_delegated_builders>>.

==== The running tally

An action line leads with this sconscript and variant's tally and the percent of the
whole build, ` 19/182 · 10%`. The subdued fraction is that one cell, so another
sconscript has its own total. The percent is plain-coloured. It is how many of this
run's actions have been accounted for, out of the actions that are going to run. Counts
reserve three digits and the percent three (so `100%` does not shift the status
column), and grow past 999. A `→` line is
indented so `[status]` stays in the same column. Actions SCons finds up to date are
included in both numbers. They are counted when SCons visits them, and that visit does
not print a line.

[NOTE]
====
The percent can differ between runs at the same point in the graph.

Every run starts the count at zero. An action that still has to run adds one when its
line prints. An action left built by a previous run adds its whole count when a worker
visits it, and that visit is silent.

With `--parallel`, several workers visit the graph at once. If most nodes are already
built, those workers are likely to reach built nodes early, and the percent jumps toward
that share before many new lines appear. If only a little is built, the first lines are
often compiles that still have to run, so the percent stays near zero until the walk
reaches the built nodes. The same compile can therefore show `0%` on one run and `66%`
on the next. The fraction in front of the percent (`19/182`) is only that sconscript and
variant. It is not a second reading of the percent.

The closing line uses the same ratio once the jobs have returned: `[interrupted] reached
57%: 1280/2245`.
====

==== Tests

A passing test binary is one `[pass]` badge, in the quieter green. The text is plain
black on a dark console, and the paper colour on a light console. The elapsed time
follows the action. `[fail]`, `[skip]`, `[xfail]`, and `[xpass]` use
that same quiet badge in their own colour. The test name is a badge, like the status. A
`test-case` uses the same text without the badge, and colours only the case leaf. A
multi-case binary ends with `11/12 cases, 40/52 assertions`. A run with no assertion
total says `no assertions`: a notice-yellow badge on the roll-up, with paper-coloured
text on a light console, and on a `test-case` a bold notice in that same dull yellow
rather than bright yellow. A failure prints each failing case (`test-case`) and its assertion text,
then the binary's `[fail]` badge. `--show-test-cases` also prints the cases that passed,
and requires `--terse-output`. `run` and `benchmark` stay `[ok]`.

==== Interrupting a build

Ctrl-C prints `interrupted — finishing in-flight actions...`. Tasks that have already
started are left to finish, and those lines look the same as any other status line. No
new tasks are started. When they have finished, one line says `finished in-flight actions`, then
`[interrupted] reached 57%: 1280/2245 · 80 ran · 1200 up to date`. The fraction is
actions completed against the actions that were going to run, including those already up
to date. `[interrupted]` is notice, not an error. A second Ctrl-C prints `aborted` and
stops what is still running, with no closing line. The per-target `Error -2` lines from
jobs that were still running are dropped. `-Q` does not hide this close: SCons omits its
own `scons: Build interrupted.` line in quiet mode, and Cuppa prints the close when the
jobs return.

`--scons-output` is the spawn half of `--raw-output`: SCons launches child processes, and Cuppa still colours logs and console reports. `--scons-output` together with `--standard-output` is the same outcome as `--raw-output` (no processor, no colour). Neither flag removes Cuppa progress nodes, and the `cuppa` wrapper still masks `*TOKEN*` values.

[[cuppa-mode]]
== The `cuppa` wrapper and `--cuppa-mode`

`cuppa` is not a second build engine. It launches `scons` with your arguments and appends
`--cuppa-mode`. The behaviours that differ from a bare `scons` invocation live in that wrapper,
not in a SCons option handler.

[cols="3,7"]
|===
| Behaviour | Where it runs

| Append `--cuppa-mode`
| Wrapper; session marker on the inner SCons process. Excluded from `--save-conf`. Not read to
  switch colour, verbosity, or masking inside `cuppa.run()`

| Mask `*TOKEN*` environment values on SCons stdout/stderr
| Wrapper pipe. Replaces each matching variable's *value* with its *name* so
  `CI_JOB_TOKEN`, `GITLAB_REGISTRY_TOKEN`, and similar secrets do not land in captured logs

| Inject `-i` / `--ignore-errors` for Profiles inventory
| Wrapper, when `--cxx-profiles-report` or `CollateCxxProfilesIndex()` implies an inventory run
  and you did not already pass `-i`

| Restrict CPU affinity with `--parallel`
| Wrapper (`psutil`), so a hardware-sized `-j` does not saturate the machine

| Colour, output modes, `register_secret` / logger masking
| Inside `cuppa.run()`, whether you started `cuppa` or `scons`
|===

The stdout intercept exists because SCons, compilers, `curl`, and similar tools can echo URLs or
headers that contain a token. Older GitLab CI versions in particular would place that text into
failure logs without redacting `CI_JOB_TOKEN`. Current GitLab and GitHub Actions mask *known*
secrets in the collected job log; that is complementary, not a replacement:

* The wrapper redacts at the process boundary, so local files, piped logs, and CI systems that
  do not mask a given variable still omit the value.
* Host masking only applies to secrets the CI system knows about. A custom `*TOKEN*` variable
  that is not marked masked still needs the wrapper.
* Only environment variable *names* matching `TOKEN` (case-sensitive) are intercepted this way.
  `PASSWORD`, `SECRET`, or `API_KEY` names are not. Empty values are ignored so they cannot
  rewrite every line.
* Direct `scons` still benefits from in-process `register_secret` (package headers, expanded
  location URLs) on Cuppa log lines and exception text. Native SCons and compiler output is
  not piped through `MaskSecrets` unless you used `cuppa`.

Use `cuppa` in CI and on shared machines whenever those tokens may appear. Use `scons` when you
are debugging the SCons process itself and need unfiltered child output. Do not persist
`--cuppa-mode`; it is a session flag, not project policy.

== Verbosity levels

`--verbosity=LEVEL` controls Cuppa's logger threshold. Each level includes the levels below it in
this table.

[cols="2,3,5"]
|===
| Level | Includes | Use

| `trace`
| Trace, debug, exception, info, warning, error
| Maximum internal detail, including source paths and line numbers

| `debug`
| Debug, exception, info, warning, error
| Option resolution, registration, and selection details

| `exception`
| Exception, info, warning, error
| Stack traces for caught exceptions without all debug traffic

| `info`
| Info, warning, error
| Normal default output

| `warn`
| Warning and error
| Problems only

| `error`
| Error and critical
| Failures only
|===

TIP: If Cuppa fails while reading sconscripts, re-run with `--verbosity=exception`. Use
`--verbosity=debug` when the option or registration path leading to the exception is unclear.

At the default `info` level, configure no longer prints the full available-toolchain name list
or each managed-archive registration line. Use
xref:toolchains.adoc#list-toolchains[`--list-toolchains`] for a structured inventory, and
`--verbosity=debug` when you need those registration details in the build log.

[[environment-propagation]]
== Environment propagation

These options control how much of the parent shell environment reaches compiler, linker, test, and
`Run()` child processes.

[cols="3,7"]
|===
| Option | Effect

| `--propagate-env` | Copy the complete parent environment, including `PATH`, into each variant environment
| `--propagate-path` | Copy only the parent shell's `PATH`
| `--merge-path` | Merge parent `PATH` entries with Cuppa's managed path
| `--inherit-process-env` | At each test or `Run()` spawn, merge the current `os.environ`; `env['ENV']` wins on clashes
| `--use-shell` | Run coloured `SPAWN` subprocesses with `shell=True`, joining the argument list into one shell command
|===

Use `--propagate-path` or `--merge-path` when a compiler or utility is available through the shell
but not Cuppa's managed path. Use `--propagate-env` only when subprocesses need additional values
such as credentials, locale settings, or custom package configuration.

`--propagate-env` copies the environment when a variant build environment is created. It does not
see values written to `os.environ` later in a sconscript. Prefer `export_for_subprocess()`, return
an environment dictionary from a `Run()` callable, or use the narrower `--inherit-process-env`
escape hatch.

Cuppa forwards host `PKG_CONFIG_PATH` when it is set even without these options. Dependencies that
install shared libraries, such as the optional
xref:dependencies/using/conan.adoc#conan-2-consumer-optional[Conan consumer], configure their own runtime
search paths; they do not require `--propagate-env`.

`--use-shell` is also an escape hatch. Prefer `working_dir`, `cwd=`, or Python actions over shell
strings such as `cd ... && ...`; see
xref:methods/custom-commands.adoc[Custom commands and working directories].

== Dependency deciders

Cuppa sets SCons' default decider to `MD5-timestamp`. Override it with `--decider=MODE`.

[cols="2,3,5"]
|===
| Mode | Basis | Trade-off

| `timestamp-newer`
| Whether a dependency is newer than its target
| Fastest and least precise; clock and restored-file timestamps matter

| `timestamp-match`
| Whether a dependency timestamp differs from the recorded value
| Detects timestamp changes even when the dependency is not newer

| `MD5`
| File content signature
| Precise content comparison with more hashing work

| `MD5-timestamp`
| Timestamp shortcut backed by content signatures
| Cuppa default; avoids hashing unchanged timestamps while retaining content checks when needed
|===

== Test runners

Select a runner with `--runner=NAME` or `cuppa.run(default_runner=...)`.

[cols="3,7"]
|===
| Runner | Behaviour

| `process` | Default; success follows the child process exit status
| `boost` | Understands Boost.Test output
| `patched_boost` | Boost.Test runner with Cuppa's command-line patches where enabled
|===

Toolchain modules advertise the runners they support. See
xref:testing-coverage.adoc#runners[Testing and coverage: runners] before selecting a non-default
runner.
