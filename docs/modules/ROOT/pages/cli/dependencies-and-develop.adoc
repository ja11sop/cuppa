= Dependencies and develop
:description: Develop working copies and dynamic dependency/package options

Dependency options come from two sources. Cuppa registers global develop/location policy, while
each dependency declared by the project can register options under its own name. Therefore this
page documents the patterns; `cuppa -D -h` shows the concrete names available in your project.

== Selecting develop copies

[cols="3,4"]
|===
| Option | Effect

| `--develop` | Prefer each dependency's configured local develop path
| `--offline` | Refuse remote updates; compatible with building existing develop copies
| `--location-default-branch=NAME` | Set the published default branch used by offline/relative logic (default `master`)
| `--location-base-branch=NAME` | Set the develop home branch used to create/reset feature branches; defaults to the published branch
| `--location-match-current-branch` | For relative locations ending in `@`, try the consumer project's current branch
| `--location-match-branch=NAME` | Match relative locations to the explicitly named branch
| `--location-match-tag=NAME` | Match relative locations to the explicitly named tag
| `--location-explicit-default-branch` | Record the resolved default branch explicitly in local checkouts
|===

Relative location syntax and fallback order are explained on
xref:dependencies/location.adoc[Location dependencies]. These options select revisions for a
build; the commands below maintain local working copies.

== Inspecting and maintaining develop copies

[cols="3,4"]
|===
| Option | Action

| `--list-develop` | Report branch, upstream, dirty, ahead/behind, diverged, and detached state without contacting remotes
| `--clone-develop` | Clone configured missing/empty develop paths, including submodules; refuse non-empty destinations and tag/revision pins. Package dependencies clone from `package_source` (declared, staged manifest, or `--<name>-<manager>-package-source=`)
| `--checkout-develop-branch=NAME` | Switch clean copies to `NAME`, creating it through the develop base when needed
| `--reset-develop-branch[=NAME]` | Return clean copies to a resolved branch, then fetch and fast-forward where safe
| `--update-develop` | Fetch and fast-forward clean copies that are behind; leave modified, ahead, diverged, or detached copies unchanged
|===

Clone, checkout, reset, and update refuse `--offline`. None of them stashes, hard-resets, deletes
feature branches, or overwrites dirty/unpushed work. SCons `-n` previews actions.

=== Checkout and reset branch values

[cols="2,3,5"]
|===
| Value | Used by | Resolves to

| `current`
| Checkout and reset
| The consumer project's current branch

| bare flag
| Reset
| `--location-base-branch`, or the published default when no base is configured

| `base`
| Reset
| Same target as a bare reset

| `default`
| Reset
| `--location-default-branch`

| any other `NAME`
| Checkout and reset
| The literal named branch
|===

See xref:dependencies/managing/develop.adoc#checking-your-develop-copies[Checking your develop copies] for
the state model and examples.

== Per-location dependency options

Each location dependency named `<name>` registers the following pattern.

[cols="3,7"]
|===
| Option | Meaning

| `--<name>-location=VALUE` | Repository, archive, or path to build against
| `--<name>-develop=PATH` | Local path selected when `--develop` is active
| `--<name>-branch-path=PATH` | Optional path-based branch component
| `--<name>-include=PATH` | Include subdirectory
| `--<name>-sys-include=PATH` | System-include subdirectory
| `--<name>-extra_sub_path=PATH` | Additional relative path used to locate the dependency
| `--<name>-source-path=PATH` | Source-file path within the dependency
| `--<name>-linktype=TYPE` | `static` (default) or `shared`
|===

The underscore in `extra_sub_path` is part of the registered CLI name. Consumer code and plugins
can register additional options; do not infer that this pattern is the complete output of
`cuppa -D -h`.

== Per-package options

Every package dependency registers `--<name>-package-manager=MANAGER`. A GitLab package dependency
also registers this family:

[cols="3,4"]
|===
| Option | Meaning

| `--<name>-gitlab-registry=URL` | Registry to use
| `--<name>-gitlab-package=NAME` | Package name in that registry
| `--<name>-gitlab-version=VERSION` | Package version
| `--<name>-gitlab-variant=VARIANT` | Published build variant
| `--<name>-gitlab-library-prefix=PREFIX` | Optional library prefix accepted when resolving libraries
| `--<name>-gitlab-pkg-config-dir=PATH` | Package directory containing pkg-config files
| `--<name>-gitlab-develop=PATH` | Local package path used in develop mode
| `--<name>-gitlab-custom-token=TOKEN` | Package-specific registry credential
|===

== Package lookup (all GitLab packages)

These flags apply to GitLab generic archives. Lookup overrides do not change published stems.
`--package-gitlab-os-identity` does: it selects the stem shape used at **publish** and as the
preferred **lookup** shape. A `404` on the preferred stem retries the other toolchain identity
and the other OS encoding unless fallback is off. See
xref:dependencies/gitlab.adoc#consume-overrides[GitLab lookup overrides].

[cols="3,4"]
|===
| Option | Meaning

| `--package-gitlab-os-override=ID` | OS segment for every GitLab package
| `--package-gitlab-os-override-<name>=ID` | OS segment for one named dependency; takes precedence over the project-wide override
| `--package-gitlab-toolchain-override-<name>=TOKEN` | Toolchain token for one named dependency (`gcc152` or `gcc15`)
| `--package-gitlab-identity-fallback=on\|off` | Dual-stem `404` retry (default `on`)
| `--package-gitlab-os-identity=include\|omit` | Include the OS id in the stem (default) or omit it
|===

Prefer `GITLAB_REGISTRY_TOKEN` or `CI_JOB_TOKEN` when one credential serves the registry. The
wrapper masks environment values whose names contain `TOKEN`, but credentials should never be
written to tracked configuration.

`--publish-package` enables actions declared through `env.PublishPackage(...)`. See
xref:packages.adoc[Publishing packages] for GitLab and Conan publishing; consuming packages is
covered by xref:dependencies/packages.adoc[Package dependencies].

`--amend-package-manifest` rewrites `cuppa-dependency.json` from the publisher kwargs,
retars from an existing stage or registry archive, and skips DownloadExtract / CMake
rebuild. Pair with `--publish-package` to upload. See
xref:packages.adoc#amend-package-manifest[Amending metadata without rebuilding].

`--build-and-publish-dependencies` builds and publishes GitLab package dependencies
(leaf-first) before the tip; requires `--publish-package`. Optional
`--publisher-root=` resolves trees when `package_source` is omitted. See
xref:packages.adoc#build-and-publish-dependencies[Cascading dependency publishes].

`--cascade-plan` reports the resolved cascade order and each dependency's publisher
tree, then stops without building or uploading. It requires
`--build-and-publish-dependencies`, but not `--publish-package`. Every unresolved
publisher tree is reported rather than only the first, and the run exits non-zero
when any remain. See xref:packages.adoc#cascade-plan[Checking the plan before anything uploads].

`--clone-publishers` lets cascade clone a publisher tree it cannot find locally from
that dependency's `package_source` URL, optionally pinned as `url@branch`, `url@tag`,
or `url@revision`. Clones land in `PATH/<name>` under `--publisher-root` when it is
set, otherwise in `<storage-root>/publishers/<name>`. Existing trees are always
preferred and are used as they stand — never switched, reset, or overwritten — and
cloning is unavailable with `--offline`. It is opt-in because cascade runs a build in
the tree it fetches. See xref:packages.adoc#clone-publishers[Fetching publisher trees
on demand].

`--develop` is related but not the same. Outside a cascade, a package dependency's
`develop=` names a built package prefix (the directory `include/` and `lib/` hang off),
and the build links against it directly. During a cascade, a `develop=` naming a
publisher source tree (a tree with an `sconstruct`) is the tree cascade publishes from,
ranked above `package_source` and `--publisher-root`; the build then consumes the
package that publish produced rather than swapping the source tree in as a prefix. See
xref:packages.adoc#cascade-develop[Publishing from a tree you are working in].

`--publish-modified-develop` lifts cascade's refusal to publish from a develop tree
holding work only this machine has: uncommitted changes, unpushed commits, or a branch
with no upstream. Without it, such a run stops before the first upload and names every
offending tree. A tree found under `--publisher-root` or cloned by `--clone-publishers`
is reported the same way but only warns, and the publish goes ahead.

== Built-in Boost options

Source Boost has a stable option family rather than a project-generated `<name>` prefix.

[cols="3,7"]
|===
| Option | Effect

| `--boost-version=VERSION` | Select a Boost version
| `--boost-latest` | Override a pin or force an online latest-version refresh
| `--boost-home=PATH` | Use a source home
| `--boost-location=VALUE` | Override the source location
| `--boost-build-always` | Re-run Boost.Build whenever a Boost library is requested
| `--boost-verbose-build` | Show Boost.Build command output
| `--boost-verbose-config` | Show Boost.Build configuration output
| `--boost-patched` | Select the `patched/` source tree instead of `clean/`
| `--boost-patch-boost-test` | Deprecated alias for `--boost-patched`
|===

Unpinned Boost already resolves the latest known version; `--boost-latest` is an explicit override
or refresh request. See xref:dependencies/builtins/boost.adoc[Boost] for source layout and build
behaviour.
