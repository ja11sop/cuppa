= C++ modules
:description: Experimental named modules, partitions, header units, and import std (GCC/Clang/MSVC)

Cuppa can build C++20 **named modules** (including interface / implementation partitions),
**header units** (GCC/Clang), and (with a capable toolchain) **`import std` / `import std.compat`**.

Supported platforms / floors:

* **Linux / macOS:** GCC 14+ or **LLVM** Clang 16+ (`import std`: GCC 15+; Clang 18+ with libc++)
* **macOS note:** Apple Clang (Xcode) is **not** modules-capable even when it reports a high major (e.g. `Apple clang version 21`). Use Homebrew `llvm` (or another upstream Clang) and ensure its `bin` precedes `/usr/bin` on `PATH`.
* **Windows:** MSVC toolset 14.29+ (VS 2019 16.10+ / VS 2022) for named modules; header units and `import std` not yet

Enablement is **opt-in** so existing projects are unchanged.
BMIs are per env / variant. Same-sconscript `BuildLib` / `Module` + `Build` share the registry.
Libraries also install a `modules/module-map.json` next to `final/` for cross-project reuse via
`env.ImportModules(...)` or `package_dependency` / `BuildWith` (see <<packaged-modules>>).

== Enable modules

[source,sh]
----
cuppa -D --dbg --modules --stdcpp=c++20 --toolchains=gcc
cuppa -D --dbg --modules --stdcpp=c++20 --toolchains=clang
cuppa -D --dbg --modules --stdcpp=c++20 --toolchains=vc   # Windows
----

`--modules` sets `env['modules']=True` for each variant env.
If the selected dialect is below C++20, cuppa raises it to `c++20`.
You can also call `env.Modules()` from a sconscript.
On an unsupported toolchain, `--modules` stops the build with a clear error (no silent fallback).

Unresolved `import` names after BMI pre-registration fail the build with `StopError`
(list the missing named / header imports). Declare `HeaderUnit` or include the interface
unit in the same `Build` / `Compile` call.

== Named modules

Interface units use `.cppm` / `.cxxm` / `.ccm` / `.ixx` (or a `.cpp` that contains `export module`).
Pass them to `Build` / `Compile` like any other source:

[source,python]
----
Import('env')
env.Build('app', [
    'math.cppm',  # export module math;  → math.cppm.o
    'math.cpp',   # module math;         → math.o
    'main.cpp',   # import math;
])
----

Or use the `Module` sugar (compiles the interface, registers the BMI, and links the
objects into a later `Build` in the same sconscript):

[source,python]
----
Import('env')
env.Module('math', interface='math.cppm', implementation=['math.cpp'])
env.Build('app', ['main.cpp'])  # import math;
----

Cuppa scans sources for `export module` / `module` / `import`, builds BMIs under
`_build/.../working/modules/`, and wires SCons `Depends` so BMI-producing units
compile before their consumers. BMI nodes are **pre-registered** for every unit in the
source list, so partitions may appear before or after the primary interface.

== Libraries with modules

`BuildLib` / `BuildStaticLib` / `BuildSharedLib` go through the same modules compile path.
A consumer in the **same** sconscript can import the library's named modules because they
share the env BMI registry:

[source,python]
----
Import('env')
env.BuildStaticLib('mathlib', ['math.cppm'])
env.AppendUnique(LIBPATH=[env['abs_final_dir']])
env.Build('app', ['main.cpp'], LIBS=['mathlib'])
----

Same pattern works with `BuildSharedLib`.

== Packaged modules (cross-project)

When `--modules` is enabled, `BuildLib` / `BuildStaticLib` / `BuildSharedLib` install named-module
BMIs under `final/modules/` and write `module-map.json`. Consumers in another project (or after
extracting a cuppa package) load that map:

[source,python]
----
Import('env')
env.ImportModules('/path/to/final/modules')   # or package_dir/modules after BuildWith
env.AppendUnique(LIBPATH=['/path/to/final'])
env.Build('app', ['main.cpp'], LIBS=['mathlib'])
----

`package_dependency` / GitLab `BuildWith` automatically calls `ImportModules` when
`{package_dir}/modules/module-map.json` is present. BMI extensions must match the consumer
toolchain (`.gcm` vs `.pcm` vs `.ifc`) — cross-toolchain BMI reuse is not supported.
`PublishPackage` copies `modules/` into the package archive alongside `include/` and `lib/`.

NOTE: Producer and consumer still need matching toolchain *family* for BMI format. Same-sconscript
use remains the simplest path; packaging is for shipping modular libraries.

== Implementation units

Keep declarations in the interface and definitions in a separate TU:

[source,cpp]
----
// math_decl.cppm
export module math_impl;
export int add(int a, int b);

// math_impl.cpp
module math_impl;
int add(int a, int b) { return a + b; }
----

[source,python]
----
env.Build('impl_app', ['math_decl.cppm', 'math_impl.cpp', 'apps/impl_main.cpp'])
----

== Interface partitions

Split a large interface across partition units and re-export them from the primary:

[source,cpp]
----
// geo/point.cppm
export module geo:point;
export struct Point { int x; int y; };
export int manhattan(Point p);

// geo/geo.cppm
export module geo;
export import :point;          // relative partition import
export int origin_distance(Point p);
----

[source,python]
----
env.Build('geo_app', [
    'geo/geo.cppm',      # order does not matter — BMIs are pre-registered
    'geo/point.cppm',
    'apps/geo_main.cpp', # import geo;
])
----

Relative imports (`import :point` / `export import :point`) are resolved against the
owning module's primary name (`geo:point`).

== Implementation partitions

Internal partitions are not exported to importers of the primary module.
A common pattern is: primary interface declares the API, an implementation
partition holds helpers, and an implementation unit wires them together:

[source,cpp]
----
// calc/calc.cppm
export module calc;
export int add(int a, int b);

// calc/core.cpp
module calc:core;              // implementation partition → its own BMI
int core_add(int a, int b);

// calc/calc.cpp
module calc;
import :core;
int add(int a, int b) { return core_add(a, b); }
----

[source,python]
----
env.Build('calc_app', [
    'calc/calc.cppm',   # → calc.cppm.o (extension kept in object stem)
    'calc/core.cpp',
    'calc/calc.cpp',    # → calc.o
    'apps/calc_main.cpp',
])
----

== Private module fragments

Hide implementation details inside the primary interface unit with `module :private;`:

[source,cpp]
----
export module secrets;
export int public_answer();
module :private;
static int hidden = 7;
int public_answer() { return hidden; }
----

[NOTE]
====
**Toolchain support:** Clang 16+ implements private module fragments.
GCC (through at least GCC 15) still reports `sorry, unimplemented: private module fragment`.
Cuppa scans and registers the module either way; prefer Clang when you need this feature.
====

== Re-exports and multi-module graphs

`export import` forwards another module's interface:

[source,cpp]
----
export module util;
export int answer();

export module appmod;
export import util;
export int use_util();
----

[source,python]
----
env.Build('reexport_app', ['appmod.cppm', 'util.cppm', 'apps/reexport_main.cpp'])
----

== Header units

Declare headers that should be imported as header units. Spelling must match the
`import` line (quoted path or angle brackets):

[source,python]
----
Import('env')
env.HeaderUnit('include/widget.hpp')
env.Build('tool', ['tool.cpp'])   # import "include/widget.hpp";

env.HeaderUnit('<span>')
env.Build('span_tool', ['span_tool.cpp'])  # import <span>;
----

Named modules and header units can be mixed in one binary — declare the header unit
first, then `Build` sources that `import` both.
Angle-bracket units are **explicit** (`HeaderUnit('<…>')`); cuppa does not auto-build a
BMI for every `import <std_header>`.

== `import std` / `std.compat`

When a scanned source contains `import std;` or `import std.compat;`, cuppa:

* Raises the dialect floor to **C++23** (if lower)
* Builds the standard library BMI once per env/variant under `modules/std.gcm` or `modules/std.pcm`
* Registers it as a named module for consumers

Requirements:

* `--modules`
* **GCC 15+** with `bits/std.cc` (and optionally `bits/std.compat.cc`)
* **Clang 18+** with **libc++** (`--clang-stdlib=libc++`) and installed module interfaces
  (typically `/usr/lib/llvm-<N>/share/libc++/v1/std.cppm`)

[source,python]
----
Import('env')
env.Build('std_app', ['apps/std_main.cpp'])  # import std;
----

[source,sh]
----
cuppa -D --dbg --modules --toolchains=gcc
cuppa -D --dbg --modules --toolchains=clang22 --clang-stdlib=libc++
----

== Artifact layout

----
_build/<toolchain>/<variant>/<arch>/<abi>/working/modules/
  math.pcm|gcm
  geo--point.pcm|gcm          # colon → -- in BMI filenames
  header--include--widget.hpp.pcm|gcm
  header--angle--span.pcm|gcm
    std.pcm|gcm|ifc
  std.compat.pcm|gcm|ifc
  module-mapper.txt           # GCC only
  (also installed under final/modules/ for libraries)
----

== Limits

* Linux / macOS: GCC 14+ / LLVM Clang 16+ (`import std`: GCC 15+ / Clang 18+ with libc++; Apple Clang unsupported)
* Windows: MSVC 14.29+ named modules; header units and `import std` not yet
* Lightweight line-oriented import scanner (macros that invent imports are unsupported)
* Header-unit spelling in `import "..."` / `import <…>` must match `HeaderUnit` (GCC/Clang)
* Private module fragments: Clang only (GCC unimplemented)
* Packaged BMIs are toolchain-family specific (`.gcm` / `.pcm` / `.ifc`)
* Experimental compiler support — expect toolchain-specific quirks
* `--modules` on an unsupported toolchain stops the build with a clear error
* Integration tests require a modules-capable compiler and **fail** if GCC/Clang is too old
