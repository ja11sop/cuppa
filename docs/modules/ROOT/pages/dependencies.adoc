= Dependencies
:description: Boost, Qt, Quince, location_dependency, and optional Conan 2 consumer

Dependencies encapsulate include paths, defines, library linkage, and optional download/build steps.

== Declaring dependencies

In `sconstruct`:

[source,python]
----
import cuppa

cuppa.run(
    default_dependencies = ['boost'],
    default_options = {
        'boost-location': '/opt/boost',
    },
)
----

Or per sconscript:

[source,python]
----
Import('env')
env.BuildWith('boost')
----

== Boost (source / Boost.Build)

The built-in `boost` dependency builds or uses a Boost tree via Boost.Build (`b2`).

Common options:

* `--boost-home` / `--boost-location`
* `--boost-version` / `--boost-latest`
* `--boost-build-always`, `--boost-verbose-build`, `--boost-verbose-config`
* `--boost-patch-boost-test`

In a sconscript:

[source,python]
----
env.BuildWith('boost').use_libs(['system', 'filesystem'])
# or the older env-method form:
env.AppendUnique(STATICLIBS=env.BoostStaticLibs(['system', 'filesystem']))
# or
env.AppendUnique(DYNAMICLIBS=env.BoostSharedLibs(['system']))
----

`use_libs([...])` matches the call shape used by registry packages such as
xref:packages.adoc[boost_package], so you can switch between source Boost and a prebuilt
package by changing only the `BuildWith` name. It builds (or reuses) static libraries via
`BoostStaticLibs` and appends them to `STATICLIBS`. Aliases such as `BoostStaticLib` /
`BoostStaticLibrary` also exist for compatibility.

Optional dependency convention: when a dependency offers linkable libraries, prefer exposing
`use_libs(libs, depends_on=[])` on the instance returned by `env.BuildWith(...)`. Package
dependencies already do this; location-only (header) dependencies typically omit it.

For *prebuilt* Boost from a GitLab registry, prefer xref:packages.adoc[boost_package] instead of compiling from source every time.

== Qt4 and Qt5

Dependencies `qt4` and `qt5` integrate SCons Qt tools for MOC/UIC/RCC-style workflows.
Enable via `default_dependencies = ['qt5']` (or `qt4`) when Qt is installed on the builder.

== Quince

The `quince` dependency (and related Quince backends such as PostgreSQL/SQLite helpers) pulls Quince as location dependencies for ORM-style C++ projects.

== Location-only (header) libraries

Create a lightweight dependency with `cuppa.location_dependency()` (also aliased as `header_library_dependency`):

[source,python]
----
import cuppa

MyHeaders = cuppa.location_dependency(
    'my_headers',
    location = 'https://example.com/my_headers/archive/main.zip',
    include_root = 'include',
)

cuppa.run(
    dependencies = [MyHeaders],
    default_dependencies = ['my_headers'],
)
----

Locations may be filesystem paths, archive URLs, or VCS URLs (for example `git+https://…@branch`).
Cuppa keeps checkouts and extracted archives under `--dependencies-root` and the downloaded
archives themselves under `--downloads-root`, both shared between projects by default. See
xref:build-layout.adoc[Build layout] for the defaults and for how to move them.

With `--develop`, location dependencies that define a develop path use the local tree instead of fetching.

Relative locations ending in `@` participate in `--location-match-*` branch/tag behaviour (see xref:cli-reference.adoc[CLI reference]).

[#which-listing]
== Which listing for which question

Cuppa has several read-only reports that answer different questions. `--develop` is a *build*
switch; `--list-develop` is a *report* about working copies. They are easy to mix up.

|===
| You want to know… | Use | Looks at

| What is under the shared dependencies root, and which trees this project would use | `--list-dependencies` (optional `--list-dependencies-scope`) | `--dependencies-root` (for example `~/.cuppa/dependencies` or a legacy `~/_cuppa/_download`)
| Branch, cleanliness, and ahead/behind of configured develop working copies | `--list-develop` | Develop paths from the sconstruct
| What is under `_build` | `--list-builds` | `--build-root`
|===

**Inspecting dependency storage** — omit `--develop`:

[source,shell]
----
cuppa -Q -D --list-dependencies
----

Resolve marks the tree this project would use (without develop) as `referenced`, and sibling
branches or other leftovers as `unreferenced`. That is the listing to use before reclaiming disk.

**Inspecting develop checkouts** — also omit `--develop` unless you want the banner to say it is
active; the table is the same either way:

[source,shell]
----
cuppa -Q -D --list-develop
----

**`--list-dependencies --develop` is uncommon.** Passing `--develop` makes resolve point at
working copies, so cache trees for those identities are no longer `in use`; the dependency name
row shows `develop` instead (the branches themselves stay unmarked). Use that only when you care
how the storage table would look under a develop resolve — not as the default storage listing,
and not instead of `--list-develop`.

[source,shell]
----
# Storage under a develop resolve (optional)
cuppa -Q -D --list-dependencies --develop
----

[#list-dependencies]
== Listing dependency trees

`--list-dependencies` walks the dependencies root and prints a hierarchical table: size,
last used, remark (`in use` / `N used` when more than one leaf is selected / `missing` /
`develop`), and dependency identity. Before the walk it prints `Collating dependency tree...`
(text and verbose only; omitted for JSON). When inventory sizes are missing or only sampled
estimates, it prints a short notice and upgrades those trees to exact sizes (the first run on a
large root can take a while; later runs reuse the cache). Pass `--exact-sizes` to force a full
remeasure of every tree. Rows are grouped referenced first then unreferenced,
then by type (location dependencies, gitlab packages, archives, …), then by short name or
registry name, with branch or version children underneath. On-disk paths are omitted by
default; pass `--list-format=verbose` to add a LOCATION column, or `--list-format=json` for a
machine-readable tree (plus flat `entries`). Default dependencies that are expected but absent
appear as `missing`. Referenced section roll-ups separate `dependencies in use`,
`missing dependencies` (when any expected trees are absent), and only then
`potentially stale dependencies` for other non-selected referenced leaves. It exits without
building (exit 0 even when some rows are missing). See
xref:integration/test-list-dependencies.adoc[`test_list_dependencies`] for the integration
scenario.

[source,shell]
----
cuppa -Q -D --list-dependencies
cuppa -Q -D --list-dependencies --list-dependencies-scope=referenced
cuppa -Q -D --list-dependencies --list-format=verbose
cuppa -Q -D --list-dependencies --list-format=json
cuppa -Q -D --list-dependencies --exact-sizes
----

`--list-dependencies-scope` selects which sections appear. It is independent of
`--list-format` (so you can combine `referenced` with `verbose` or `json`). Persist a
preference in `~/.cuppaconfig` or `configure.conf` as
`list_dependencies_scope = 'referenced'`.

|===
| Scope | Effect

| `all` (default)
| Referenced section, then unreferenced (current behaviour)

| `referenced`
| Only the referenced section (in use, missing, and other leaves under those identities).
  Footer: `N entries, X total, X referenced` (no unreferenced size)

| `unreferenced`
| Only leftover trees this project does not resolve
|===

Example shape (sizes and names vary; glyphs may be ASCII on some consoles). Every horizontal
rule — including the one between `referenced` and `unreferenced` — spans the full table width
(the same run of hyphen characters as the header and footer rules), not a short separator:

`SIZE` is right-aligned in a fixed eight-character field. Blank rows that carry only a tree
stem (`│`) keep the hanging lines continuous between siblings. Referenced trees open with a
`dependencies in use` roll-up when at least one leaf is selected; absent expected trees add a
`missing dependencies` / `N missing` summary (error-coloured like other missing rows).

Under `--list-format=verbose` a LOCATION column is added. What it shows depends on the type:

* *Location dependencies* — bare repository URL on the identity; `URL@branch` on each branch leaf.
* *GitLab packages* — empty on the identity; registry `…/package/version` on the version row;
  archive basename on each toolchain leaf.
* *Archives* (Boost source tarballs, GitHub release zips, and similar) — short name such as
  `boost` or `github.com/fmtlib/fmt` on the identity; version or tag on each child; download URL
  on the version leaf.

When a regenerating archive exists under the downloads root (`--downloads-root`, for example
`~/.cuppa/downloads` or a legacy `~/_cuppa/_cache`), LOCATION is prefixed with `[D]` on the
leaf that names that archive (HTTP/Boost extract rows, and GitLab toolchain archive basenames —
not the GitLab registry URL on the version row). A footer explains the mark in verbose mode
whenever such archives are present. If re-extracting a dependency fails, remove the corrupt
archive under downloads; deleting only the dependency tree is not enough.

The inventory under `<dependencies_root>/.cuppa-inventory/` records sizes (exact after listing
upgrades missing or sampled entries; resolve/build may still write samples until listing
upgrades them), optional
`remote_location` / `source_url` (configured or reconstructed remotes), and paths of known
download archives so later listings can show LOCATION and `[D]` without re-guessing. Listing
does not stamp `last_used`; that belongs to a real resolve or build.

[#remove-dependencies]
== Removing dependency trees

`--remove-dependencies=name1,name2` and `--remove-all-dependencies` delete trees under the
dependencies root for the named registry dependencies (or every default dependency), scoped to
the current toolchain / variant / location-match selection — the same options that decide where
cuppa writes. They exit without building. Downloads, develop working copies, and unreferenced
trees that are not named stay put; siblings for other toolchains or branches are reported as
left behind. SCons `-n` is a dry run.

Names are the keys this project uses: `default_dependencies` plus names registered from the
sconstruct’s `dependencies=[…]` list. Built-in factories that module scan always registers
(`boost`, `qt4`, …) are **not** removable unless the project names them that way. On-disk folder
names and listing short names are rejected. An unknown or unused name prints an error (rejected name error-coloured and emphasised) and a
ruled tree of dependencies that *can* be removed for the current selection (the in-use /
referenced picture from `--list-dependencies`, without unreferenced leftovers), after
`Collating dependency tree...`. See
xref:integration/test-remove-dependencies.adoc[`test_remove_dependencies`].

Source Boost (the `boost` dependency that builds with b2) stores headers and all toolchain
variant products inside one extract folder. When that dependency implements selection-scoped
`storage_clean` (Boost does), `--remove-dependencies=boost` deletes only the b2 **stage** and
matching Boost.Build toolset directories under `--build-dir` (`bin.<abi>`) for the current
toolchain / variant / arch selection — not the whole `bin.<abi>` tree. The extract root,
headers, and the `b2` binary stay in place so a later build does not need to re-download the
tarball. Other stage trees and other toolsets' intermediates under the same extract are reported
as left behind. Removal leaves use honest scopes: cuppa-precise for stage
(`clean/build.c++2c [clang211/debug/x86_64]`) and Boost.Build toolset **family** for bin
(`clean/bin.c++2c [clang-linux-21*/debug]` — major family ± patch dirs such as `clang-linux-21.1`,
not a cuppa minor like `clang211`). The identity SIZE is the full extract (same basis as
`--list-dependencies`); a muted `source assets` leaf shows non-product bytes that stay on disk,
and the freed-space summary reports the remaining archive size after product removal.
After a live product clean, cuppa refreshes that extract's inventory with an exact size, and the
verify hint is `cuppa -Q -D --list-dependencies` (listing upgrades any remaining missing or
estimated inventory sizes to exact on encounter).
Dependencies without `storage_clean` still remove their
whole owned tree under the dependencies root (for example GitLab `boost_package` removes the
selected package variant folder).

[source,shell]
----
cuppa -Q -D --remove-dependencies=boost_package
cuppa -Q -D --dbg --toolchains=gcc --remove-dependencies=boost_package
cuppa -Q -D --dbg --remove-dependencies=boost
cuppa -Q -D -n --remove-dependencies=widget
cuppa -Q -D --remove-all-dependencies
----

Example shape after a source Boost product clean (extract stays; sizes and toolset ids vary).
The identity SIZE is the full extract; `source assets` is the non-product remainder:

The identity row rolls up size (muted) and emphasises the dependency name and package version.
Selected leaves use a check (or ballot on failure) with the removal-notice colour; leftover
leaves stay muted with a `-` mark. Tree stems are subdued. `LAST USED` comes from inventory
resolve stamps when present, otherwise the tree's modification time. Passing multiple
toolchains (for example `--toolchains=gcc,clang`) removes each matching package variant.

With `--develop`, a develop working copy is never deleted; the report lists it under skipped
develop paths. Cached stems under the dependencies root may still be removed when selected.

== Checking your develop copies

`--develop` substitutes a working copy on disk for a retrieved dependency and says nothing about the state of that copy.
You can be building your feature branch against a dependency parked on someone else's spike branch, or against a copy that has not been pulled for months, and the only symptom is a compile error that makes no sense, a test that fails only on your machine, or one that passes only on your machine.
A develop path that does not exist is not checked at all today: the swap happens regardless and the failure surfaces much later as a missing include.

`--list-develop` reports what you are actually building against.
It runs after dependency registration and exits without building.
One row appears for every dependency that has a develop location configured, whether or not `--develop` is active, plus a count of those that have none:

[source,shell]
----
cuppa -Q -D --list-develop
----

Example output from a project with several develop locations (integration scenario
xref:integration/test-list-develop.adoc[`test_list_develop`]). Your branch names and paths will
differ; the shape of the report does not. Colour is described in the commentary below.

[source,text]
----

  ----------------------------------------------------------------------------------------------
  STATUS  DEPENDENCY  BRANCH          UPSTREAM            STATE                  PATH
  ----------------------------------------------------------------------------------------------
  warn    flange      spike_cache     origin/spike_cache  clean, 2 behind        ~/coding/flange
  ok      gadget      master          origin/master       clean                  ~/coding/gadget
  error   gizmo       -               -                   path does not exist    ~/coding/gizmo
  note    widget      feature_orders  -                   modified, no upstream  ~/coding/widget
  ----------------------------------------------------------------------------------------------

4 develop locations: 1 ok, 1 note, 1 warning, 1 error; 1 dependency not using develop
│
├── 1 error
│   │
│   └── gizmo

│           succeed

│
└── 1 note
    │
    └── widget
        ├── has no upstream branch, so ahead and behind cannot be answered
        └── has uncommitted changes on [feature_orders]

Of these, --update-develop would fast-forward 1 ([flange]) as of your last fetch; it fetches
first, so it may find more
----

The table is the inventory of what you are building against.
Every judgement then hangs from the summary line as one tree, grouped by severity with the worst first, so reading down the tree is reading a work list: what stops the build, then what needs a decision, then what is only worth knowing.
Each severity heading counts the dependencies beneath it, and each dependency is named once, with a gap on the stem above each name so that a dependency and its reasons read as one block.
A reason too long for the line is wrapped to the table's right edge and the stem is carried down through the wrapped lines, so the report keeps one right edge and the tree stays a tree.
Paths are shown the way the table shows them, with `..` segments resolved and your home directory written as `~`, because a develop location written relative to the `sconstruct` resolves to a path that is hard to recognise.
Where the console cannot encode box drawing characters the tree falls back to ASCII.
No remote is contacted, so the option remains available with `--offline`.

The last line appears when `--update-develop` would do something with what has just been observed, and names the copies it would fast-forward.
The decision behind it is the one `--update-develop` uses, so the line cannot offer an update that the option then declines to make.
It can understate, because `--update-develop` fetches before deciding and a fetch can find copies that are behind without your knowing yet, which is why the line says so.
Nothing is printed when every copy would be left alone.

On a colour console the `ok` and `note` rows recede, so the rows at full strength are exactly the ones wanting attention.
Receding is done by reduced intensity rather than by a background colour, so it works on either console, and a terminal that ignores it simply shows a plain table.
On a light console reduced intensity applied to black text can look untouched, so grey is used there instead; set `CUPPA_CONSOLE_BACKGROUND=light` to say which console you have, since most terminals do not report it (see xref:configuration.adoc#_environment_variables[Environment variables]).
In the judgement tree the severity, the dependency name, and the values are coloured and the prose is left plain, so a dependency or branch name can be found without reading every line.

The report is written to standard output rather than to the log, because it is the result you asked for rather than commentary on producing it.
That means a quieter build does not take pieces out of it, and `-Q` gives you the report on its own:

[source,shell]
----
cuppa -Q -D --list-develop
cuppa -Q -D --list-develop --raw-output > develop.txt
----

Severity appears in the `STATUS` column as well as in colour, so it survives `--raw-output` and can be searched for.
It is the value of the option:

|===
| Situation | Severity

| Branch equals the branch being built, or the default branch | ok
| Any other branch, or detached HEAD | warning
| Behind upstream, or diverged | warning
| Ahead or modified, on the branch being built | note — this is the intended workflow
| Ahead or modified, on the default branch | warning — local work that no other build will see
| No upstream tracking branch | note — ahead and behind cannot be answered
| Not a working copy | warning
| Path does not exist | error
|===

Local work is only benign where the rest of the world will find it.
Uncommitted or unpushed changes on a branch that matches the branch being built are the intended workflow: when that branch is pushed, `--location-match-current-branch` selects it and everyone else's build sees the same code.
The same changes sitting on the default branch are a trap.
Your build works, because `--develop` reads the working copy; every build that does not use `--develop` resolves the dependency to the published default branch and compiles something else.
The warning names the remedy: put the work on a branch named for the branch you are building, commit it, and push it.

The exit status is zero for a report, and non-zero when a develop path does not exist, because that build cannot succeed and a CI job should hear about it.

`--update-develop` answers the next question after `--list-develop` tells you a copy is behind.
It fetches each git working copy, then fast-forwards only those that are clean and strictly behind their upstream.
Everything else is skipped and reported with the reason: ahead, diverged, modified, detached, no upstream, not a working copy, or path missing.

[source,shell]
----
cuppa -D --update-develop
cuppa -D --update-develop -n
----

It prints the table before acting, then what it did to each copy, then the table again if anything moved, so the effect is visible rather than inferred.
It never stashes, resets, rewrites history, or switches branches.
A fast-forward of a clean tree discards nothing and leaves nothing to recover from.
`--offline` makes `--update-develop` an error rather than a silent no-op, because this is the one option in the family that needs the network.
`-n` / `--no-exec` shows the plan and changes nothing; because no fetch happens, the plan is judged as of your last fetch, and the report says so.
Updating several repositories is not atomic: a failure in one is reported, the rest continue, and the exit status is non-zero.

Subversion, Mercurial, and Bazaar copies appear in the `--list-develop` table with branch and revision from the existing SCM support; ahead, behind, and modified are reported as unknown, and `--update-develop` leaves them alone.

== Conan 2 consumer (optional)

Cuppa can consume Conan 2 packages through `cuppa.conan_deps` / `cuppa.conan_dependency` and apply them with `env.BuildWith`, using Conan's **SConsDeps** generator (`SConscript_conandeps` + `env.MergeFlags`).

Conan is **not** required to use Cuppa. Location dependencies and GitLab `package_dependency` remain separate supply chains. `--develop` does **not** substitute Conan packages with local develop paths.

[WARNING]
====
`conan install` executes recipe code from remotes (same class of risk as fetching location dependencies). Prefer pinned lockfiles and trusted remotes.
====

=== Declaring a Conan graph

Create a `conanfile.txt` (preferred for Cuppa-managed installs) that lists requires and includes `SConsDeps`:

[source,ini]
----
[requires]
fmt/12.1.0

[generators]
SConsDeps
VirtualRunEnv
----

Prefer fmt 12.0+ when targeting Clang 21+ with libc++ (older releases hit undeclared `malloc`/`free`; fmtlib/fmt#4477). Examples use **12.1.0**, the latest 12.x on ConanCenter at the time of writing.

Wire it into Cuppa:

[source,python]
----
import cuppa

Conan = cuppa.conan_deps( conanfile = 'conanfile.txt' )

cuppa.run(
    dependencies = [Conan],
    default_dependencies = ['conan'],
)
----

Cuppa maps the active toolchain and variant into Conan settings (`compiler`, `compiler.version`, `compiler.cppstd`, `compiler.libcxx`, `build_type`, `os`, `arch`), runs `conan install` once per settings fingerprint (cached under the dependencies root), and merges the resulting flags.

Cuppa also passes Conan conf `tools.build:compiler_executables` from the active toolchain's C/C++ drivers.
Without that, host settings can say `compiler=clang` while CMake still picks `g++` from `PATH` when building missing packages — a common failure on Linux CI images that ship both compilers.

Conan 2 still requires a **build** profile for the machine that runs `conan install` (even when Cuppa passes host settings with `-s`). On a fresh Conan home, create one once:

[source,sh]
----
conan profile detect
----

If `conan.lock` sits beside the conanfile, Cuppa passes it to `conan install`. Without a lockfile, dependency versions are not pinned.

=== Sugar for a single require

[source,python]
----
Fmt = cuppa.conan_dependency( 'fmt' )  # requires fmt/[*]
# or
Fmt = cuppa.conan_dependency( 'fmt', requires = ['fmt/12.1.0'] )
----

Prefer one `conan_deps(conanfile=...)` for multi-package graphs so Cuppa performs a single install.

=== Reusing a pre-run install (CI)

[source,python]
----
Conan = cuppa.conan_deps( generators_folder = '_conan' )
----

Point `generators_folder` at a directory that already contains `SConscript_conandeps` from a prior `conan install`. Cuppa skips install and only loads flags. This is the preferred pattern when CI (or a wrapper script) already ran Conan.

Integration coverage: xref:integration/test-conan.adoc[].
For publishing Cuppa-built libraries into Conan, see xref:packages.adoc#conan-package-publishing[Conan 2 publishing].

=== Dialect mapping note

Cuppa's default dialect folder (`cxx2c` / `-std=c++2c`) maps to Conan `compiler.cppstd=26`. Packages may rebuild from source when no binary exists for that setting; pin `--stdcpp=c++20` (or similar) if you need broader binary compatibility from ConanCenter.

=== Pip plugin packaging

You can ship a Conan-backed dependency as a pip package so consumers only `pip install` it and list the name in `default_dependencies`.
Cuppa discovers plugins through the `cuppa.dependency.plugins` entry point.

A Conan example lives at `examples/conan_fmt_plugin/` (registers `fmt` via `cuppa.conan_dependency`).
For the same `fmt` name built from a GitHub archive with `location_dependency` instead, see `examples/cuppa_fmt_plugin/`.
Walkthrough for both: xref:extending.adoc#pip-dependency-plugins[Extending cuppa — Pip dependency plugins].

=== Offline mode

With Cuppa `--offline`, Conan is invoked with `--no-remote`: the local Conan cache may be used, but remotes are not contacted. Missing packages fail clearly.

=== Runtime libraries for `--test` / `--run`

When Conan packages install shared libraries, linking alone is not enough for `--test` and `--run`: the dynamic loader must find those libraries when the binary starts.

Cuppa applies the package search paths from SConsDeps so test and run actions can locate them (`PATH` on Windows; `LD_LIBRARY_PATH` on Linux; `DYLD_LIBRARY_PATH` / `PATH` on macOS as appropriate).

You do **not** need `--propagate-env` (or the path-propagation flags) for this. Those flags control whether your *shell* environment is visible to subprocesses; Conan runtime paths are applied by the Conan dependency itself. See xref:cli-reference.adoc#environment-propagation[Environment propagation] when you instead need tools from your shell `PATH`.

=== Limitations (MVP)

* Host-only profiles (no cross build/host split yet)
* `tool_requires` / code generators (for example protobuf plugins) are out of scope
* Link flags use Conan's `LIBS` via `MergeFlags` (no extra `STATICLIBS` / `DYNAMICLIBS` routing yet)
* Prefer including `SConsDeps` in the conanfile (or rely on Cuppa's `-g SConsDeps`); a fully custom `generate()` must still produce `SConscript_conandeps`

Design notes: see the repository file `design/archive/conan-consumer-plan.md`.

== Custom dependencies

Implement a class with:

* `add_options(add_option)` (optional)
* `add_to_env(env, add_dependency)` classmethod that calls `add_dependency(name, factory)`
* instance `__call__(env, toolchain, variant)` to mutate the environment
* `name()` identifying the dependency

You can also subclass or wrap `location_dependency` / `package_dependency` factories.
Register extras via `cuppa.run(dependencies=[MyDep])` or setuptools entry point group `cuppa.dependency.plugins`.

See xref:extending.adoc[Extending cuppa].
