= Testing and coverage
:description: Test runners, BuildTest, and gcovr coverage reports

== Running tests

1. Declare tests with `env.BuildTest(target, sources)` (or `env.Test` on an existing binary).
2. Pass `--test` (or `--force-test`) on the command line.

[source,sh]
----
cuppa -D --dbg --test --show-test-output
----

Limit which sconscripts participate:

[source,sh]
----
cuppa -D --dbg --test --scripts=test/sconscript
----

Test and run actions use the same process environment Cuppa builds for the variant.
If a dependency provides shared libraries (for example xref:dependencies/conan.adoc#conan-2-consumer-optional[Conan]), those library search paths are applied automatically.
Separately, `--propagate-env` / `--propagate-path` / `--merge-path` control whether your *shell* environment is visible to those processes — see xref:cli/output-and-environment.adoc#environment-propagation[Environment propagation].

== Runners

Select with `--runner` or `cuppa.run(default_runner=...)`.

[cols="3,7"]
|===
| Runner | Behaviour

| `process` (default) | Success if the process exits cleanly
| `boost` | Boost.Test aware
| `patched_boost` | Boost.Test with cuppa's command-line patches where enabled
|===

Toolchain modules advertise which runners they support.

== Coverage workflow

Coverage needs the coverage *variant* and the test *action*:

[source,sh]
----
cuppa -D --cov --test
----

[mermaid]
....
flowchart TD
    A[BuildTest / Test targets] --> B["--test executes binaries"]
    B --> C[coverage data files]
    C --> D["env.Coverage() with gcovr"]
    D --> E[HTML / JSON per test]
    E --> F[CollateCoverageFiles / CollateCoverageIndex]
    F --> G["_artefacts/coverage index"]
....

[IMPORTANT]
====
`--cov` and `--test` are separate on purpose.

* `--cov` selects the coverage *variant* (instrumented compile/link). It does **not** run tests.
* `--test` (or `--force-test`) runs test actions so executed coverage data exists for
  `BuildTest` targets.

That split lets you build a large instrumented tree with `--parallel`, then collect coverage
serially:

[source,sh]
----
cuppa -D --cov --parallel --offline
cuppa -D --cov --test --offline
----

Typically the instrumented build dominates wall time; the serial test/coverage step is shorter.
Avoid `--parallel` on the `--cov --test` step — interleaved runner and gcov/gcovr output is hard
to follow, and parallel collection has historically been unreliable. See
https://github.com/ja11sop/cuppa/issues/236[#236] and xref:methods/coverage.adoc[Coverage methods].
====

Cuppa uses toolchain gcov support plus https://gcovr.com/[gcovr] to emit HTML/JSON beside the variant output (and optionally collated destinations).

`CollateCoverageIndex` also builds a *By source file* union (JSON across tests, annotated HTML under `by-source/`), so you can read coverage per source file rather than per test binary.

Useful methods:

* `env.Coverage(program, sources, include_patterns=…, exclude_dependencies=…)`
* `env.CollateCoverageFiles(sources, destination=…)`
* `env.CollateCoverageIndex(...)` -- master index across tests/toolchains

Consumer projects often write a master index under `_artefacts/coverage/` for browsing.

Compare like-for-like toolchains (do not mix gcc and clang instrumentation into one logical report).

== Benchmarks and run actions

* `--benchmark` / `--force-benchmark` with `BuildBenchmark` / `Benchmark`
* `--run` / `--force-run` with `env.Run(...)`

== HTML test reports

Plugin methods such as `GenerateHtmlTestReport` and `CollateTestReportIndex` produce browsable suite reports when tests run.
