= Concepts
:description: Methods, dependencies, profiles, variants, actions, and toolchains
:hash: #

Cuppa uses a small vocabulary so `sconstruct` / `sconscript` files stay declarative.

[#command-line]
== Command line and project description

SCons is a general dependency-management framework: you can pass construction variables
(`NAME=value`) and target names on the command line, and the DAG will honour them. That power is
useful, but it also makes every project invent its own everyday build ritual — target names,
variable knobs, and flag combinations that live in someone's shell history rather than in the
repository.

Cuppa sits on that foundation and deliberately narrows the everyday surface. It packages common
{cpp} build practice into a shared vocabulary (methods, dependencies, variants, toolchains,
actions) so experts encode the hard choices once, and everyone else selects from a small, named
toolbox instead of composing an open-ended flag matrix.

In a Cuppa project the *sconscript* describes *what* to build (`env.Build`, `env.BuildTest`,
`env.BuildWith`). The command line selects *how* and *which slice*: variants (`--dbg`), toolchains
(`--toolchains=`), actions (`--test`), and filters (`--scripts=`).

That split is intentional:

* *Reproducible workflows* — the same named Cuppa options appear in docs, CI, and local shells, so
  a coverage run or a dual-toolchain check is a shared recipe rather than a one-off target list.
* *Onboarding* — new contributors learn a short intent API and a handful of selectors; they do not
  need to reverse-engineer which SCons targets or construction variables the team happens to use.
* *Encapsulation* — toolchain defaults, dependency fetch/link rules, and output layout stay in
  reusable Python modules; everyday command lines stay short and transferable across projects.
* *Escape hatch when needed* — SCons `VARIABLES` and bare `TARGETS` still work because Cuppa does
  not replace the parser. Prefer them for diagnosis or rare custom graphs, not as the normal way
  to express product builds.

See xref:cli-reference.adoc[CLI reference] for the full option map, and
xref:methods.adoc[Methods] for the intent APIs used in sconscripts.

[#sconscript-discovery]
== Sconscript discovery and sharing

Cuppa **discovers** `sconscript` files under the launch directory (folder-and-below) and
invokes each once per active toolchain/variant. That discovery is the right default for most
projects and does not require SCons `Export` / `Import`.

A common multi-file layout keeps library (or other product) targets in a root `sconscript`
and puts tests or applications in a nested script such as `test/sconscript` or
`apps/sconscript`. That split mirrors how many CMake trees use `add_subdirectory`: one
place builds the reusable products, another consumes them for `BuildTest` / programs.
Folder-and-below discovery finds both scripts automatically; sharing library nodes (or
other values) between them is a **separate** concern from discovery.

When one discovered script needs a value another published, use Cuppa's preferred API:

[source,python]
----
# sconscript (libraries)
Import('env')
libs = env.Build( 'mylib', ['mylib.cpp'] )
env.ExportShared( 'mylibs', libs )

# test/sconscript
Import('env')
libs = env.ImportShared( 'mylibs' )
env.BuildTest( 'unit', ['test.cpp'], LIBS=libs )
----

Cuppa scans discovered scripts for `Export` / `Import` and `ExportShared` /
`ImportShared`, builds a small dependency graph, and runs exporters before importers.
When an import is not satisfied in the current set, discovery **widens** toward the
`sconstruct` root to find a matching export — including under
`--scripts=leaf/sconscript` when only the importer was named (multi-hop chains are
pulled until the import graph is closed). Pass `--strict-sconscript-exports` to
refuse that widen and fail if any Import needs a script outside the selected set.
Two scripts that export the same product name are an error (stricter than SCons,
which last-wins on a global pool). Native SCons `Export` / `Import` are also
recognised by the scan when names are string literals.

`ExportShared` / `ImportShared` are **variant-aware**: values are stored per
toolchain/variant/arch/abi (`tool_variant_dir`), so the same name exported under
`--dbg` and `--rel` resolves to the matching nodes for each variant. That is a
concrete reason to prefer the Cuppa API over native SCons `Export` / `Import`,
whose global pool is last-wins across the whole configure pass.

They are also **configure-time only**: they publish or read values while Cuppa
evaluates sconscripts. They do **not** create build-action nodes and do **not**
call `NotifyProgress.add` (same class as `BuildWith()` / `Filter()` — see
xref:methods.adoc#progress-tracking-and-variant-scoping[Progress tracking]).
Progress still comes from the `Build()` / `BuildTest()` / `Build*Lib()` targets
you pass around.

Without product imports, execution order stays the discovery walk (a flat graph).
When one discovered script nests another with ``SConscript(..., exports=...)``,
Cuppa **drops the nested path from the outer discovery invoke list** (string-literal
targets) and also skips a path if a live nested call already evaluated it for that
toolchain/variant. Prefer ``ExportShared`` / ``ImportShared`` for new layouts; nested
``SConscript`` remains supported for SCons-style ``exports=`` without double-running.

=== Project-rooted paths from a nested sconscript

Discovered scripts under a subdirectory (for example `test/sconscript`) still run with
that folder as the SCons working context for relative paths. A bare `extra/foo.cpp` or
`src/foo.cpp` is resolved relative to `test/`, not the project root next to `sconstruct`.
That bites when tests live under `test/` but shared helpers, includes, or other sources
sit beside the `sconstruct` (or elsewhere at the project root).

Use the SCons `{hash}/` prefix (project / `sconstruct` directory) when a nested script
must name sources, include roots, or globs that live at the project root:

[source,python]
----
# test/sconscript — sources live at the project root, not under test/
Import( 'env' )
libs = env.ImportShared( 'mylibs' )
env.BuildTest(
    'unit',
    [ '{hash}/test/unit.cpp', '{hash}/extra/helpers.cpp' ],
    LIBS = libs,
)
----

The same rule applies to `RecursiveGlob( ..., start='{hash}/src' )`,
`AppendUnique( CPPPATH=[ '{hash}/include' ] )`, and similar. Relative paths without
`{hash}/` remain correct for files that really sit beside the nested sconscript.
See also xref:methods/discovery.adoc[Source discovery] for `{hash}/` with
`Glob` / `RecursiveGlob`.

[#methods]
== Methods

Build helpers on the environment, for example `env.Build()`, `env.BuildTest()`, `env.BuildWith()`, `env.Compile()`, and `env.CreateVersion()`.
Cuppa enhances SCons with helpers that understand variants, toolchains, and cuppa's output layout.
Prefer those over vanilla SCons `Program()` and `Object()`, which skip that layout.
See xref:methods.adoc[Methods].
For how progress events and variant scoping work, see xref:methods.adoc#progress-tracking-and-variant-scoping[Progress tracking and variant scoping].

[#dependencies]
== Dependencies

Named packages of compile/link settings and optional fetch/build logic -- Boost, Qt4/Qt5, Quince, location-based header libraries, GitLab registry packages, or optional xref:dependencies/conan.adoc#conan-2-consumer-optional[Conan 2] graphs (`conan_deps` / `conan_dependency`).
Apply them with `auto_enable_dependencies` in `cuppa.run()` or `env.BuildWith('boost')` in a
`sconscript`. Built-ins are already imported; custom factories need `import_dependencies` too.
Publish Cuppa-built libraries with `env.PublishPackage` to GitLab generic packages or a Conan remote.
See xref:dependencies.adoc[Dependencies] and xref:packages.adoc[Publishing packages].

[#profiles]
== Profiles

Lightweight collections of environment tweaks (sometimes wrapping dependencies).
Example built-in: `quad_float` (links `quadmath`).
Apply with `auto_enable_profiles` or `env.BuildProfile(...)`.

[#variants-and-actions]
== Variants and actions

*Variants* select how binaries are compiled:

[cols="1,4"]
|===
| Flag | Meaning

| `--dbg` | Debug
| `--rel` | Release (optimised)
| `--cov` | Coverage-instrumented
|===

*Actions* run additional work after (or as part of) the build:

[cols="1,1"]
|===
| Flag | Meaning

| `--test` / `--force-test` | Run `BuildTest` / `Test` targets
| `--benchmark` / `--force-benchmark` | Run benchmark targets
| `--run` / `--force-run` | Run generic `Run` targets
|===

IMPORTANT: `--cov` does *not* imply `--test`. For a typical coverage workflow use both: `cuppa -D --cov --test`.

[#toolchains]
== Toolchains

A toolchain is a concrete compiler family/version (for example `gcc15`, `clang21`, or the generic aliases `gcc` / `clang` that resolve to whatever is on `PATH`).
Select with `--toolchains=gcc,clang` or wildcards such as `gcc*`.
See xref:toolchains.adoc[Toolchains].

[#platforms]
== Platforms and target architecture

Cuppa detects Linux, macOS (Darwin), and Windows.
The *target architecture* (for example `x86_64`) is tracked so multiple arch builds can coexist under the build root.

[#sconstruct-api]
== cuppa.run() parameters

Common keyword arguments to `cuppa.run()`:

[cols="3,7"]
|===
| Parameter | Purpose

| `default_options` | Dict of option keys *without* `--` (for example `{'offline': True}`)
| `default_projects` | Default list of `sconscript` paths
| `default_variants` | Restrict default variants (for example `['rel']`)
| `import_dependencies` | **Import** dependency factories into this sconstruct session so sconscripts can look them up and call `BuildWith` when they choose. Legacy alias: `dependencies`
| `auto_enable_dependencies` | **Auto-enable** subset: names or the same factories, treated as `BuildWith()` in every sconscript. Legacy alias: `default_dependencies`
| `import_profiles` | Import profile factories (legacy: `profiles`)
| `auto_enable_profiles` | Auto-enable profile names or factories (legacy: `default_profiles`)
| `default_runner` | Test runner name (default `process`)
| `configure_callback` | Optional SCons `Configure()` hook
| `tools` | Extra SCons tools for all environments
| `base_path` / `branch_root` | Project root / SCM branch root offsets
|===

`auto_enable_dependencies` is not a second import list. Put a **custom** factory in
`import_dependencies` to bring it into the session; put the same factory (or its
`.name()` string) in `auto_enable_dependencies` to auto-enable it. A custom factory only in
`auto_enable_dependencies` both imports and auto-enables. Built-ins (`boost`, `qt5`, …) and
pip entry-point plugins are already imported — list them only under `auto_enable_dependencies`
when you want every sconscript to `BuildWith` them.

[source,python]
----
MyPkg = cuppa.package_dependency( 'mypkg', ... )

cuppa.run(
    import_dependencies = [ MyPkg ],
    auto_enable_dependencies = [ MyPkg ],
)
----
