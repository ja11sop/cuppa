= GitLab packages
:description: Consume GitLab generic registry packages, including boost_package

Cuppa consumes GitLab **generic** package archives through `cuppa.package_dependency()` with
`package_manager = 'gitlab'`. See xref:dependencies-packages.adoc[Package dependencies] for the
factory overview.

== Authentication

|===
| Mechanism | Notes

| `GITLAB_REGISTRY_TOKEN` | Personal or project access token with package read (and write if publishing)
| `CI_JOB_TOKEN` | Used automatically in GitLab CI when available
| `--<name>-gitlab-custom-token` | Point at another env var / token setting for that package
|===

The `cuppa` launcher redacts env values whose names contain `TOKEN` in logged output.

To **publish** a Cuppa-built library to the same registry, see
xref:packages.adoc[Publishing packages].

[#boost-package]
== Boost package

`cuppa.packages.boost_package.define(...)` builds a `boost_package` dependency backed by the registry:

[source,python]
----
import cuppa

BoostPkg = cuppa.packages.boost_package.define(
    registry = 'https://gitlab.example.com/api/v4/projects/123/packages/generic',
    version = '1.85',
)

cuppa.run(
    dependencies = [BoostPkg],
    default_dependencies = ['boost_package'],
)
----

Use `package.use_libs([...])` helpers where provided to append the correct static library files
for the active toolchain/variant. The built-in source `boost` dependency accepts the same call
shape — `env.BuildWith('boost').use_libs([...])` — so switching supply chains does not require
rewriting sconscripts beyond the dependency name. See xref:dependencies-boost.adoc[Boost (source)].
